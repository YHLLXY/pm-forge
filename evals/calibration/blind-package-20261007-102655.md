## 打分锚点（同 judge 四维，1-5 整数）

- factuality（事实性/幻觉控制）：5=所有断言可溯源到输入材料，或明确标注【行业常识】并给出核实方式；3=个别断言无来源标注；1=存在编造事实且无任何标注

```
## 五、差异化与机会点

**结论先行：Q4 应把资源投向"快速记账的可视化表达"，而不是去做钱迹式的专业报表。** 即把"10 秒记账"的既有优势延伸到"看得懂的一眼报表"，而不是在报表专业度上与钱迹正面竞争。理由如下。

1. **我方唯一被验证的优势是速度，不能丢，行业里也没有人把它和"看得懂"绑在一起。** 用户好评集中在记账速度【依据输入】，这是我方 4 人小团队的护城河；钱迹强在深度报表、鲨鱼强在上手模板，两者都没有把"快"和"可视化易读"作为组合卖点。速度是获客钩子，易读报表是把钩子转化为留存的手段。

2. **"图表看不懂"是留存杀手，且解决成本低于做专业报表。** 差评集中在图表看不懂【依据输入】——这意味着已有用户在用报表、但被劝退，而非无人使用。修复"看不懂"（降低认知门槛、自动化解读）属于体验优化，不需要搭建钱迹级别的多维分析引擎，4 人团队在 Q4 周期内可控。

3. **不要在专业报表上与钱迹硬碰。** 钱迹是买断制的专业资产管理工具，长期位于财务榜前 20【依据输入】，其深度是长期积累的结果。我方以 4 人团队、面向年轻人的极简定位去追其报表专业度，投入产出比极低，且会侵蚀"10 秒"的速度优势。

4. **不要在广告模式上跟随鲨鱼。** 鲨鱼广告较多【依据输入】，其下沉市场用户对广告容忍度较高【推断】；我方面向年轻人，广告会直接伤害"极简"品牌感知。我方变现方式尚待明确（见第四章待验证项），建议在 Q4 决策中单独讨论，不与功能迭代混同。

**建议 Q4 落点（供讨论，非结论性数字）**：以"记账 → 看得懂的结果反馈"为闭环做 1-2 个可视化体验改进，功能范围收窄、深度控制在"用户能一眼看懂自己这个月的钱花在哪"，用访谈复测"看得懂"这一差评是否缓解。

**需在决策前补齐的关键空白**：我方变现方式、留存/活跃数据、报表功能的实际使用率——若报表使用率极低，则"图表看不懂"的影响面需重新评估（可能只有少数用户触达报表）。
```

```
原因只有一条：**差异化的前提是知道"我们是什么"，而用户材料里我方只有主观赞语，没有一个事实支点。** 在信息如此稀缺的情况下，任何"我们更懂年轻人""我们界面更美"的机会点，都是先有结论再找理由，投放到真实融资场景中经不起一个追问。

可以给出的、诚实的阶段判断：

1. **"身边同学用了都说好"不是差异化，是样本偏差。**（【推断】基于"身边同学"这一表述的天然同质性）它至少不能替代留存、复购、NPS 类指标。在 BP 里这样写，投资人的第一反应是"那你为什么还需要融资打仗"。
2. **真正的机会点必须先定义我们的"不做什么"。**（【推断】）面对随手记这样功能大而全的老牌产品，"功能特别多"不构成优势，反而可能意味着与对手正面同质化。差异化的常见可行方向包括：极简到极致、垂直人群（学生/自由职业者）、特定场景（自动记账/一键导入）、体验或隐私取舍——**但选择哪个方向，取决于我方产品实际能力，材料不足，无法定论。**
3. **MoneyWiz 的订阅路线是一条参照，不是答案。**（【行业常识】+【推断】）它在海外/进阶人群成立，不代表国内免费习惯下能直接复制，需结合我方用户付费意愿验证——而这项验证我们目前没有。
4. **最大的机会点，可能就在于"我们还没想清楚自己是谁"。** 这不是讽刺：在补充材料阶段，把"我方一句话定位 + 核心用户 + 一个别人做不到的点"找出来，是本项目最高优先级的动作，比再写十页竞品对比更值钱。

**给 BP 的可执行建议：** 在补齐我方事实之前，竞品页**不要写量化对比**，改为"我们选择不与随手记比功能数量、不与 MoneyWiz 比专业深度，我们专注服务于<待补充人群>的<待补充场景>"——但**括号里的内容，必须你先填**。
```

```
## 四、流程与交互

**主流程（读者提交评论）**

1. 读者在文章页评论区输入内容并提交。
2. 系统执行前置校验：频率限制（F4）→ 规则校验（F5：外链、关键词）。
3. 校验通过或需进一步判断的，进入垃圾识别判定，输出三种结果：直接放行、进入待审、拦截。
4. 放行的评论展示在评论区；待审与拦截的评论不出现在读者视图，写入作者管理视图。
5. 作者在管理视图复核，可放行或删除；放行的评论恢复展示。

**主流程（作者处理）**

1. 作者进入评论管理视图，默认展示「待处理」列表。
2. 列表按时间倒序，每条展示评论内容、提交时间、来源标识、命中原因。
3. 作者对单条执行「放行」「删除」；支持批量选择后批量操作。
4. 操作结果实时生效并更新列表状态。

**关键页面说明**

- 评论区（读者侧）：正常评论列表 + 输入框 + 提交反馈；不暴露反垃圾内部逻辑。
- 评论管理页（作者侧）：待处理列表 + 已放行/已删除列表，含拦截原因与来源标识。
- 反垃圾设置页：严格程度档位、关键词与域名黑白名单配置。【待补充：设置页是否属于本期范围，需与产品负责人确认】

**异常路径**

- 空态：无任何评论时，评论区展示引导文案；管理页无待处理记录时展示「暂无待处理评论」。
- 提交失败：网络或服务异常时，向读者展示可重试的失败提示，不丢失已输入内容。
- 限流触发：向读者展示明确但不暴露风控细节的提示（如「提交过于频繁，请稍后再试」）。
- 权限不足：非作者身份的访问者无法进入评论管理页与设置页，访问时返回无权访问提示。
- 识别服务不可用：识别服务超时或异常时，降级为「仅执行基础规则 + 进入待审」，避免直接放行全部评论。【待补充：降级策略是否可接受待审量激增，需与产品负责人及后端确认】
```

```
# PRD：降雨提醒

## 一、背景与目标

用户（城市通勤用户）在出门前无法及时获知即将降雨，导致淋雨、行程受阻。当前产品缺少主动式降雨提醒能力，用户在"出门决策"这一关键窗口内没有触达手段。

本需求的目标是提供降雨提醒，让用户在出门前收到通知，从而避免淋雨。提醒依赖第三方天气 API，该 API 最近 30 天可用率 97.2%，存在超时情况，因此提醒的时效性与稳定性存在不确定性。

**北极星指标**
- 降雨提醒到达后的有效出门避雨率：收到降雨提醒的用户中，在提醒触达后 30 分钟内发生"出门行为且未在自身位置检测到降雨时段"的比例，口径按"次/周·收到提醒的用户去重"。

**护栏指标**
- 提醒触达成功率：成功推送的提醒条数 / 触发的提醒条数，统计口径"次/日·触发提醒去重"，目标不低于 99%（需与第三方 API 可用率 97.2% 对齐后确认，见第六章）。
- 提醒准确率（误报率反向指标）：用户反馈"未下雨/无需提醒"的次数 / 收到提醒次数，口径"次/周·收到提醒用户去重"，用于控制过度打扰。
- 打扰率：单用户单日收到降雨提醒次数上限内的实际触达次数分布，口径"次/日·登录用户去重"，用于防止通知过载。

## 二、用户与场景

**目标用户**：城市通勤用户，日常依赖公共交通或步行/骑行出门，对出门时段的天气敏感。

**核心场景一句话**：城市通勤用户在准备出门前，需要知道目的地或当前位置是否会降雨，以便决定是否带伞、提前出发或改变出行方式。

【待补充：目标用户的城市范围/地域覆盖要求、是否区分通勤时段（早高峰/晚高峰）的提醒优先级、需要谁确认——待产品与业务负责人确认】

## 三、用户故事与功能需求

| 编号 | 用户故事 | 优先级(P0/P1/P2) | 验收标准 |
|---|---|---|---|

## 四、流程与交互

3. 系统判断预测降雨时间窗是否落在用户生效时段内、且满足提前量条件。
4. 满足条件则生成提醒任务，通过推送渠道下发通知。

**关键页面**
```

```
本次分析的决策目的是：**判断"县城小商户简易记账+赊账登记"这一细分定位是否存在立项空间，以及现有记账类竞品在多大程度上已经覆盖该需求。** 因此下文重点不是罗列大厂功能，而是回答三个问题：(1) 现有竞品是不是我们的直接对手；(2) 它们在"赊账/欠款"这个核心场景上的覆盖深度；(3) 我们若立项，应打哪个差异点。

## 二、市场与竞品选择

### 竞品分层

**直接竞品（个人记账工具下沉到小商户场景）**
- **钱迹**：主打"纯净、无广告、轻量"的个人记账工具，以快速记账和简洁体验见长。选择理由：它代表了一批"轻量个人记账"产品，最可能被小商户顺手拿来记账。【行业常识】
- **鲨鱼记账**：以极简操作为卖点的个人记账 App，面向个人日常收支。选择理由：操作路径最短，与"小商户要快"的诉求一致，是低门槛替代方案。【行业常识】
- **随手记**：老牌个人/家庭记账工具，功能体系较完整，历史上向多账本、生意账方向延伸过。选择理由：它可能是竞品中最接近"小商户/生意记账"的一个。【行业常识】

**间接竞品（更重或更工具化的记账产品）**
- **挖财**：老牌记账与个人理财平台，功能覆盖记账、理财等。选择理由：代表"记账+理财"的平台型路线，商业模式与纯工具不同。【行业常识】
- **MoneyWiz**：面向多币种、多账户的个人财务管理工具，偏专业与跨平台。选择理由：代表"专业财务工具"路线，可作为功能上限的参照，但用户群与县城小商户大概率不重合。【行业常识】

### 重要缺口提示

上述 5 个竞品**没有一个是"县城小商户赊账登记"的专门产品**。真正的直接威胁可能来自用户未列出的品类：**进销存 App、店铺管理/收银类工具、以及微信/纸质账本**。【推断】建议在正式立项前补做一轮"替代品"扫描，见第五章机会点。

## 五、差异化与机会点

**结论先行：存在一个清晰但未被验证的机会窗口——"赊账往来"是小商户的高频刚需，而现有 5 个竞品全部是为个人记账设计的，预计在赊账场景覆盖极弱。但这只是假设，立项前必须用实地调研把它证实或证伪，不要凭此直接立项。**

判断与依据：

1. **主机会点：赊账/往来账，而非记账本身。** 个人记账 App 的记账体验已相当成熟，我方在"记一笔"上难以做出代差；但"谁欠我多少钱、欠了多久、什么时候结清"是个人记账产品结构上不擅长、也不关心的场景。【推断】这是最可能拉开差异的方向。

2. **风险一：真实竞品可能不在这个清单里。** 小商户的替代方案更可能是**进销存/店铺管理工具、收银工具，甚至微信备注和纸质账本**，而不是个人记账 App。若不做替代品扫描，容易"在错误的战场上找到机会"。【推断】

3. **风险二：需求真实性与付费意愿未验证。** 县城小商户是否愿意为"记账+赊账"单独装一个 App 并付费，缺乏材料支撑，**待验证**。这是决定立项与否的第一变量。

4. **风险三：极简与功能覆盖的张力。** 目标用户对操作复杂度的容忍度可能很低，"赊账管理"若做得太重，反而失去易用性优势。需要在产品设计上做取舍。【推断】

**建议的下一步验证动作（立项前必做）**：
- 实地访谈 10-20 位县城小商户，核实赊账是否高频、现在怎么记、痛点有多痛；
- 实测 5 个竞品的赊账相关功能，坐实第四、五章的评分；
- 补扫进销存/店铺管理类替代品，确认竞争真实边界；
- 核实各竞品的商业模式与规模数据（见第六章）。
```
