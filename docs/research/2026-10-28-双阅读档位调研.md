# 2026-10-28 双阅读档位调研（专业版 / 简明版）

> 触发：用户 2026-10-28 反馈「每个项目的叙事是不是有些过于专业化了……有没有必要做两套文案？一套给专业的人，一套给小白，像暗色和亮色一样一键切换」。
> 本文只回答三个问题：**这件事有没有成熟做法、代价是什么、我们该选哪条路**。实施细节在 `../plans/2026-10-28-双阅读档位计划.md`。

## 0. 结论先行

1. **机制是成熟的，内容不是。** "一键切换"在工程上等同主题切换（`<html>` 上一个属性 + localStorage + URL 参数），Docusaurus 的 Tabs 组件已经把 `groupId`（全站同步 + localStorage 记住）和 `queryString`（分享链接带上选择）做成了公开 API，可以直接照抄思路。
2. **"两套完整文案"是这个方案里最贵、最容易坏的一种实现。** 两套 = 两份事实，改一处要改两处，且门禁查得出"结构不一致"，查不出"两种说法互相矛盾"。本项目自己就吃过副本漂移的亏（README 里记过事故）。
3. **现成的"受众开关"只有一个小项目。** `mkdocs-audience-toggle`（2026-10-01 发布 v0.1.1，MIT，GitHub ★0）做的正是这件事：**一份正文**，给段落打标 `{: data-audience-hide="beginner" }`，切换档位时隐藏/显示这些块，状态存 localStorage，切页不丢。**它是"隐藏块"模型，不是"两套文案"模型**——这一点决定了我们的取舍。
4. **推荐方案 C：一份正文 + 每节一句白话导读 + 深水块标注 + 全局档位开关。** 白话导读解决"读不下去"，隐藏块解决"细节太多"，两者共用一份事实来源。

## 1. 问题到底是什么

用户的原话是"叙事过于专业化，读者没有读下去的欲望"。拆开看是两件事，它们的解法不同：

| 症状 | 本质 | 换文案能解决吗 | 隐藏内容能解决吗 |
|---|---|---|---|
| 满屏"注册中心""双适配器""报童模型"，看不懂 | **术语密度**高 | ✅ 必须重写那几句话 | ❌ 隐藏不掉主干 |
| 讲了太多实现细节，找不到结论 | **信息密度**高 | ⚠️ 重写会丢信息 | ✅ 隐藏"深水区"段落 |
| 读完不知道"所以呢" | **缺摘要层** | ✅ | ❌ |

只做"两套文案"= 同时解决三件事，但成本 ×2；只做"隐藏块"= 只解决第二件。所以真正的解是"摘要层 + 隐藏块"，而"两套文案"是把摘要层写成了另一整篇。

## 2. 方案盘点

评估维度：事实来源数、维护成本、漂移风险、体积、SEO、实现难度。以本站 5 篇案例的实际体量评估（实测：单页 HTML 45–51 KB，正文 1,164–2,500 汉字，每篇 5 个二级标题）。

### A. 两篇独立文章（`/case-studies/x/` + `/case-studies/x/simple/`）

- 做法：写两篇 md，两套路由，互相加"换一种读法"链接。
- 事实来源：**2 份**。
- 成本：正文写两遍（5 篇平均 1,600 字 ≈ 8,000 字/版，两版合计 16,000 字），改一次要改两处。
- 风险：漂移（一份改了另一份忘）、SEO 重复内容（要 canonical 互指）、导航多一层。
- 现成实现：Simple English Wikipedia 是这种形态（同主题、独立站点/页面）。
- 结论：**不推荐**，除非两版内容差异大到"不是同一篇文章"。

### B. 一份正文 + 隐藏块（mkdocs-audience-toggle 模型）

- 做法：正文里给"深水"块打标，切到"简明"档时 `display:none`。
- 事实来源：**1 份**。
- 成本：标注工作量（每篇挑 3–6 块）+ 组件 + 门禁。
- 风险：**主干文字仍然是专业的**——隐藏掉细节后，剩下的句子还是"注册中心架构 + 单向依赖"这种，读者照样卡住。
- 结论：机制可用，内容不够。

### C. 一份正文 + 每节白话导读 + 隐藏块（推荐）

- 做法：每个 `##` 小节的第一段固定是 40–70 字的白话导读（谁、遇到什么、做了什么、结果多少），深水块打 `data-depth="deep"`。简明档 = 导读 + 关键数字；完整档 = 全文。
- 事实来源：**1 份**（导读是正文的摘要，不是另一套说法）。
- 成本：每篇 5 段导读 ≈ 300 字，5 篇 ≈ 1,500 字；组件与门禁 4–6 小时（详见计划 §3–4）。
- 风险：导读与正文可能说岔（门禁只能查"有没有"，查不出"对不对"）→ 用"导读必须包含正文里的数字"这类可机检的约束兜底。
- 结论：**推荐**。

### D. 渐进披露（`<details>` 折叠，不做全局开关）

- 做法：每节默认白话，技术细节折叠在"展开实现细节"里。
- 事实来源：1 份。
- 成本：最低（无状态、无 JS）。
- 风险：读者要一处处点开；打印/PDF 里折叠内容默认不展开（除非 `open`）；没有"整体档位"的心理暗示。
- 结论：作为 C 的降级备选（如果不想引入全局状态）。

| 方案 | 事实来源 | 维护 | 漂移风险 | 体积增量 | SEO | 实现 |
|---|---|---|---|---|---|---|
| A 两篇 | 2 | 高（×2） | **高** | +100% | 需 canonical 互指 | 低 |
| B 隐藏块 | 1 | 低 | 低 | ≈0 | 低 | 低 |
| **C 导读+隐藏** | **1** | **中** | **低** | **<5%** | **低** | **中** |
| D 折叠 | 1 | 低 | 低 | ≈0 | 低 | 最低 |

## 3. 外部证据（2026-10-28 取）

### 3.1 机制：Docusaurus Tabs（MIT）

官方文档（`docusaurus.io/docs/markdown-features/tabs`）两个 props 正好是我们要的：

- `groupId`：**同一 groupId 的所有 Tabs 联动，选择会存进 localStorage**，切页保留。
- `queryString`：把当前选择写进 URL 查询参数，**可以分享"打开就是某一档"的链接**。

这条是"一次选择、全站一致、可分享"的成熟答案，本站的档位开关按同样语义设计（`data-level` + localStorage + `?level=`）。

### 3.2 模型：mkdocs-audience-toggle（MIT，★0，2026-10-01 v0.1.1）

- 声明式标注：`{: data-audience-hide="beginner" }`（pymdownx attr_list）。
- **"By default all content is otherwise available in all modes"** —— 默认全显示，档位只负责隐藏。
- **"State persists across pages via localStorage"**，**"Switching modes updates the page without reloading it"**。
- 诚实判断：**只有 1 位作者、0 star、发布不到一个月**。可以当参考实现读，**不能**当"经过大规模验证的方案"。它的价值在于印证"隐藏块"模型是可行且实现成本低的，不在于它的流行度。

### 3.3 标准：复杂信息应当提供简化版

- **WCAG 3.1.5 Reading Level（AAA）**：In Brief 原文是 "Users can get a simplified version of complex information. / When text information becomes complex, create a more easily understood version."（`w3.org/WAI/WCAG21/Understanding/reading-level.html`，2026-10-28 取）。标准层面的态度很直接：**复杂信息要配一个简化版**。它同时说明简化版是"同一内容的另一种说法"，不是"另一套事实"。
- **ISO 24495-1:2023（Plain language）**：写作原则标准。本站只取三条：句子短、主语明确、术语首次出现要解释。*（注：iso.org 有反爬，本次未取到正文，只引用标准名与主题，不引用条款原文。）*
- **Diátaxis**（`diataxis.fr`）：主张按"读者的任务"分文档类型（教程/操作/参考/解释），而不是按"读者的水平"复制两份内容。它的立场可以作为"不要做两套文案"的旁证：**同一篇里分层，比另起一篇更符合文档工程的经验**。

### 3.4 检索记录（怎么找的，找到了什么）

GitHub 仓库检索（2026-10-28，`api.github.com/search/repositories`）：

| 关键词 | 命中 | 结果 |
|---|---|---|
| `audience toggle documentation` | **0** | —— |
| `reading level toggle docs` | 2 | 均不相关（一个是 FTC 机器人仓库） |
| `dual audience documentation` | 4 | 全是 2026 年新出的 AI 写作技能/插件（★0–2），不是界面方案 |
| `mkdocs audience toggle` | 1 | `luka-sherman/mkdocs-audience-toggle`（★0，MIT，2026-10-01） |

**结论**：这个需求在开源世界里**没有"被广泛采用的现成方案"**。有的是：① 文档框架里通用的"多版本内容"机制（Docusaurus Tabs、Material content tabs）；② 一个 3 周前发布的单人插件，把"隐藏块 + 档位"做成了 MkDocs 插件。

所以本站不能"装个包解决"，只能**照着已验证的机制自己拼**——而这套机制本站已经有了（主题切换就是同一套：`<html>` 属性 + localStorage + 内联无闪脚本）。工程量因此很小，真正的成本在**写导读**。

### 3.5 交互：渐进披露

NN/g（`nngroup.com/articles/progressive-disclosure/`）："Progressive disclosure defers advanced or rarely used features to a secondary screen, making applications easier to learn and less error-prone." —— 默认收起高级内容、需要时再展开，是被验证过的降低认知负荷的方式。

## 4. 为什么不做"两套完整文案"（我们的判断）

1. **漂移**：本项目 README 记过一次"两处各存一份文档 → 副本漂移"的事故；两套正文是同一类风险，只是换成文案。
2. **门禁管不住语义**：现有 12 道门禁能查死链、标题层级、数字一致性，查不出"简明版说 3 天交付、完整版说 4 天"。
3. **读者会丢位置**：切档后如果整篇换掉，滚动位置、正在读的那句都没了；隐藏块模型下版面骨架不变，只是密度变化。
4. **SEO 与搜索**：两个 URL 要 canonical 互指、互相加链接；而站内 pagefind 会把两版都索引，搜出来还得猜是哪一版。一份正文 + 隐藏块只需要给隐藏块加 `data-pagefind-ignore`。
5. **成本**：5 篇 × 1,600 字 × 2 ≈ 16,000 字，且以后每改一次都是两处。

## 5. 推荐方案 C 的形态（给计划用）

- **数据**：用一个小 rehype 插件按 `h2` 把正文拆成 `<section data-section>`，每段首段加 `.lead`；深水块 `data-depth="deep"`（详见计划 §4.5）。
- **状态**：`<html data-level="plain|full">`；localStorage `pm-level`；`?level=` 可覆盖并写回。
- **无闪烁**：复用 `Layout.astro` 里那段 inline 脚本（现在只读 theme），加读 level，一次性写两个属性。
- **控件**：页头主题按钮左侧的 segmented control（`简明 / 完整`），`role="group"` + `aria-pressed`；移动端收进同一行。
- **默认档**：简明（面试官/HR 先看），完整档记住上次选择。
- **打印**：始终完整版（`@media print` 里忽略档位）。
- **搜索**：隐藏块挂 `data-pagefind-ignore`。
- **门禁**：新增 `check-levels`（6 条断言，见计划 §4.6）。

## 6. 成本与分期（粗估）

| 期 | 范围 | 工作量 | 产出 |
|---|---|---|---|
| P0 | 2 篇（个人工作台、情侣心愿）：30 秒版 + 每节导读，**不做开关** | ≈3 h | 先验证"导读写得对不对"，零状态零风险；导读在 P1 直接复用 |
| P1 | 同上 2 篇 + 开关组件 + rehype 分包 + 门禁 | 4–6 h | 可点、可分享、可打印 |

| P3 | 数据分析 2 篇 / 拆解 4 篇 / 工具箱 4 篇 | 8–12 h | 全站一致（合计 19–27 h） |

## 7. 待验证 / 待用户拍板

1. **默认档位**：简明（推荐）还是完整？
2. **范围**：只案例，还是全站？
3. **是否接受"简明档隐藏部分内容"**（方案 C 的前提）——如果不接受，就退回 A（两套文案），成本翻倍。
4. **导读的责任人**：导读必须由我写、用户审，还是用户给要点我润色？（涉及"事实只能由当事人确认"的边界）
5. **性能实测**：每页 +300–400 字对 LCP/TTFB 的影响（预计 <1%，需 build 后实测）。
6. **无障碍**：切档后是否需要 `aria-live` 播报"已切换到简明版"（初步判断：需要一句，避免屏幕阅读器用户不知道内容变了）。
