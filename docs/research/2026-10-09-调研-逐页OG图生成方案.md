### A2 `default-og.jpg` vs `og-default.png` —— **不是线上 bug，是死回退值**（你的判断正确）

完整赋值链：

```ts
// site/src/config.ts:11
const DEFAULT_OG_IMAGE = "default-og.jpg";

// site/src/config.ts:16
ogImage: userConfig.site.ogImage ?? DEFAULT_OG_IMAGE,   // ← 只有 userConfig 没写才生效
```

```ts
// site/astro-paper.config.ts:11
ogImage: "og-default.png",       // ← 用户配置写了
// site/astro-paper.config.ts:18
dynamicOgImage: false,           // ← 关掉了动态回退
```

```ts
// site/src/utils/resolveDefaultOgImagePath.ts:24-47
const filename = config.site.ogImage;           // "og-default.png"
// ...:25-33 目录穿越守卫（含 ".."、"/"、"\\" 即 throw）
if (config.features.dynamicOgImage) {           // false，跳过
  return existsInPublic(filename) ? getAssetPath(filename) : getAssetPath("og.png");
}
if (!existsInPublic(filename)) {                // og-default.png 存在 → 不 throw
  throw new Error(`AstroPaper: missing public/${filename}...`);
}
return getAssetPath(filename);                  // → "/og-default.png"
```

**核实结果**：`public/og-default.png` 真实存在（`C:\dev\pm-forge\site\public\og-default.png`，37,318 字节）。所以 `DEFAULT_OG_IMAGE = "default-og.jpg"` 这行 **当前完全不参与任何计算**，是死代码。你上一轮的自我修正是对的。

⚠️ **但它是个陷阱**：谁要是把 `astro-paper.config.ts:11` 那行删了，config 就回退到 `"default-og.jpg"` → `existsInPublic("default-og.jpg")` 为 false → 因为 `dynamicOgImage:false`，**第 41-45 行直接 throw，构建失败**。是好消息（fail loud，不会静默上线一张 404 图），但不该留。

**建议改法**（二选一，都是一行）：

```ts
// site/src/config.ts:11 —— 方案一：只消除陷阱，行为不变
const DEFAULT_OG_IMAGE = "og-default.png";
```

```ts
// site/src/config.ts:16 —— 方案二（更彻底）：删掉回退，让缺配置直接漏出来
ogImage: userConfig.site.ogImage,   // 类型上改成必填
```

### A3 `dynamicOgImage: true` 在本仓库会不会 404 —— **会**

已核实：`site/src/pages` 下**不存在任何 og 端点**。

- `glob("**/og*", path=site/src/pages)` → 返回空数组 ✅
- `grep "og\\.png|og\\.ts|og\\.js"` 在 `src` 下只命中 3 处**文档注释**（`src/types/config.ts:28`、`src/utils/resolveDefaultOgImagePath.ts:18/38/43`），无实现 ✅

**准确描述**：

| 当前状态 | `dynamicOgImage` | 结果 |
|---|---|---|
| `public/og-default.png` 存在 | `false`（现状） | `/og-default.png` ✅ 正常 |
| `public/og-default.png` 存在 | `true` | `existsInPublic` 先命中 → 仍返回 `/og-default.png`，**不会**走 `og.png` 分支 |
| 删掉 `public/og-default.png` | `true` | 回退 `getAssetPath("og.png")` → 但没有任何路由产出 `/og.png` → **线上 404 且构建成功（静默失败）** |
| 删掉 `public/og-default.png` | `false` | 构建 throw（fail loud） |

所以 `dynamicOgImage: true` **只有在默认图不存在时**才会踩雷，而那种情况下会静默产出死链——这比 throw 更危险。既然我们要做逐页 OG，这个开关的语义应该被替换掉（见 B3）。

### B0 两条路线 + 一个对比（含 🧪 本机实测）

### B1 路线①：satori + @resvg/resvg-js

#### 版本与运行时要求（✅ 2026-10-09 查 `registry.npmmirror.com/<包名>/latest`）

| 包 | 最新版 | `engines` | License | 备注 |
|---|---|---|---|---|
| `satori` | **0.47.1** | `node >=16` | MPL-2.0 | 依赖含 `harfbuzzjs`、`@shuding/opentype.js`、`linebreak` |
| `@resvg/resvg-js` | **2.6.2** | `node >=10` | MPL-2.0 | 无 node-gyp/postinstall；平台二进制走 `optionalDependencies`（含 `@resvg/resvg-js-win32-x64-msvc` 等） |
| `subset-font` | **2.9.0** | — | BSD-3-Clause | harfbuzzjs 的 wasm 子集器，纯 npm，无需 Python |

本机 `site/package.json` 要求 `node >=22.12.0`，实际运行 v24.18.1 → 两者都满足 ✅。

#### 字体要求（✅ 官方 README 原文）

> "Satori currently supports three font formats: TTF, OTF and WOFF. **Note that WOFF2 is not supported at the moment.**"
> —— `https://unpkg.com/satori@0.47.1/README.md` 的 `## Fonts` 章节

**你的判断正确：satori 只吃 TTF / OTF / WOFF，不吃 WOFF2。** 这一点很关键，因为网页端自托管字体几乎都是 woff2 —— **同一份字体文件不能两边复用**，OG 生成必须另外准备 ttf/otf/woff。

#### 最小可运行示例（🧪 我实际跑通的版本）

> 我用的是**纯对象元素树**，不装 React 也能跑（satori README 明确支持这种写法，也支持 satori/jsx 的实验性内置 JSX）。

```js
// gen-og.mjs
import { readFileSync, writeFileSync } from "node:fs";
import satori from "satori";
import { Resvg } from "@resvg/resvg-js";

const W = 1200, H = 630;
// 必须是 ttf / otf / woff —— woff2 会直接报错
const font = readFileSync("./fonts/NotoSansSC-400.ttf");

// satori 接受 { type, props: { style, children } } 的纯对象
const element = {
  type: "div",
  props: {
    style: {
      width: W + "px", height: H + "px",
      display: "flex", flexDirection: "column", justifyContent: "center",
      backgroundColor: "#fbfaf8",        // ← 必须字面量，不能写 var(--background)
      fontFamily: "Noto Sans SC",        // ← 必须与下面 fonts[].name 完全一致
      padding: "80px 72px",
    },
    children: "红岩集团访谈复盘：把 90 分钟访谈变成 12 条可执行洞察",
  },
};

const svg = await satori(element, {
  width: W,
  height: H,
  fonts: [{ name: "Noto Sans SC", data: font, weight: 400, style: "normal" }],
});

const png = new Resvg(svg, {
  fitTo: { mode: "width", value: W },
  // satori 默认 embedFont=true，SVG 里文字已经变成 <path>，
  // 所以这里不需要字体；关掉系统字体扫描还能更快
  font: { loadSystemFonts: false },
}).render().asPng();

writeFileSync("./og.png", png);
```

`@resvg/resvg-js` 的 API 名字我逐个核对过（来自 `https://unpkg.com/@resvg/resvg-js@2.6.2/index.d.ts`）：
`new Resvg(svg, options)`、`.render()` → `RenderedImage`、`.asPng()` → `Buffer`、`.width` / `.height`；
`options.fitTo` 是 `{ mode: 'original' | 'width' | 'height' | 'zoom', value }`；
`options.font` 支持 `loadSystemFonts`（默认 true）、`fontFiles`、`fontDirs`、`defaultFontFamily`。

```
    at Object.parseFvarTable [as parse] (@shuding/opentype.js/dist/opentype.js:10321:16)
    at CC.addFonts (satori/dist/index.cjs:10:77300)
```

**踩坑点是 `fvar` 表**（变量字体的轴定义表）。现在 Google Fonts 的 Noto Sans SC 默认就是 VF，所以这个坑很容易踩。

**✅ 已验证的绕法**：先用 harfbuzz 把 VF **实例化**到具体字重，再喂给 satori：

```js
const inst = await subsetFont(vfBuffer, glyphs, {
  targetFormat: "sfnt",              // sfnt = ttf
  variationAxes: { wght: 400 },      // 把轴钉死 → 输出静态实例，fvar 变得可解析
});
// → 21,808 B，satori 渲染成功 ✅
```

#### ⚠️ 陷阱 2：CSS 变量不会被解析

`Cover.astro` 里大量使用 `var(--section-case)`、`var(--surface-2)`、`var(--foreground)`、`var(--border)`、`var(--muted-foreground)`。satori **不会去读 `theme.css`**，遇到 `var(...)` 不会求值。

要在 OG 图里复用站点的视觉语言，必须把 token 抽成一份 JS/TS 常量再传字面量。你给的浅色 token 应当落到一张共享映射表里（例如 `site/src/utils/ogTokens.ts`）：

```ts
export const light = {
  background: "#fbfaf8", foreground: "#1c1b1a", accent: "#0b6bcb",
  surface1: "#ffffff",   surface2: "#f5f2ed",   border: "#e6e2db",
  muted: "#6b655c",      warm: "#a24d05",
  section: {
    case: "#0b5fa5", analysis: "#0f6b73", dissection: "#4f46b8",
    story: "#a24d05", toolbox: "#2a6b45",
  },

```

> ⚠️ 我**没有**去读 `site/src/styles/theme.css` 交叉核对这几个色值（它们来自你消息里的转述）。落地前请以文件为准。

#### ⚠️ 陷阱 3：`Cover.astro` 的衬线 kicker 字体

`Cover.astro:83` 写的是 `font-family="Georgia, 'Times New Roman', serif"`。satori 里没注册的字体不会自动回退到系统字体，要么一起传一份衬线字体，要么改成已注册的无衬线 —— 否则 kicker 那行可能渲染异常。

**我的建议**：OG 图**不要**照抄 `Cover.astro` 的 SVG 结构（它是为屏幕上的 536×301 小卡设计的，字号按 `fitSize` 算），而是**重写一份 1200×630 的 satori 组件**，只复用 token 和版式规则（左侧板块色条、kicker、大标题、副标题、底部域名）。理由见 B5。

### B2 中文字体与动态子集

#### B2.1 先排除一个选项：`cn-font-split` 不适合这个场景

`cn-font-split` 最新版 **7.4.3**（Apache-2.0，✅ registry），它的定位是「把字体切成大量分包 + 生成配套 CSS，供浏览器按需加载」（README 原文：「通过高性能的各种技术将庞大的字体包拆分为适合网络分发的版本」「单个分片目标大小 `chunkSize`」）。**它是给网页 webfont 分发用的，不是给"生成一张 PNG 时需要一份完整字体"用的。** OG 生成需要的是**一个能解析的字体的单文件**，不是一堆分包。→ **不要用。**

（如果你哪天要做网页端中文字体自托管 + `unicode-range` 分片，那才是它的主场；那是另一个议题。）

#### B2.2 正确的工具：`subset-font`（harfbuzzjs 的 wasm 版 hb-subset）

`subset-font@2.9.0`，API 来自官方 README（✅ `https://unpkg.com/subset-font@2.9.0/README.md`）：

```ts
subsetFont(buffer, text, options): Promise<Buffer>
// options.targetFormat: 'sfnt' | 'woff' | 'woff2'
// options.variationAxes: { wght: 400 }  ← 实例化变量字体
// options.keepAllGlyphs, options.preserveNameIds, options.keepFeatures
```

好处：**纯 npm，WASM，不需要 Python / fonttools / 系统字体工具链**，在 Vercel 构建镜像里也能跑。

#### 🧪 实测数字（本机，Node v24.18.1）

| 场景 | 输入 | 输出 | 耗时 |
|---|---|---|---|
| 单页动态子集（约 40 个不同字符） | `simhei.ttf` 9,745,792 B | `sfnt` **12,160 B** / `woff` **7,704 B** | 28 ms |
| 单页动态子集（VF 实例化） | `NotoSansSC-VF.ttf` 17,773,244 B | `sfnt` **21,808 B** | 11 ms |
| **全站字符集**子集（19 个内容文件，**1,304 个不同字符**） | 同上 | VF 保留变量轴 **691,356 B (0.66 MB)**<br>实例化 wght400 **412,404 B (0.39 MB)**<br>实例化 woff **258,904 B (0.25 MB)** | 38 ms / 18 ms |

**结论：中文 OG 图的字体问题比想象中小得多。**
- 想要极致（每页一套字）：**约 12–22 KB/页**，直接不落盘也行。
- 想要简单（一次子集、全站共用）：**约 0.4 MB/字重**，完全可以入库。

#### B2.3 针对「文章标题里的字」做动态子集：可直接用的代码

关键点：**必须把这一页会出现的所有字符都算进去**，不只是 `title`。漏一个字符，satori 渲染到那个字时会缺字形（产出空白或豆腐块，且**不会报错**）。

```js
// site/scripts/og/subset.mjs
import subsetFont from "subset-font";

/** 收集一张 OG 图上会出现的全部字符 */
export function collectGlyphs(card) {
  const parts = [
    card.title,            // 标题
    card.description,      // 副标题
    card.sectionLabel,     // 板块名，如「案例研究」
    card.dateText,         // "2026-10-09"
    card.siteTitle,        // "余翰林 · 产品作品集"
    card.domain,           // "yuhailinlxy.com"
    "…",                   // Cover 的截断符号，标题被截断时会用到
  ];
  // 去重后拼成字符串；harfbuzz 按码点取字形
  return [...new Set(parts.join(""))].join("");
}

export async function buildFont(sourceFontBuffer, card) {
  const glyphs = collectGlyphs(card);
  return subsetFont(sourceFontBuffer, glyphs, {
    targetFormat: "sfnt",            // ⚠️ 必须 sfnt/woff，不能 woff2（satori 不支持）
    variationAxes: { wght: 400 },    // ⚠️ VF 必须实例化，否则 satori 崩（见 B1 陷阱 1）
  });
}
```

**健壮性兜底（强烈建议）**：因为「漏字不报错」，加一道**子集覆盖率断言**——用同一份 `collectGlyphs` 的输出做长度对照，或者干脆把每个字符都做一次 codepoint 存在性检查。最省事的做法是：子集化后**同时保留一个「常用字兜底集」**（例如 site 全站 1,304 字那版 0.39 MB 的字体），一旦某页出现超集外字符就自动降级到全量字体并告警。考虑到 0.39 MB 本来就不大，**更简单的做法是干脆不按页子集，直接用全站字符集那一版**。

#### B2.4 字体来源与授权（这一条有法律风险，请务必看）

| 来源 | 能否用 | 说明 |
|---|---|---|
| `C:\Windows\Fonts\simhei.ttf` / `msyh.ttc` / `Deng.ttf` | ⚠️ 本地渲染可以，**不要提交进仓库 / 不要随站点分发** | 微软随 Windows 分发的字体，再分发需另行授权 |
| `C:\Windows\Fonts\NotoSansSC-VF.ttf` | ✅ 可自由使用（OFL-1.1） | 本机确有此文件（17,773,244 B）✅ |
| `@fontsource/noto-sans-sc` v5.3.1 | ⚠️ 未核实其是否含 ttf/otf | fontsource 主要发 woff2，**而 satori 不支持 woff2** —— 不要想当然 |
| `@expo-google-fonts/noto-sans-sc` v0.4.4 | ⚠️ 未核实内容 | 该系列通常发 TTF，但我没下载 tarball 验证 |
| Google Fonts 官方 TTF（`github.com/google/fonts`） | ✅ OFL-1.1 | 从本机 `raw.githubusercontent.com` **抓不通**（测过，见来源清单），构建时下载也不可靠（GFW） |

**我的建议**：字体文件（无论全量还是子集）**不要进 git**，改用「本地预生成」路线，把字体路径写成一个可配置项（默认探测 `C:\Windows\Fonts\NotoSansSC-VF.ttf`，可用环境变量覆盖）。这样：
- ✅ 不涉及再分发
- ✅ 仓库不膨胀
- ⚠️ 代价：换机器要能装到同一字体 —— 需要在 README 写清楚，并在门禁脚本里做**存在性检查**（字体缺失就报错，不要静默出图）

如果哪天真要 CI 生成，再考虑把「全站字符集子集」（0.39 MB）提交进仓库 —— 体积可控，且 OFL-1.1 允许再分发（需保留许可证文件）。

#### B2.5 `unicode-range` 在这个场景里**不适用**（避免走弯路）

`unicode-range` 是 CSS `@font-face` 的描述符，作用是告诉**浏览器**「这个字体文件负责哪些码点，按需下载」（MDN ✅ 页面可达）。它的作用域是**浏览器里的 webfont 加载**。

而 OG 生成是**构建期的 Node 进程把自己 rasterize 成 PNG**，中间没有浏览器、没有 CSS 字体加载、没有按需下载。
→ **`unicode-range` 对 OG 图生成零作用**。你真正需要的是 B2.2 的那种子集化（把字库裁小），而不是 `unicode-range`（把字体切成多份让浏览器挑）。

#### B2.6 备选：`fonttools pyftsubset`（⚠️ 未在本机实测）

如果哪天更想用 Python：

```bash
pyftsubset NotoSansSC-VF.ttf --text-file=chars.txt --output-file=NotoSansSC-subset.ttf --layout-features='*' --glyph-names --symbol-cmap --legacy-cmap --notdef-glyph --notdef-outline --recommended-glyphs --name-IDs='*' --name-legacy --name-languages='*'
```

⚠️ 我只确认了 fontTools 官方文档页面可达（`fonttools.readthedocs.io/en/latest/subset/index.html`），**没有在本机跑过 `pyftsubset`，也没验证上述参数组合是否与当前 fontTools 版本完全一致**。这条仅在「你已经决定要引入 Python 工具链」时才值得考虑；否则 `subset-font` 更省事。

#### 🔴 `astro:build:done` 的一个关键限制（决定了它不适合当主方案）

钩子参数里**只有 `pathname`，没有内容集合的数据**。

`getCollection()` 是 `astro:content` 的虚拟模块，**只在 Astro 页面/端点上下文里可用**，在 integration 里 import 不到。所以如果你在 `astro:build:done` 里生成图，就得**自己再解析一遍 markdown frontmatter**（意味着要引 `gray-matter` 之类的依赖，或手写 YAML 解析），而且会和 `content.config.ts` 的 zod schema **形成第二套真相**。

**结论**：`astro:build:done` 适合做「后置校验」（拿 `dir` 扫产出的 PNG），**不适合做「生成」**。

#### ✅ 方案 C（**推荐**）：独立 npm script + 产物入库 + 陈旧门禁

**思路**：OG 图是「派生产物」，但它变化频率远低于内容；把它当成**版本控制里的构建产物**，用一个脚本保证它不陈旧。

**为什么不放进构建**：
1. 不引入 Chromium（430 MB）或「字体必须进仓库」的耦合；
2. Vercel 构建时间不增加；
3. 图与内容的一致性可以被**显式门禁**覆盖，而不是「碰巧构建时就对」。

**目录**：

```
site/
  scripts/og/
    build-og.mjs         # 生成器
    check-og.mjs         # 门禁：尺寸/体积/可解码/是否陈旧
    tokens.mjs           # 从 theme.css 抄过来的色值常量
    card.mjs             # 1200×630 的 satori 卡片组件
  public/og/
    case-studies--agriagent.png
    analysis--vegetable-pricing.png
    ...
  src/data/og-manifest.json   # { url: { srcHash, generatedAt } }
```

**`package.json` 脚本**（注意 `build` 里要挂门禁）：

```jsonc
{
  "scripts": {
    "og:build": "node scripts/og/build-og.mjs",
    "og:check": "node scripts/og/check-og.mjs",
    "build": "node scripts/copy-duckdb-assets.mjs && astro check && node scripts/og/check-og.mjs && astro build && node scripts/check-case-studies.mjs && node scripts/check-dissections.mjs && node scripts/check-links.mjs && node scripts/validate-rss.mjs && node scripts/check-ld.mjs && node scripts/check-story-budget.mjs && pagefind --site dist"
  }
}
```

**陈旧判定（关键设计）**：`build-og.mjs` 为每个页面算出 `hash(title + description + sectionLabel + dateText)`，写进 `og-manifest.json`。`check-og.mjs` 重算 hash 并与 manifest 比对 —— **不一致就 exit 1，提示「跑 npm run og:build」**。这就把「忘记重生成」变成了构建失败，而不是线上不一致。

**Astro 侧的数据源**：不要在生成器里重新解析 markdown。用一个 **Astro 静态端点**把内容集合导出来：

```ts
// site/src/pages/og-index.json.ts
import type { APIRoute } from "astro";
import { getCollection } from "astro:content";
import { entryUrl } from "@/utils/entryUrl";

export const GET: APIRoute = async () => {
  const cards = [];
  for (const e of await getCollection("caseStudies")) {
    cards.push({
      url: entryUrl("case-studies", e.id),
      section: "case",
      title: e.data.title,
      description: e.data.description,
      date: e.data.pubDatetime.toISOString().slice(0, 10),
    });
  }
  // analysis / dissections / toolkitReports 同理……
  return new Response(JSON.stringify(cards), {
    headers: { "Content-Type": "application/json" },
  });
};
```

→ `astro build` 产出 `dist/og-index.json` → `build-og.mjs` 读它生成 PNG。

> ⚠️ 这个端点的写法我**没有在本仓库实测**（我没改你的代码）。端点用 `getStaticPaths` + `GET` 产出静态文件是 Astro 的标准能力，`astro-og-canvas` 的 README 就是这么用的（✅ 已读到该 README）。落地时请先用 `astro build` 确认 `dist/og-index.json` 真的产出。

**meta 注入**（改 `Layout.astro`，注意 `og:image:*` 的补全）：

```astro

<meta property="og:image:type" content="image/png" />
```

#### 方案 B：Astro 端路由内联生成（`src/pages/og/[slug].png.ts`）

**这是 `astro-og-canvas` 用的模式**，图像**参与 Astro 构建图**，字体/图片可以通过 Vite 正常 import，不需要额外的路径逻辑。

```ts
// site/src/pages/og/[...path].png.ts
import type { APIRoute, GetStaticPaths } from "astro";
import { getCollection } from "astro:content";
import satori from "satori";
import { Resvg } from "@resvg/resvg-js";
import { readFileSync } from "node:fs";
import { fileURLToPath } from "node:url";
// 字体必须能被构建期读到；用 ?url 拿到产物 URL 再读文件
import fontUrl from "@/assets/fonts/NotoSansSC-subset.ttf?url";

const font = readFileSync(fileURLToPath(new URL(fontUrl, import.meta.url)));

export const getStaticPaths = (async () => {
  const entries = await getCollection("caseStudies");
  return entries.map(e => ({
    params: { path: "case-studies--" + e.id },
    props: {
      title: e.data.title,
      description: e.data.description,
      section: "case",
      date: e.data.pubDatetime.toISOString().slice(0, 10),
    },
  }));
}) satisfies GetStaticPaths;

export const GET: APIRoute = async ({ props }) => {
  const svg = await satori(makeCard(props), {
    width: 1200, height: 630,
    fonts: [{ name: "Noto Sans SC", data: font, weight: 400, style: "normal" }],
  });
  const png = new Resvg(svg, {
    fitTo: { mode: "width", value: 1200 },
    font: { loadSystemFonts: false },
  }).render().asPng();
  return new Response(png, {
    headers: {
      "Content-Type": "image/png",
      "Cache-Control": "public, max-age=31536000, immutable",
    },
  });
};
```

**优点**：一次 `astro build` 全自动，图与内容天然同步，永远不会陈旧。
**代价**：
1. **字体必须进仓库**（构建时要用）→ 至少 ~0.4 MB/字重；
2. **Vercel 构建时间增加**（实测 30 张约 0.4 s，可忽略）；
3. 生成失败的报错会混在 Astro 构建日志里；
4. **30 张图的 PNG 每次构建都重算** —— 除非用缓存，否则 Vercel 的构建缓存要额外处理。

> ⚠️ 这段代码我**没有实测**（未在本仓库跑 build）。`satori` / `Resvg` 部分是我实测过的；`?url` 字体导入 + `GET` 返回 `Response(Buffer)` 的写法请先小范围验证。

#### B3.4 决策表

### B5 能不能直接复用现有的内联 SVG 封面当 OG 图？

#### 结论：**不能直接复用，但可以复用它的视觉语言。**

三个层次的回答：

**① 格式层面：SVG 不能当 og:image。**
- ✅ ogp.me 的原文只说 `og:image` 是「An image URL which should represent your object within the graph」，`og:image:type` 是「A MIME type for this image」——**ogp.me 本身没有规定格式白名单**（我通读了抓到的全文）。
- ⚠️ **X/Twitter 与 Facebook 的官方文档我从本机抓不通**（`developer.x.com`、`docs.x.com`、`developer.twitter.com`、`developers.facebook.com` 全部 `fetch failed`，重试多次；详见来源清单），所以「SVG 不被支持」这个结论**我无法用一手官方来源证实**。
- 我能给的**最硬的实证**是一份第三方跨平台实测（Darek Kay，2024-11-17 发布 / 2025-11-13 更新，✅ 页面我读到了全文）：
  > "**All tested providers support JPEG and PNG.** All tested providers except Xing support WebP. No tested provider except Facebook supports AVIF."
  测试平台：WhatsApp、Telegram、Signal、Discord、Slack、Teams、Facebook、LinkedIn、Xing、Bluesky、Threads、Phanpy(Mastodon)。**SVG 根本不在被测集合里。**

**工程结论**：按「跨平台最保守」选，**输出 PNG（或 JPEG）**。你现有的 `og-default.png` 就是 PNG，路线正确。
（PNG vs JPEG：🧪 实测同一张卡片 satori 输出 PNG 27 KB、JPEG q85 27.6 KB、调色板 PNG 12.6 KB —— **PNG 完全够小**，还能保留纯色块边缘锐利度，没必要换 JPEG。）

**② 结构层面：`Cover.astro` 的 SVG 不能喂给 satori。**

| `Cover.astro` 的写法 | 能不能直接搬 |
|---|---|
| `viewBox="0 0 536 301"` | ❌ 尺寸不对（OG 要 1200×630） |
| `fill="var(--surface-2)"` / `sectionVar` / `var(--foreground)` / `var(--border)` / `var(--muted-foreground)` | ❌ **satori 不解析 CSS 变量**，必须换成字面量 |
| `font-family="Georgia, 'Times New Roman', serif"` | ⚠️ satori 不会回退到系统字体，得单独注册衬线字体 |
| `<pattern>` + `<circle>` 点阵 | ⚠️ satori 对任意 SVG 子元素支持有限 —— 未核实，建议改用 CSS 渐变或直接放弃点阵 |
| `fitSize()` 按 CJK=1em / 拉丁=0.56em 估计字号 | ✅ **这个思路可以照搬**，很有用 |
| `clip()` 可视宽度截断 | ✅ 可以照搬 |

**③ 可复用的是什么**：版面语言（左侧板块色条、kicker + 下划线、右上日期、大标题、副标题、底部数字 facts、右下域名）和 `fitSize` / `clip` 这两个中文排版工具函数。

**推荐做法**：在 `site/scripts/og/card.mjs` 里**重写一份 1200×630 的 satori 卡片**，把 `Cover.astro` 的布局规则按 1200/536 ≈ 2.24 的比例放大，色值从 B1 陷阱 2 的 `tokens.mjs` 取。这样两处视觉同源但不共享代码 —— 鉴于目标尺寸、渲染引擎都不同，强行共享反而更脆。

> ⚠️ 顺带指出：`Cover.astro` 的 SVG 有 `aria-hidden="true"`，这是**内容性插图被标记为装饰**，本身不构成无障碍问题（旁边的 `<h1>` 提供了文字）。但 OG 图的 `og:image:alt` 必须补上（见 A1 结尾）—— 那是给屏幕阅读器/爬虫的**另一条**无障碍路径。

### D1 构建门禁：校验生成的图（尺寸 / 体积 / 非空 / 可解码）

#### 方案 1（**推荐**）：零依赖 PNG 校验器

OG 图永远是 PNG，那么「可解码 + 尺寸正确」只需要读 **PNG 的 IHDR chunk**——**8 字节签名 + 13 字节 IHDR**，不需要任何第三方库。🧪 我实现了并对三个真实文件跑过：

```js
// site/scripts/og/png.mjs
import { readFileSync } from "node:fs";

const PNG_SIG = "89504e470d0a1a0a";

/** 纯 Node 读 PNG 尺寸；失败即抛错（等于「能解码」的最小证明） */
export function readPngSize(buf) {
  if (buf.length < 24) throw new Error("PNG too short");
  if (buf.subarray(0, 8).toString("hex") !== PNG_SIG) throw new Error("not a PNG (bad signature)");
  if (buf.subarray(12, 16).toString("ascii") !== "IHDR") throw new Error("first chunk is not IHDR");
  return {
    width: buf.readUInt32BE(16),
    height: buf.readUInt32BE(20),
    bitDepth: buf[24],
    colorType: buf[25],
    interlace: buf[28],
  };
}

export function assertOgPng(file, { w = 1200, h = 630, maxBytes = 200 * 1024 } = {}) {
  const buf = readFileSync(file);
  const errs = [];
  if (buf.length === 0) errs.push("文件为空");
  if (buf.length > maxBytes) errs.push("体积 " + buf.length + " B > " + maxBytes + " B");
  let size;
  try { size = readPngSize(buf); } catch (e) { errs.push("解码失败: " + e.message); }
  if (size && (size.width !== w || size.height !== h)) {
    errs.push("尺寸 " + size.width + "x" + size.height + " != " + w + "x" + h);
  }
  return { ok: errs.length === 0, errs, size, bytes: buf.length };
}
```

```
og-default.png               => {width:1200,height:630,bitDepth:8,colorType:2,interlace:0} bytes:37318
negative test (ttf): not a PNG (bad signature)     ← 反向用例也生效
```

```js
import { join } from "node:path";

const DIST = "dist";
const OG_RE = /<meta\\s+property="og:image"\\s+content="([^"]+)"/g;

function* walk(d) {
  for (const n of readdirSync(d)) {
    const p = join(d, n);
    if (statSync(p).isDirectory()) yield* walk(p);
    else if (n === "index.html") yield p;
  }
}

const site = "https://yuhailinlxy.com";
const seen = new Map();
const problems = [];

for (const file of walk(DIST)) {
  const html = readFileSync(file, "utf8");
  const urls = [...html.matchAll(OG_RE)].map(m => m[1]);
  if (urls.length === 0) { problems.push(file + ": 没有 og:image"); continue; }
  const url = urls[0];
  seen.set(url, [...(seen.get(url) ?? []), file]);

  // 必须是本域绝对 URL
  if (!url.startsWith(site + "/")) problems.push(file + ": og:image 不是本域绝对 URL -> " + url);
  // 映射回本地文件并检查存在
  const local = join(DIST, url.slice(site.length));
  if (!existsSync(local)) problems.push(file + ": og:image 指向的文件不存在 -> " + local);

  // og:image:alt 必须存在
  if (!/<meta\\s+property="og:image:alt"/.test(html)) problems.push(file + ": 缺 og:image:alt");
}

for (const [url, files] of seen) {
  if (files.length > 1) problems.push("og:image 复用 " + files.length + " 次: " + url + "  <- " + files.join(", "));
}

if (problems.length) { problems.forEach(p => console.error("FAIL " + p)); process.exit(1); }
console.log("OG meta 校验通过：" + seen.size + " 个唯一 og:image");
```

#### 对 Lighthouse 的影响

**逐页 OG 图对 Lighthouse 分数的影响是 0**，理由：
1. OG 图**不会被页面加载**——它只出现在 `<meta>` 里，浏览器不下载它（没有 `preload`、没有 `<img>`）；
2. 生成发生在构建期，产物是静态 PNG，无运行时 JS/CSS 增量；
3. 唯一可能的间接影响是**部署体积**（+0.7 MB 左右），而 Vercel 静态托管与 Lighthouse 评分无关。

**唯一需要的注意点是别做蠢事**：不要给 `og:image` 加 `<link rel="preload">`，不要把这些 PNG 塞进页面里当装饰图。只要守住这两条，13 个页面的四类 100 分不受影响。
