## 摘要（10 条可直接执行的结论）

**1. 右栏必须显式给一个非 `auto` 的 inset（`top`），否则 sticky 等同 relative。**
【官方文档】MDN《position》sticky 值原文：「At least one inset property (top, inset-block-start, right, inset-inline-end, etc.) needs to be set to a non-auto value for the axis on which the element needs to be made sticky. If both inset properties for an axis are set to auto, on that axis the sticky value will behave as relative.」 https://developer.mozilla.org/en-US/docs/Web/CSS/position#sticky_positioning
同义规范原文：【官方规范】「If both inset properties in a given axis are auto, no offsets are added in that axis; the element stays where it was laid out in that axis.」 https://drafts.csswg.org/css-position-3/#sticky-pos

**2. 右栏所在的那一栏（grid/flex 子项）必须显式 `align-self: start`，否则默认拉伸会让栏高等于整行高，sticky 没有位移空间。**
【官方规范】CSS Box Alignment 3 §6.2.5 Grid Items（`align-self`）原文：「normal Behavior: Sizes as either stretch (typical non-replaced elements) or start (typical replaced elements); see Grid Item Sizing in [CSS-GRID-1]. The resulting box is then start-aligned.」 https://drafts.csswg.org/css-align-3/#self-alignment
【官方文档】MDN《align-self》stretch 值原文：「If the item's cross-size is auto, the used size is set to the length necessary to be as close to filling the container as possible, respecting the item's width and height limits.」 https://developer.mozilla.org/en-US/docs/Web/CSS/align-self

**3. 祖先链上任何 `overflow: hidden | scroll | auto` 都会抢走 sticky 的参照系，即使它根本不能滚。反之 `overflow: clip` 不是滚动容器，不破坏 sticky。**
【官方文档】MDN《position》sticky 值原文：「Note that a sticky element "sticks" to its nearest ancestor that has a "scrolling mechanism" (created when overflow is hidden, scroll, auto, or overlay), even if that ancestor isn't the nearest actually scrolling ancestor.」 https://developer.mozilla.org/en-US/docs/Web/CSS/position#sticky_positioning
【官方规范】CSS Overflow 3 §3.1 原文：「The scroll, auto, and hidden values are known as the scrollable values of overflow. They cause the box to be a scroll container and the affected axis to be a scrollable axis.」＋「The visible and clip values are known as the non-scrollable values. However, if the other axis specifies a scrollable value, a specified value of visible computes to auto, enabling scrolling in its axis. If neither axis computes to a scrollable value, the box is not a scroll container.」 https://drafts.csswg.org/css-overflow-3/#overflow-properties
【本项目实测】本项目正文列表用的正是 clip：`C:\dev\pm-forge\site\src\styles\typography.css:34-36` 的 `ul { @apply overflow-x-clip; }`，按上式它不会破坏祖先内的 sticky。

**4. 「粘性顶栏遮住锚点」的标准解法是滚动容器上的 `scroll-padding-top`；只有个别目标需要单独留白时才用该目标自己的 `scroll-margin-top`。且必须写在根元素上才对视口生效，写在 `body` 上不会传播。**
【官方规范】CSS Scroll Snap 1 §1 原文：「this module defines the scroll-padding property for use on all scroll containers, to adjust the scroll container's optimal viewing region for the purpose of paging and scroll-into-view operations. Similarly the scroll-margin property can be used on any box to adjust its visual area for the purpose of scroll-into-view operations.」 https://drafts.csswg.org/css-scroll-snap-1/#scroll-padding
同规范 §4.2 原文：「UAs must apply the scroll-padding values set on the root element to the document viewport. (Note that, unlike overflow, scroll-padding values are not propagated from HTML body.)」 https://drafts.csswg.org/css-scroll-snap-1/#scroll-padding
【官方文档】MDN《scroll-padding-top》原文：「This allows the author to exclude regions of the scrollport that are obscured by other content (such as fixed-positioned toolbars or sidebars) or to put more breathing room between a targeted element and the edges of the scrollport.」 https://developer.mozilla.org/en-US/docs/Web/CSS/scroll-padding-top

**5. 本项目当前没有粘性顶栏，所以「锚点被遮」这件事今天不成立；现有的 `:target { scroll-margin-block: 1rem }` 只是留白，不是遮挡修复。**
【本项目实测】全站 `src` 里只有一处 sticky：`C:\dev\pm-forge\site\src\components\BackToTopButton.astro:13` 的 `md:sticky md:inset-e-auto md:float-end md:me-1`；`Header.astro:42-44` 的 header 没有任何 sticky/fixed 类。
【本项目实测】`C:\dev\pm-forge\site\src\styles\global.css:65-67`：
```css
:target {
  scroll-margin-block: 1rem;
}
```
若将来真的加粘性顶栏，正确改法是根元素上的 `html { scroll-padding-top: <栏高> }`，不要写 `body`（依据见上一条）。

**6. 目录必须是 `<nav>`，且当页面里已有别的 nav 时，每个 nav 都要有唯一 `aria-label`；标签里不要带「导航 / navigation」这个词。**
【官方规范】WHATWG HTML 4.3.4 原文：「The nav element represents a section of a page that links to other pages or to parts within the page: a section with navigation links.」＋「Common examples of navigation sections are menus, tables of contents, and indexes.」 https://html.spec.whatwg.org/multipage/sections.html#the-nav-element
【官方文档】WAI-ARIA APG《Landmark Regions》原文：「If a specific landmark role is used more than once on a page, provide each instance of that landmark with a unique label.」＋「Do not use the landmark role as part of the label. For example, a navigation landmark with a label "Site Navigation" will be announced by a screen reader as "Site Navigation Navigation".」＋「If a landmark is only used once on the page it may not require a label.」 https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/
【官方规范】HTML-AAM 3.5.94：`nav` → `navigation role` https://w3c.github.io/html-aam/#el-nav
【本项目实测】页面里已经有不止一个 nav：`C:\dev\pm-forge\site\src\components\Header.astro:54-56`（`<nav id="nav-menu">`，无 aria-label）、`C:\dev\pm-forge\site\src\components\Breadcrumb.astro:60`（`<nav class="app-layout mt-8 mb-1" aria-label="breadcrumb">`）。加右栏 nav 后就有 3 个 nav，新 nav 必须带唯一标签。

**7. 当前项用 `aria-current`，且一组里只能标一个；规范对 `location` / `true` 的定义分别是「当前所在位置」和「集合中的当前项」，没有为「页面内目录 scrollspy」指定唯一取值（取舍见 §4.2）。**
【官方规范】WAI-ARIA 1.2 §6.6 aria-current 原文：「The aria-current attribute is used when an element within a set of related elements is visually styled to indicate it is the current item in the set.」＋「Authors SHOULD only mark one element in a set of elements as current with aria-current.」＋取值表：「location — Represents the current location within an environment or context.」「true — Represents the current item within a set.」＋「Any value not included in the list of allowed values SHOULD be treated by assistive technologies as if the value true had been provided.」 https://www.w3.org/TR/wai-aria-1.2/#aria-current

**8. WCAG 2.2 里真正会被这条右栏触碰的只有 2.4.11 Focus Not Obscured (Minimum)，而它的触发条件是「sticky 内容与获得焦点的组件重叠」；只要两列栅格不重叠就不触碰。1.4.10 Reflow 用 min-width 媒体查询天然满足。**
【官方规范】WCAG 2.2 SC 2.4.11（AA，2.2 新增）原文：「When a user interface component receives keyboard focus, the component is not entirely hidden due to author-created content.」 https://www.w3.org/TR/WCAG22/#focus-not-obscured-minimum
【官方文档】Understanding 2.4.11 原文：「Typical types of content that can overlap focused items are sticky footers, sticky headers, and non-modal dialogs.」 https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html
【官方规范】WCAG 2.2 SC 1.4.10 Reflow（AA）原文：「Content can be presented without loss of information or functionality, and without requiring scrolling in two dimensions for: Vertical scrolling content at a width equivalent to 320 CSS pixels; …」＋Note 1：「320 CSS pixels is equivalent to a starting viewport width of 1280 CSS pixels wide at 400% zoom.」 https://www.w3.org/TR/WCAG22/#reflow
1.3.1 / 2.4.1 / 2.4.5 的逐条判定见 §4.3。

**9. `prefers-reduced-motion` 的规范措辞是「移除或替换」（removes or replaces），媒体特性总述才是「把非必要动效降到最低」（minimize）；不要理解成「移除全部动画」。目录高亮不要做动画，或把动效包在 no-preference 里。**
【官方规范】Media Queries 5 §12.1 原文：「The prefers-reduced-motion media feature is used to detect if the user has requested the system minimize the amount of non-essential motion it uses.」＋`reduce` 值原文：「Indicates that user has notified the system that they prefer an interface that removes or replaces the types of motion-based animation that either trigger discomfort for those with vestibular motion sensitivity, or distraction for those with attention deficits.」 https://drafts.csswg.org/mediaqueries-5/#prefers-reduced-motion
【本项目实测】本项目已有同款闸门：`C:\dev\pm-forge\site\src\styles\global.css:86-89` 把 `scroll-behavior: smooth` 放在 `@media (prefers-reduced-motion: no-preference)` 内，右栏要照抄这个口径。

**10. 两个必须在写代码前就定下来的坑：(a) IntersectionObserver 在 Astro ClientRouter 下不会自动销毁，必须在 `astro:before-swap` 里 `disconnect()`；(b) IO 本身无法告诉你「谁在视口顶部」，需要自己补几何判定。**
【官方文档】Astro《View transitions》原文：「Bundled module scripts, which are the default scripts in Astro, are only ever executed once.」＋「inline scripts have the potential to be re-executed during a user's visit to a site」＋生命周期：「The astro:after-swap event is triggered on the document.」、「The astro:page-load event fires.」 https://docs.astro.build/en/guides/view-transitions/
【官方文档】MDN《Intersection Observer API》原文：「One thing the Intersection Observer API can't do: trigger logic based on the exact number of pixels that overlap, or specifically on which ones they are.」 https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API
【本项目实测】本项目已有正确先例：`C:\dev\pm-forge\site\src\pages\data-stories\userbehavior.astro:311-313`（`astro:page-load` → init，`astro:before-swap` → teardown）与 `:203-208` 的 `io?.disconnect()`。

## 逐条证据

### 1. `position: sticky`

#### 1.1 生效条件：至少要有一个非 auto 的 inset

【官方文档】MDN《position》（2026-10-12 抓取，https://developer.mozilla.org/en-US/docs/Web/CSS/position ）：

> sticky
> This value always creates a new stacking context. Note that a sticky element "sticks" to its nearest ancestor that has a "scrolling mechanism" (created when overflow is hidden, scroll, auto, or overlay), even if that ancestor isn't the nearest actually scrolling ancestor.
> At least one inset property (top, inset-block-start, right, inset-inline-end, etc.) needs to be set to a non-auto value for the axis on which the element needs to be made sticky. If both inset properties for an axis are set to auto, on that axis the sticky value will behave as relative.

同页 Examples → "List with sticky headings" 原文：

> You must specify a threshold with at least one of top, right, bottom, or left for sticky positioning to behave as expected. Otherwise, it will be indistinguishable from relative positioning.

同页 Values 段落中 Definition 原文（用于 CLS 判断）：

> A stickily positioned element is an element whose computed position value is sticky. It's treated as relatively positioned until its containing block crosses a specified threshold (such as setting top to value other than auto) within its flow root (or the container it scrolls within), at which point it is treated as "stuck" until meeting the opposite edge of its containing block.

→ 可直接推出：sticky 在「粘住」之前占位与 relative 相同，不产生布局位移，因此不引入 CLS。这条由上面 MDN 原文直接得出，规范侧同义表述见 CSS Position 3（下一小节）。

#### 1.2 规范原文：sticky 的参照系与受限期

【官方规范】CSS Positioned Layout 3 §3.4 Sticky positioning（https://drafts.csswg.org/css-position-3/#sticky-pos ）原文：

> Sticky positioning is similar to relative positioning except the offsets are automatically calculated in reference to the nearest scrollport.
> For a sticky positioned box, the inset properties represent insets from the respective edges of the scrollport of the nearest scroll container with a matching scrollable axis, defining the sticky view rectangle used to constrain the box's position.
> If both inset properties in a given axis are auto, no offsets are added in that axis; the element stays where it was laid out in that axis. Otherwise, auto insets represent zero insets.
> For each side of the box, if the corresponding inset property is not auto, and the corresponding border edge of the box would be outside the corresponding edge of the sticky view rectangle, then the box must be visually shifted (as for relative positioning) to be inward of that sticky view rectangle edge, insofar as it can while its position box remains contained within its containing block.
> Note: A sticky positioned element with a non-auto top value and an auto bottom value will only ever be pushed down by sticky positioning; it will never be offset upwards.
> Note: Multiple sticky positioned boxes in the same container are offset independently, and therefore might overlap.

→ 三件事直接由原文得出：
1. **参照系是「最近的滚动容器（scrollport）」**。谁会成为滚动容器由 CSS Overflow 3 §3.1 定义（见 §7.1）。
2. **位移上限由包含块决定**——「insofar as it can while its position box remains contained within its containing block」。右栏能粘多久，等于它的父容器还有多高。
3. **同一容器里的多个 sticky 会各自偏移、可能互相重叠**（规范原文用 Note 明说）。本项目已有另一个 sticky（`BackToTopButton.astro:13`），如果右栏和它落进同一个包含块，就要自己保证不重叠。

#### 1.3 sticky 元素比滚动容器还高时会怎样

【官方规范】CSS Positioned Layout 3 §3.4 原文：

> If this results in a sticky view rectangle size in any axis less than the size of the border box of the sticky box in that axis, then the effective end-edge inset in the affected axis is reduced (possibly becoming negative) to bring the sticky view rectangle's size up to the size of the border box in that axis (where end is interpreted relative to the writing mode of the containing block).
> For example, if the nearest scrollport is 300px tall, the sticky box's border box is 200px tall, and it has top: 20px, then the top-edge inset of the nearest scrollport is 20px, and the bottom-edge inset is 0px, yielding a sticky view rectangle that is 280px tall. But if the nearest scrollport were only 100px tall, then the effective bottom-edge inset becomes -120px, resulting in a sticky view rectangle that's 200px tall, enough to fully contain the margin box of the sticky box.

解读（由原文直接得出，不是额外推测的机制）：
- 元素高于滚动容器时，浏览器不会让矩形小于元素，而是把「end 侧 inset」压成负数，让矩形至少能装下元素本身。此时元素仍按 `top` 约束移动，但因为它已经装不下第二屏，视觉上表现为「粘住后底部持续被裁」。
- 「元素高于**父容器（包含块）**」是另一回事：§1.2 的 `insofar as it can while its position box remains contained within its containing block` 意味着位移被限制在包含块内，父容器一旦走完，右栏就跟着滚走。这正是「父容器高度」这个坑的规范依据。

#### 1.4 sticky 元素被 scroll-to-target 时的位置

【官方规范】CSS Positioned Layout 3 §3.4.1 Scroll Position of Sticky-Positioned Boxes 原文：

> For the purposes of any operation targeting the scroll position of a sticky positioned element (or one of its descendants), the sticky positioned element must be considered to be at its offsetted position.
> For example, if a user clicks a link targeting a sticky-positioned element, if the element's nearest scrollport is currently scrolled such that the sticky positioned element is offset from its initial position, the scroll container will be scrolled back only the minimum necessary to bring it into its desired position in the scrollport (rather than scrolling all the way back to target its original, non-offsetted position).

→ 与右栏的关系：右栏的目录链接指向的是正文标题（非 sticky），不受这条影响。但如果将来给「右栏自身」加 id 并被链接，就要按这条预期行为验证。

### 2. `scroll-margin-top` / `scroll-padding-top`

#### 2.1 MDN 原文

【官方文档】MDN《scroll-padding-top》（https://developer.mozilla.org/en-US/docs/Web/CSS/scroll-padding-top ）：

> The scroll-padding-top property defines offsets for the top of the optimal viewing region of the scrollport: the region used as the target region for placing things in view of the user. This allows the author to exclude regions of the scrollport that are obscured by other content (such as fixed-positioned toolbars or sidebars) or to put more breathing room between a targeted element and the edges of the scrollport.

【官方文档】MDN《scroll-margin-top》（https://developer.mozilla.org/en-US/docs/Web/CSS/scroll-margin-top ）：

> The scroll-margin-top property defines the top margin of the scroll snap area that is used for snapping this box to the snapport. The scroll snap area is determined by taking the transformed border box, finding its rectangular bounding box (axis-aligned in the scroll container's coordinate space), then adding the specified outsets.

注意 MDN 自己的措辞差异：**scroll-padding 的官方描述直接点名「被固定工具栏/侧栏遮挡的区域」，scroll-margin 的官方描述则只用「scroll snap area / snapport」来定义**。所以「粘性顶栏遮锚点」在文档层面天然对应 scroll-padding；scroll-margin 的锚点用法属于「顺带可用」（规范 §1 明说它也用于 scroll-into-view，见 2.2）。

#### 2.2 规范怎么定义两者，以及谁负责 scroll-into-view

【官方规范】CSS Scroll Snap 1 §1 Introduction（https://drafts.csswg.org/css-scroll-snap-1/#scroll-padding ）原文：

> Also, to offer better control over paging and scroll positioning even when snapping is off, this module defines the scroll-padding property for use on all scroll containers, to adjust the scroll container's optimal viewing region for the purpose of paging and scroll-into-view operations.
> Similarly the scroll-margin property can be used on any box to adjust its visual area for the purpose of scroll-into-view operations.

【官方规范】同规范 §4.2 Scroll Snapport: the scroll-padding property 原文：

> This property specifies (for all scroll containers, not just scroll snap containers) offsets that define the optimal viewing region of a scrollport: the region used as the target region for placing things in view of the user. This allows the author to exclude regions of the scrollport that are obscured by other content (such as fixed-positioned toolbars or sidebars) or simply to put more breathing room between a targeted element and the edges of the scrollport.

同节 `Applies to: scroll containers`；`Initial: auto`。

【官方规范】同规范 §5.1 Scroll Snapping Area: the scroll-margin property 原文：

> Values represent outsets defining the scroll snap area that is used for snapping this box to the snapport. The scroll snap area is determined by taking the transformed border box, finding its rectangular bounding box (axis-aligned in the scroll container's coordinate space), then adding the specified outsets.

同节 `Applies to: all elements`；`Initial: 0`。

【官方规范】CSSOM View §scroll a target into view（https://drafts.csswg.org/cssom-view/#scroll-a-target-into-view ）里的示例原文（说明 `scrollIntoView()` 会同时尊重两者的原文证据）：

> // scrollIntoView correctly aligns target item respecting scroll-snap-align,
> // scroll-margin, and the scroll container's scroll-padding.

#### 2.3 根元素 vs body

【官方规范】CSS Scroll Snap 1 §4.2 原文：

> UAs must apply the scroll-padding values set on the root element to the document viewport. (Note that, unlike overflow, scroll-padding values are not propagated from HTML body.)

→ 结论（直接由原文）：要修「所有锚点都被顶栏遮」，写 `html { scroll-padding-top: … }`；写 `body { scroll-padding-top: … }` **不会**对文档视口生效。

#### 2.4 两者区别（全部来自上面原文）

| 维度 | `scroll-padding-top` | `scroll-margin-top` |
|---|---|---|
| 属于谁 | 滚动容器（`Applies to: scroll containers`）【官方规范】css-scroll-snap-1 §4.2 | 目标元素（`Applies to: all elements`）【官方规范】css-scroll-snap-1 §5.1 |
| 作用对象 | 滚动容器的 optimal viewing region（可视区内缩） | 元素自己的 scroll snap area（元素外扩） |
| 一次性覆盖全站锚点 | 是（根元素上一条搞定） | 否（要写给每个可能被链接的元素，如 `h2[id], h3[id]`） |
| 写在 body 上 | 不传播到视口【官方规范】同上 | 与位置无关，写在元素上即可 |
| 触发时机 | 每个 scroll-into-view / 分页滚动 | 每个 scroll-into-view |

→ 「有粘性顶栏时点击锚点被遮住」的标准解法 = **scroll-padding-top（滚动容器侧）**；只用 scroll-margin-top 也能解决，但那是逐元素方案，容易漏（本项目正文标题由 markdown 渲染，h2/h3 都有 id，将来新增 h4 就会漏）。

### 3. `IntersectionObserver`

#### 3.1 root / rootMargin / threshold 的定义原文

【官方文档】MDN《IntersectionObserver.root》（https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserver/root ）原文：

> The root read-only property of the IntersectionObserver interface identifies the Element or Document whose bounds are treated as the bounding box of the viewport for the element which is the observer's target.
> If the root is null, then the bounds of the actual document viewport are used.

【官方文档】MDN《IntersectionObserver.rootMargin》（https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserver/rootMargin ）原文：

> Each side of the rectangle represented by rootMargin is added to the corresponding side in the root element's bounding box before the intersection test is performed.
> This lets you, for example, adjust the bounds outward so that the target element is considered 100% visible even if a certain number of pixels worth of width or height is clipped away, or treat the target as partially hidden if an edge is too close to the edge of the root's bounding box.
> If rootMargin isn't specified when the object was instantiated, it defaults to the string "0px 0px 0px 0px"…

【官方文档】MDN《IntersectionObserver.thresholds》（https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserver/thresholds ）原文：

> Regardless of the order your original threshold array was in, this one is always sorted in numerically increasing order.
> If no threshold option was included when IntersectionObserver() was used to instantiate the observer, the value of thresholds is [0].
> Note: Although the options object you can specify in the IntersectionObserver() constructor has a field named threshold, this property is called thresholds. If you accidentally use thresholds as the name of the field in your options, the thresholds array will wind up being [0.0], which is likely not what you expect.

【官方规范】Intersection Observer（https://w3c.github.io/IntersectionObserver/ ）原文：

> rootMargin, of type DOMString, defaulting to "0px" … Similar to rootMargin … See rootMargin above for the example.
> threshold, of type (double or sequence<double>), defaulting to 0 — List of threshold(s) at which to trigger callback.
> thresholds, of type FrozenArray<double>, readonly — A list of thresholds, sorted in increasing numeric order, where each threshold is a ratio of intersection area to bounding box area … of the thresholds are crossed for that target.
> Note: rootMargin only applies to the intersection root itself.

「交集面积与 bounding box 面积之比」的 MDN 原文（https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API ）：

> The degree of intersection between the target element and its root is the intersection ratio. This is a representation of the percentage of the target element which is visible as a value between 0.0 and 1.0.

#### 3.2 回调语义：只在跨阈值时报告，且一次 callback 里可能混着多个目标

【官方文档】MDN《Intersection Observer API》原文（https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API ）：

> Rather than reporting every infinitesimal change in how much a target element is visible, the Intersection Observer API uses thresholds. … Then, the API only reports changes to visibility which cross these thresholds.
> When the callback is invoked, it receives a list of IntersectionObserverEntry objects, one for each observed target which has had the degree to which it intersects the root change such that the amount exposed crosses over one of the thresholds, in either direction.
> The list of entries received by the callback includes one IntersectionObserverEntry object for each threshold-crossing event — multiple entries can be received at a time, either from multiple targets or from a single target crossing multiple thresholds in a short amount of time. The entries are dispatched using a queue, so they should be ordered by the time they were generated, but you should preferably use IntersectionObserverEntry.time to correctly order them. … The entry only contains information about that particular instant — if you want information that requires tracking over time, such as the scroll direction and speed, you may need to compute that yourself by storing previously received entries.

【官方规范】Intersection Observer §3.2.10 Run the Update Intersection Observations Steps 原文：

> For each target in observer's internal [[ObservationTargets]] slot, processed in the same order that observe() was called on each target:

→ 这一条是「IO 不能直接回答『谁在顶部』」的规范侧根据：**报告顺序由 observe() 调用顺序决定，与元素在视口中的视觉先后无关**；一次 callback 可能同时收到多个 entry（同一瞬间多个 target 都在交叉）。

#### 3.3 MDN 明说的能力边界 —— 以及我没有找到的东西

【官方文档】MDN《Intersection Observer API》原文：

> One thing the Intersection Observer API can't do: trigger logic based on the exact number of pixels that overlap, or specifically on which ones they are. It only solves the common use case of "If they intersect by somewhere around N%, I need to do something."

这是我在 MDN 上找到的**唯一**一句直接的能力边界声明。关于「MDN 是否有专门章节说明『无法精确知道哪个元素在视口顶部』」——**没有找到**【未核实】，试过的 URL 与现象见 §8.1。

可用的替代依据（都是原文，不是我的推测）：
- entry 只描述「那一刻」的信息（§3.2 原文 `The entry only contains information about that particular instant`）；
- 一次 callback 可能收到多个 target 的 entry（§3.2 原文）；
- 遍历顺序 = observe() 顺序（§3.2 规范原文）。

→ 因此「当前高亮哪一节」这件事，IO 只提供「谁跨了阈值」的信号，最终判定必须由调用方补：要么记录上一状态做状态机，要么在候选集合里用 `entry.boundingClientRect.top <= 0 且 bottom > 0` 一类几何条件自己算。**这一步不是规范问题，是设计问题，必须在方案里显式写下判定规则。**

另有一条与本项目相关的 MDN 提示：不要在嵌套滚动容器场景用 rootMargin 硬凑「顶部偏移」，MDN 原文：

> You could create an intersection observer on each scroll container for which you want a scroll margin, and use the root margin property to achieve a similar effect. Using a scroll margin is more ergonomic, as in most cases you can have just one intersection observer for all nested targets.

（https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API 「The intersection root and scroll margin」一节）

### 4. 无障碍

#### 4.1 目录该不该用 `<nav>`，`aria-label` 怎么写

【官方规范】WHATWG HTML §4.3.4 The nav element（https://html.spec.whatwg.org/multipage/sections.html#the-nav-element ）原文：

> The nav element represents a section of a page that links to other pages or to parts within the page: a section with navigation links.
> Not all groups of links on a page need to be in a nav element — the element is primarily intended for sections that consist of major navigation blocks.
> User agents (such as screen readers) that are targeted at users who can benefit from navigation information being omitted in the initial rendering, or who can benefit from navigation information being immediately available, can use this element as a way to determine what content on the page to initially skip or provide on request (or both).

同页示例（正是「页面内目录」场景）原文：

> In the following example, there are two nav elements, one for primary navigation around the site, and one for secondary navigation around the page itself.

【官方文档】MDN《<nav>》（https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/nav ，2026-10-12 抓取）原文：

> The <nav> HTML element represents a section of a page whose purpose is to provide navigation links, either within the current document or to other documents. Common examples of navigation sections are menus, tables of contents, and indexes.

【官方规范】HTML-AAM §3.5.94（https://w3c.github.io/html-aam/#el-nav ）：`nav` 的 computed role 是 `navigation`。

【官方文档】WAI-ARIA APG《Landmark Regions》（https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/ ）原文：

> By classifying and labelling sections of a page, they enable structural information that is conveyed visually through layout to be represented programmatically.
> Screen readers exploit landmark roles to provide keyboard navigation to important sections of a page.
> Landmark regions can also be used as targets for "skip links" and by browser extensions to enhanced keyboard navigation.
> If a specific landmark role is used more than once on a page, provide each instance of that landmark with a unique label.
> If a landmark is only used once on the page it may not require a label.
> If an area begins with a heading element (e.g. h1-h6) it can be used as the label for the area using the aria-labelledby attribute.
> If an area requires a label and does not have a heading element, provide a label using the aria-label attribute.
> Do not use the landmark role as part of the label. For example, a navigation landmark with a label "Site Navigation" will be announced by a screen reader as "Site Navigation Navigation". The label should simply be "Site".

→ 结论：目录用 `<nav aria-label="…">`；本项目加右栏后页面上有 3 个 nav，必须给每个唯一标签；标签里不要出现「导航 / navigation」；因为目录通常不想在正文标题大纲里多一个 h2，按 APG 原文用 `aria-label`（无 heading 时的标准做法）完全合规。
→ 语言一致性：APG 未规定标签语言；但标签会被朗读，应与页面语言一致。现有 `aria-label="breadcrumb"`（`Breadcrumb.astro:60`）是英文，是否统一到中文属于产品决策，不在本规范问题内。

#### 4.2 `aria-current="location"` 还是 `aria-current="true"`——规范原文

【官方规范】WAI-ARIA 1.2 §6.6 Definitions of States and Properties → aria-current（https://www.w3.org/TR/wai-aria-1.2/#aria-current ）原文：

> aria-current state — Indicates the element that represents the current item within a container or set of related elements.
> The aria-current attribute is a token type. Any value not included in the list of allowed values SHOULD be treated by assistive technologies as if the value true had been provided. If the attribute is not present or its value is an empty string or undefined, the default value of false applies and the aria-current state MUST NOT be exposed by user agents or assistive technologies.
> The aria-current attribute is used when an element within a set of related elements is visually styled to indicate it is the current item in the set. For example:
> - A page token used to indicate a link within a set of pagination links, where the link is visually styled to represent the currently-displayed page.
> - A step token used to indicate a link within a step indicator for a step-based process, where the link is visually styled to represent the current step.
> - A location token used to indicate the image that is visually highlighted as the current component of a flow chart.
> - A date token used to indicate the current date within a calendar.
> - A time token used to indicate the current time within a timetable.
> Authors SHOULD only mark one element in a set of elements as current with aria-current.
> Authors SHOULD NOT use the aria-current attribute as a substitute for aria-selected in widgets where aria-selected has the same meaning.

取值表原文（同节 `Values:`，逐条）：

> page — Represents the current page within a set of pages.
> step — Represents the current step within a process.
> location — Represents the current location within an environment or context.
> date — Represents the current date within a collection of dates.
> time — Represents the current time within a set of times.
> true — Represents the current item within a set.
> false (default) — Does not represent the current item within a set.

【官方文档】MDN《aria-current》（https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-current ）原文：

> location — Represents the current location within an environment or context such as the image that is visually highlighted as the current component of a flow chart.
> true — Represents the current item within a set.
> Only mark one element in a set of elements as current with aria-current.

**取舍（我的推断，非规范原文）**：
- 目录高亮的是「当前阅读位置」，不是「当前页面」→ 不应使用 `page`（`page` 的规范场景是分页链接/面包屑里的当前页；本项目面包屑已经用了 `page`，见 `Breadcrumb.astro:76`）。
- `location` 的规范定义是「当前所在位置（environment or context）」，语义上最贴近「当前读到哪一节」；`true` 是「集合中的当前项」这个更泛的兜底。
- **规范与 MDN 都没有给出「页面内目录 scrollspy 该用哪个」的明文推荐**【未核实】，见 §8.2。因此这是一次设计取舍：若担心 AT 对 `location` 的朗读差异，选 `true` 一定是安全的（规范明说未知值按 `true` 处理）；若追求语义贴合，选 `location`。**两个值都合规，但一组里只能标一个元素。**

【官方规范】WCAG 2.2（https://www.w3.org/TR/WCAG22/ ）原文逐条：

**1.3.1 Info and Relationships（A）**（#info-and-relationships）

> Information, structure, and relationships conveyed through presentation can be programmatically determined or are available in text.

**2.4.1 Bypass Blocks（A）**（#bypass-blocks）

**2.4.5 Multiple Ways（AA）**（#multiple-ways）

**2.4.11 Focus Not Obscured (Minimum)（AA，2.2 新增）**（#focus-not-obscured-minimum）

> When a user interface component receives keyboard focus, the component is not entirely hidden due to author-created content.
> Note 1: Where content in a configurable interface can be repositioned by the user, then only the initial positions of user-movable content are considered for testing and conformance of this success criterion.

**2.4.12 Focus Not Obscured (Enhanced)（AAA）**（#focus-not-obscured-enhanced）

**1.4.10 Reflow（AA）**（#reflow）

> Content can be presented without loss of information or functionality, and without requiring scrolling in two dimensions for:
> - Vertical scrolling content at a width equivalent to 320 CSS pixels;
> - Horizontal scrolling content at a height equivalent to 256 CSS pixels.

> Note 1: 320 CSS pixels is equivalent to a starting viewport width of 1280 CSS pixels wide at 400% zoom.

【官方文档】Understanding 2.4.11 Focus Not Obscured (Minimum)（https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html ）原文：

> The intent of this success criterion is to ensure that the item receiving keyboard focus is always partially visible in the user's viewport.
> In recognition of the complex responsive designs common today, this AA criterion allows for the component receiving focus to be partially obscured by other author-created content.
> Typical types of content that can overlap focused items are sticky footers, sticky headers, and non-modal dialogs. As a user tabs through the page, these layers of content can obscure the item receiving focus…

### 5. `prefers-reduced-motion`

【官方规范】Media Queries Level 5 §12.1（https://drafts.csswg.org/mediaqueries-5/#prefers-reduced-motion ）原文：

> The prefers-reduced-motion media feature is used to detect if the user has requested the system minimize the amount of non-essential motion it uses.
> no-preference — Indicates that the user has made no preference known to the system. This keyword value evaluates as false in the boolean context.
> reduce — Indicates that user has notified the system that they prefer an interface that removes or replaces the types of motion-based animation that either trigger discomfort for those with vestibular motion sensitivity, or distraction for those with attention deficits.

【官方文档】MDN《prefers-reduced-motion》（https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion ）原文：

> The prefers-reduced-motion CSS media feature is used to detect if a user has enabled a setting on their device to minimize the amount of non-essential motion. The setting is used to convey to the browser on the device that the user prefers an interface that removes, reduces, or replaces motion-based animations.
> reduce — Indicates that a user has enabled the setting on their device for reduced motion. The reduce keyword value evaluates as true; therefore, @media (prefers-reduced-motion) is equivalent to @media (prefers-reduced-motion: reduce).
> Toning down the animation scaling … /* Tone down the animation to avoid vestibular motion triggers. */

→ 措辞结论（逐字对照）：
- **规范正文（reduce 值定义）用的是「removes or replaces」**：移除或替换「会触发前庭不适 / 分心的那类动效」，不是移除一切视觉变化。
- **媒体特性的总述（MDN 与规范同）用的是「minimize the amount of non-essential motion」**：把非必要动效降到最低。
- MDN 另加第三种说法 `removes, reduces, or replaces`（移除 / 减少 / 替换）。
- 因此「减少」和「移除」都对，取决于说哪一句：**总述是「减少（至最低）」，值定义是「移除或替换（那类动画）」。** 设计含义：目录高亮切换这类「状态变化」本身允许存在，但**不该用动画、位移、缩放来表达**；要做过渡就得放进 `no-preference` 闸门。
- MDN 自己的示例演示的正是「把缩放动画换成更温和的溶解动画」（`Toning down the animation scaling`），即**替换**也是官方示范接受的做法。

【本项目实测】本项目已有可复用的闸门写法：`C:\dev\pm-forge\site\src\styles\global.css:74-89`（`::view-transition-* { animation: none !important }` 与 `@media (prefers-reduced-motion: no-preference) { html { scroll-behavior: smooth } }`）。

### 6. `:target` / `::target-text` 与锚点高亮

【官方规范】Selectors Level 4 §8.3 The Target Pseudo-class: :target（https://drafts.csswg.org/selectors-4/#the-target-pseudo ）原文：

> The elements pointed to in this way are the target elements of the document.
> The :target pseudo-class matches the document's target elements.
> Note: This specification previously defined a :target-within pseudo-class … It was removed in favor of :has(:target).

【官方文档】MDN《:target》（https://developer.mozilla.org/en-US/docs/Web/CSS/:target ）原文：

> The :target CSS pseudo-class selects the target element of the document. When the document is loaded, the target element is derived using the document's URL fragment identifier.
> When an HTML document loads, the browser sets its target element. The element is identified using the URL fragment identifier. Without the URL fragment identifier, the document has no target element. The :target pseudo-class allows styling the document's target element. The element could be focused, highlighted, animated, etc.
> Baseline: Widely available — This feature is well established and works across many devices and browser versions. It's been available across browsers since July 2015.

【官方规范】CSS Pseudo-Elements Level 4（https://drafts.csswg.org/css-pseudo-4/#selectordef-target-text ）原文（**关键纠偏**）：

> ::target-text — The ::target-text pseudo-element represents text directly targeted by the document URL's fragment, if any.
> Note: When a URL fragment targets an element, the :target pseudo-element can be used to select it, but ::target-text does not match anything. It only matches text that is itself targeted by the [fragment].

【官方文档】MDN《::target-text》（https://developer.mozilla.org/en-US/docs/Web/CSS/::target-text ）原文：

> The ::target-text CSS pseudo-element represents the text that has been scrolled to if the browser supports text fragments. It allows authors to choose how to highlight that section of text.
> Baseline 2024 — Newly available. Since December 2024, this feature works across the latest devices and browser versions.

→ 结论：
1. **`::target-text` 与 `#id` 锚点无关**（规范原文：「does not match anything」），它是给 URL 文本片段（text fragment）用的。不要指望它给目录跳转做高亮。
2. `:target` 是唯一「URL fragment → 元素」的标准选择器；它只在**当前目标元素**上匹配（同一时刻最多一个），所以适合做「刚跳过去那一节」的高亮，不适合做「滚动位置高亮」（滚动位置与 fragment 可以不一致）。
3. 本项目现有的 `:target { scroll-margin-block: 1rem }`（`global.css:65-67`）语法与语义都成立：给「被跳转到的元素」留 1rem 呼吸空间。注意三点：
   - `scroll-margin-block` 是逻辑属性，与本项目 `inset-*` 逻辑属性惯例一致；
   - 因为挂在 `:target` 上，只对被链接到的那个元素生效：目录点击会生效，但浏览器「恢复滚动位置」「查找框跳转」不会触发它；
   - 本项目已经**没有**粘性顶栏（摘要第 5 条），所以现在不需要靠它防遮挡；它现在的价值纯粹是视觉呼吸。

### 7. 已知坑清单（「看起来能用、实际会坏」）

按「坑 → 依据（原文） → 本项目相关性」列。**凡是我没找到规范/官方文档依据的，一律标【未核实】。**

**7.1 祖先 `overflow` 变成 sticky 参照系**
依据：【官方文档】MDN position「a sticky element "sticks" to its nearest ancestor that has a "scrolling mechanism" (created when overflow is hidden, scroll, auto, or overlay), even if that ancestor isn't the nearest actually scrolling ancestor.」；【官方规范】CSS Overflow 3「The scroll, auto, and hidden values are known as the scrollable values of overflow. They cause the box to be a scroll container…」
本项目相关性：**高**。页面结构里 `main.app-layout` 是普通 block，没有 overflow；正文 `ul` 用了 `overflow-x-clip`（`typography.css:34-36`）——按规范「clip 是非滚动值」，它**不会**破坏 sticky（但会裁切，右栏千万不要放进这样的容器里）。

**7.2 `overflow-x: hidden` 写在 `html` / `body` 上会怎样（最容易误判的坑）**
【官方规范】CSS Overflow 3 §3.1.4 Overflow Viewport Propagation 原文：

> UAs must apply the overflow values set on the root element to the viewport when the root element's display value is not none. However, when the root element is an [HTML] html element … whose overflow value is visible (in both axes), and that element has as a child a body element whose display value is also not none, user agents must instead apply the overflow values of the first such child element to the viewport. The element from which the value is propagated must then have a used overflow value of visible.

→ 由原文可得：写在 `html` 或（`html` 两轴均为 visible 时的）`body` 上的 overflow 会**传播到视口**，且**传播来源元素自己的 used overflow 变成 visible**，因此它自己不再是滚动容器。
【未核实】我**没有**找到官方文档明写「html/body 上 overflow-x:hidden 不破坏 sticky」这句话；上面是由 §3.1.4 原文推导的规范推论，**不是官方原话**。实现阶段若真要依赖它，必须真机验证。

**7.3 父容器高度 / grid 默认拉伸 → sticky 没有位移空间**
依据：【官方规范】CSS Position 3 §3.4「insofar as it can while its position box remains contained within its containing block」；【官方规范】CSS Align 3 §6.2.5「normal Behavior: Sizes as either stretch (typical non-replaced elements) or start (typical replaced elements)… The resulting box is then start-aligned.」
本项目相关性：**高**。右栏若做成两列 grid 的子项且不写 `align-self: start`，默认 stretch 会把右栏高度撑满整行 = 包含块高度，sticky 全程无位移。

**7.4 没写 inset**
依据：MDN position 原文（§1.1）。本项目相关性：高（漏写 `top-*` 时表现为「完全没生效」）。

**7.5 多个 sticky 元素互相重叠**
依据：【官方规范】CSS Position 3 §3.4 Note 原文「Multiple sticky positioned boxes in the same container are offset independently, and therefore might overlap.」
本项目相关性：**中高**。已有 `BackToTopButton.astro:13` 的 `md:sticky md:float-end`；若右栏与它落进同一个包含块，两者可能互相压住（且 2.4.11 关心焦点遮挡）。

**7.6 sticky 会创建层叠上下文**
依据：【官方文档】MDN position 原文「This value always creates a new stacking context.」
本项目相关性：中。右栏 `z-index` 行为可预测（自成一层）；但也意味着它不能靠祖先 z-index 被「提上去」，与既有 fixed 元素（`ArticleEnhancements.astro:9-17` 的 `fixed top-0 z-10` 进度条）的叠层关系需显式验证。

**7.7 sticky + `float`**
依据：【本项目实测】本项目现状就是 `md:sticky md:float-end`（`BackToTopButton.astro:13`）。
【未核实】我**没有**在规范里找到任何「float 会破坏 sticky」或「sticky 元素不能 float」的条文（查了 CSS Position 3 §3.4、MDN position 页；MDN 页的 sticky 示例里还同时出现 `float: left` 的兄弟元素）。因此「sticky + float 会坏」既无法证实也无法证伪，**标记未核实**，不要当结论用。

**7.8 sticky + `transform` 祖先**
【官方规范】CSS Transforms 1 §2 原文：

> For elements whose layout is governed by the CSS box model, any value other than none for the transform property also causes the element to establish a containing block for all descendants. Its padding box will be used to layout for all of its absolute-position descendants, fixed-position descendants, and descendant fixed background attachments.

【未核实】这句只点名 **absolute / fixed 后代**，**没有提 sticky**（已查 css-transforms-1 §2、css-position-3 §3.4、MDN position）。所以流行的「transform 祖先会破坏 sticky」在规范里找不到依据，**不要写成既成事实**；若实现阶段怀疑，唯一可靠办法是真机验证。「改成 `contain: paint` 也行」这个替代说法同样【未核实】——本次未核对其条文细节。

**7.9 IntersectionObserver 在 SPA 视图切换后没断开**
依据：
- 【官方文档】Astro《View transitions》原文：「Bundled module scripts, which are the default scripts in Astro, are only ever executed once. After initial execution they will be ignored, even if the script exists on the new page after a transition.」＋「inline scripts have the potential to be re-executed during a user's visit to a site if they exist on a page that is visited multiple times.」＋「To force inline scripts to re-execute after every transition, add the data-astro-rerun property.」 https://docs.astro.build/en/guides/view-transitions/
- 【官方文档】MDN《IntersectionObserver.disconnect()》原文：「The disconnect() method of the IntersectionObserver interface stops the observer watching all of its target elements for visibility changes.」 https://developer.mozilla.org/en-US/docs/Web/API/IntersectionObserver/disconnect
- 【本项目实测】站点已在跑 ClientRouter（上游 2026-10-09 调研已实测 head 内有 `astro-view-transitions-enabled`），且已有正确先例：`userbehavior.astro:192-195` 的注释（打包后的模块脚本只执行一次 → 必须挂 astro:page-load）、`userbehavior.astro:200-208` 的 `teardownStory() { io?.disconnect(); … }`、`userbehavior.astro:311-313` 的 page-load / before-swap 双挂。
**反向坑**：本项目另有一类是 `is:inline data-astro-rerun`（如 `ArticleEnhancements.astro:6`、`BackToTopButton.astro:38`），这类脚本**每次导航都会重跑**——右栏 observer 若建在这种脚本里且不做幂等，就会累积多个 observer（重复回调）。「重跑 → 累积」由上面 Astro 原文 + MDN `disconnect` 语义支撑；「内存泄漏的具体量级」未实测，标**未核实**。

**7.10 IO 不知道「谁在顶部」**
依据：MDN 原文（§3.3）＋ 规范遍历顺序（§3.2）。本项目相关性：**高**（右栏目录高亮的全部难点就在这里）。

**7.11 用 `rootMargin` 冒充「顶部偏移」**
依据：【官方文档】MDN 原文（§3.3 末）建议嵌套滚动容器用 scroll margin。
本项目相关性：中。根滚动容器（`root: null`）下用 `rootMargin` 表达「粘性顶栏高度」是常见做法，但本项目没有粘性顶栏（摘要第 5 条），这条需求暂不存在；一旦有了，规范侧的正解仍是 `scroll-padding-top`（§2）。

**7.12 `scroll-padding` 写在 body 上不生效**
依据：css-scroll-snap-1 §4.2 原文（§2.3）。本项目相关性：低（现状不需要），但属于「写了没反应」的典型。

**7.13 `::target-text` 用错场景**
依据：css-pseudo-4 原文「does not match anything」（§6）。相关性：中（很容易被误当成「锚点高亮」）。

**7.14 把 `prefers-reduced-motion` 当成「移除一切动画」**
依据：mediaqueries-5 §12.1 原文（§5）。相关性：中（右栏高亮/过渡的取舍依据）。

**7.15 CLS**
依据：【官方文档】MDN position 原文「It's treated as relatively positioned until its containing block crosses a specified threshold…」（§1.1）；【官方规范】CSS Position 3 §3.4「the box must be visually shifted (as for relative positioning)」——位移是**视觉偏移**，不参与布局。
本项目相关性：高（硬约束 CLS=0）。**注意**：这条只覆盖 sticky 本身；如果引入右栏改变了栅格列宽/正文宽度，那属于布局改动，需按项目自己的构建 + 实测流程验证（不在本文范围）。

### C. 需要先决策的三件事（都不在规范里，属于设计决策）

**C1. `aria-current` 取 `location` 还是 `true`。** 两者都合规（§4.2 原文）；`true` 是零风险兜底（规范明说未知值按 `true` 处理），`location` 语义更贴合「当前阅读位置」。**建议在方案里写下选择理由，并保证只标一个元素。**

**C2. 目录在 DOM 中的位置。** 放正文之后（A9）→ 复用现有 skip link、Tab 顺序自然；放正文之前 → 必须补第二个跳过点（否则 `#main-content` 之后第一站就是目录链接，削弱 2.4.1 的既有机制）。**推荐前者**，它与「左正文右目录」的视觉顺序也一致。

**C3. 高亮的判定规则（IO 只是信号源）。** 必须显式写死：观察哪些元素（h2，是否含 h3）、threshold 取什么、同一 callback 出现多个 entry 时怎么裁决、滚动方向变化怎么处理。依据：§3.2、§3.3 的原文（IO 只在跨阈值时报告、一次 callback 可能多目标、遍历顺序 = observe 顺序）。**这是本次改动唯一「规范不会替你决定」的部分。**
