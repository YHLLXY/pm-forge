### 1.2 prefetch 已经被 ClientRouter 默认打开了（prefetchAll: true + hover）

【官方文档】Astro《Prefetch》指南 "Using with View Transitions" 一节原文（`withastro/docs` 仓库 `src/content/docs/en/guides/prefetch.mdx`）：

> When you use Astro's `<ClientRouter />` on a page, prefetching will also be enabled by default. It sets a default configuration of `{ prefetchAll: true }` which enables prefetching for all links on the page.

【官方源码】在本项目安装的 `astro@7.3.5` 中可直接读到证据链：

1. `node_modules/astro/components/ClientRouter.astro` 第 150-153 行：

   ```js
   // @ts-expect-error injected by vite-plugin-transitions for treeshaking
   if (!__PREFETCH_DISABLED__) {
       init({ prefetchAll: true });
   }
   ```

2. `node_modules/astro/dist/transitions/vite-plugin-transitions.js` 第 54-55 行决定 `__PREFETCH_DISABLED__` 的取值：

   ```js
   const prefetchDisabled = settings.config.prefetch === false;
   return code.replace("__PREFETCH_DISABLED__", JSON.stringify(prefetchDisabled));
   ```

3. `node_modules/astro/dist/prefetch/index.js` 第 6-16 行决定默认值：

   ```js
   let prefetchAll = __PREFETCH_PREFETCH_ALL__;
   let defaultStrategy = __PREFETCH_DEFAULT_STRATEGY__;
   ...
   prefetchAll ??= defaultOpts?.prefetchAll ?? false;
   defaultStrategy ??= defaultOpts?.defaultStrategy ?? "hover";
   ```

4. `node_modules/astro/dist/types/public/config.d.ts` 第 1904、1924、1948 行的官方注释：

   > Enable prefetching for links on your site to provide faster page transitions. **(Enabled by default on pages using the `<ClientRouter />` router. Set `prefetch: false` to opt out of this behaviour.)**
   > `prefetchAll`: This value **defaults to `true` when using the `<ClientRouter />` router**. Otherwise, the default value is `false`.
   > `defaultStrategy` ... `@default 'hover'`

【本项目实测】`astro.config.ts` 里**没有** `prefetch` 配置（grep 全站 `src/` 零命中）。因此 `settings.config.prefetch` 为 `undefined` → `undefined === false` 为 false → `__PREFETCH_DISABLED__` 为 false → `init({ prefetchAll: true })` 会执行。

**结论（已核实，含线上运行时探针）**：线上站点当前的行为是 —— **站内每一个 `<a>` 在 hover / focus 约 80ms 后就会被 prefetch**（`initHoverStrategy` 里的 `setTimeout(..., 80)`），慢连接/省流模式下降级为 tap 策略。

【本项目实测｜真实浏览器探针】父 agent 在 https://www.yuhailinlxy.com/ 上加载首页 → 记录请求数 → hover 第一个站内链接 → 再记录，结果：

```json
{"hovered":"/interviewers/","requestsBeforeHover":3,
 "requestsAfterHover":["other https://www.yuhailinlxy.com/interviewers/"],
 "prefetchLinkTags":["https://www.yuhailinlxy.com/interviewers/"]}
```

即 hover 之后 DOM 里**新增了一个 `<link rel="prefetch">`** 并产生了对应的网络请求 —— 源码链（`vite-plugin-transitions.js:54` 判定 `prefetchDisabled=false` → `ClientRouter.astro:151-152` 执行 `init({ prefetchAll: true })`）在**生产环境**被闭合验证。这既不是 bug 也不是"没开"，而是一个**默认打开、但配置里看不见**的行为。是否保留见 §3.4。

### 1.3 【最高优先级】脚本只执行一次：搜索页与数据故事页会静默失效

这是本轮最重要的发现，比任何动效都重要。

【官方文档】Astro《View transitions》"Script re-execution" 一节原文：

> Bundled module scripts, which are the default scripts in Astro, **are only ever executed once**. After initial execution they will be ignored, even if the script exists on the new page after a transition.

【官方源码】`astro@7.3.5` 的实现（`node_modules/astro/dist/transitions/swap-functions.js` 第 29-45、223-230 行）：

```js
function detectScriptExecuted(script) {
  const key = script.src ? new URL(script.src, location.href).href : script.textContent;
  if (scriptsAlreadyRan.has(key)) return true;
  scriptsAlreadyRan.add(key);
  return false;
}
function deselectScripts(doc) {
  for (const s2 of doc.scripts) {
    if (
      !s2.hasAttribute("data-astro-rerun") &&
      detectScriptExecuted(s2)
    ) {
      s2.dataset.astroExec = "";
    }
  }
}
const swap = (doc) => {
  deselectScripts(doc);   // ← 新文档里"跑过的"脚本被打上 astro-exec，不重跑
  ...
};
```

`router.js` 第 82-98 行：带 `data-astro-exec=""` 的脚本在 `runScripts()` 里被 `continue` 跳过。去重键：**有 `src` 的用 URL，内联的用 `textContent`**。

【本项目实测】构建产物 `dist/` 里两个受害页面的脚本形态完全不同：

| 页面 | 脚本形态 | 去重键 |
|---|---|---|
| `dist/search/index.html` | 第 5 个 script 是**内联** `<script type="module">`（body 以 `var e=document.getElementById('search-input')…` 开头） | 内联文本 |
| `dist/data-stories/userbehavior/index.html` | `<script type="module" src="/_astro/userbehavior.astro_astro_type_script_index_0_lang.Cn3vcRA5.js">` | 资源 URL |

两个脚本的写法都是**模块顶层捕获 DOM 引用并只挂一次监听**：

- `site/src/pages/search.astro` 第 41-43 行在顶层取 `input / status / list`，第 118 行挂 `input` 监听。
- `site/src/pages/data-stories/userbehavior.astro` 第 203-235 行在顶层建 `IntersectionObserver` 与 `scrollama`，第 241 行给 `#q-run` 挂 click 监听（DuckDB-WASM 就是被这个监听触发的）。

**推演结果（已核实机制，未在浏览器里逐次点击验证，标注为推演）**：

1. 首次 SPA 导航到 /search/：脚本内容从未出现 → `detectScriptExecuted` 返回 false → 不标记 → `runScripts()` 执行它 → 搜索可用。
2. **第二次** SPA 导航回 /search/：内联文本已在 `scriptsAlreadyRan` 里 → 被标记 `data-astro-exec=""` → 跳过执行 → 新页面的 `#search-input` 上**没有任何监听**，而模块里旧引用指向已被换掉的 DOM → **输入框静默无反应**。
3. 数据故事页同理（`src` 去重）：二次进入后 `IntersectionObserver`、`scrollama`、`#q-run` 监听全部缺失 → 图表不渲染、查询按钮点了没反应。注意 **DuckDB-WASM 本身没有被"加载坏"**，坏掉的是触发它的那个监听。

【官方文档】Astro 给的修法就是官方那两段：`astro:page-load` 包裹 / `data-astro-rerun`。
【官方源码】`astro:page-load` 的触发时机（`dist/transitions/router.js`）：第 352 行过渡完成后触发；**第 414 行 `addEventListener("load", onPageLoad)` 保证首次加载也会触发**。所以"把逻辑写进 `astro:page-load` 监听"对首屏和后续导航都成立。

修法（可直接落地）见 §3.4.4。**建议把这项列为 v0.15 的第一优先级，先于任何美化。**

### 1.4 reduced-motion 与 view transition：产物里没有 CSS 闸门，但默认 cross-fade 由 UA 接管

【官方文档】Astro《View transitions》→ "Accessibility / `prefers-reduced-motion`" 一节承诺：

> Astro's `<ClientRouter />` component includes a CSS media query that **disables *all* view transition animations**, including fallback animation, whenever the `prefers-reduced-motion` setting is detected.

【官方源码】`node_modules/astro/components/viewtransitions.css` 第 56-66 行确实是这个实现：

```css
@media (prefers-reduced-motion) {
	::view-transition-group(*),
	::view-transition-old(*),
	::view-transition-new(*) {
		animation: none !important;
	}

	[data-astro-transition-scope] {
		animation: none !important;
	}
}
```

【本项目实测】这个文件**没有被产物引用**：

- 在 `node_modules/astro` 全包内 grep `viewtransitions.css` → 0 命中（没有任何文件 import 它）。
- 产物 CSS 只有 1 个：`dist/_astro/Footer.BxwaP4fT.css`（58,356 字节），其中 `view-transition` 字样 **0 次**；`prefers-reduced-motion` 只出现 1 次，且是 Tailwind 的 `@media (prefers-reduced-motion:reduce){.motion-reduce\:transition-none{transition-property:none}}`。
- 直接抓线上 CSS `https://www.yuhailinlxy.com/_astro/Footer.BxwaP4fT.css`（58,356 字节，与本地一致）：`view-transition` **0 次**，`astroFade` **0 次**。
- ClientRouter 的 JS 产物（16,357 字节）：`prefers-reduced-motion` 0 次，`matchMedia` 0 次，`reduce` 0 次 → **JS 侧也没有闸门**。

**结论（已核实）**：Astro 文档承诺的那条 CSS 闸门，在 pm-forge 的**实际线上产物里不存在**，JS 侧也没有替代实现。

⚠️ **但这不等于"reduce 用户一定会看到过渡动画"** —— 见下面的运行时实测：Astro 把"要不要播"交给了 UA。这一节因此要拆成两句结论：**"缺 CSS 闸门"是事实；"因此 reduce 用户看到了动画"是我的过度推断，已由实测更正。**

【官方规范】补这条的依据是 W3C CSSWG 的正式决议（2024-09-24，议题 `[css-view-transitions] Users need to be able to disable view transitions` #10267）原文：

> RESOLVED: in cases of prefers-reduced-motion the UA stylesheet will define a cross-fade animation by default, without size/position animation

含义很重要：**规范层面的方向不是"完全禁用"，而是"UA 样式表默认降级为纯交叉淡入淡出（不带尺寸/位移动画）"**。这与 Astro 文档"disables *all* view transition animations"的措辞不一致。

#### 运行时实测（父 agent 用 Playwright + 真实浏览器，2026-10-09，对象 https://www.yuhailinlxy.com/）

这一组数据**修正了本节原本"没有闸门 = reduce 用户仍会看到过渡"的措辞**，请以实测为准。

探针做法：先在页面里 monkey-patch `document.startViewTransition` 计数，再点击站内链接；唯一变量是浏览器上下文的 `reducedMotion`。

| 变量 | no-preference | reduce |
|---|---|---|
| `matchMedia('(prefers-reduced-motion: reduce)').matches` | false | **true** |
| 点击后 `document.startViewTransition` 调用次数 | **1** | **1** |
| 点击后 `location.pathname` | /case-studies/ | /case-studies/ |
| `performance.getEntriesByType('navigation').length` | **1** | **1** |

**按实测改写后的结论（原来的"没有闸门 ⇒ reduce 用户一定会看到过渡"过于武断，此处更正）**：

1. Astro **在 reduce 下照旧调用** `document.startViewTransition`。`ClientRouter.astro:57-61` 那句 DEV 警告说的"动画会被禁用"，指的是**浏览器按用户偏好跳过动画播放**，不是不调用 API。
2. 因此**默认的原生 cross-fade 由 UA 按用户偏好处理** —— 与本节上文引的 CSSWG 决议方向一致，**不代表本站缺少无障碍支持**。
3. **但一旦加上自定义 `transition:animate`，就不能假设 UA 还会帮我们关掉。** 自定义动画是作者定义的 CSS animation，UA 不会再替作者判断。
4. 所以 §3.4.2 那条 `@media (prefers-reduced-motion: reduce)` 里对 `::view-transition-*` 的关停仍然建议写（成本极低、与 Astro 文档承诺一致），且**每加一个自定义动效都要用同一探针在 `reducedMotion: 'reduce'` 下复测**。
5. 【未核实】我**没有**核实 Chrome / Safari 当前是否已经按这条决议实现（无法在本环境跑浏览器并切系统偏好）。可操作结论：**对自定义动效不要依赖 UA 兜底**；对默认 cross-fade 则已由实测证明由 UA 接管。

【本项目实测】同一次探测还确认：软导航正常工作（`performance.getEntriesByType('navigation').length` 保持 1，没有整页重载）；点击后新页面封面 SVG 从 17 张变 10 张 → DOM 被正确替换、无残留。

### 1.6 现在这个"默认 fade"到底是什么

【官方文档】Astro 文档说默认是 `fade`："`fade` (default): An opinionated crossfade animation. The old content fades out and the new content fades in."

【官方源码】但产物里**没有** `astroFade*` 关键帧（本地 dist 与线上 CSS 均 0 次），项目里也 **没有任何 `transition:animate`**（grep `src/` 0 命中）。因此实际跑的是**浏览器 UA 样式表的根交叉淡入淡出**，而不是 Astro 自己那套 `astroFade*`。

如果要显式控制，Astro 内置动画的**确切参数**在 `node_modules/astro/dist/transitions/index.js`（第 1、43-64 行）里可以抄：

```js
const EASE_IN_OUT_QUART = "cubic-bezier(0.76, 0, 0.24, 1)";
function fade({ duration } = {}) {
  const anim = {
    old: { name: "astroFadeOut", duration: duration ?? 180, easing: EASE_IN_OUT_QUART, fillMode: "both" },
    new: { name: "astroFadeIn",  duration: duration ?? 180, easing: EASE_IN_OUT_QUART, fillMode: "both" }
  };
  return { forwards: anim, backwards: anim };
}
```

即内置 `fade` = **180ms + `cubic-bezier(0.76, 0, 0.24, 1)`（ease-in-out-quart）+ `fill-mode: both`，只动 `opacity`**。内置 `slide` = 旧页 `astroFadeOut 90ms` + `astroSlideToLeft 220ms`，新页 `astroFadeIn 210ms（delay 30ms）` + `astroSlideFromRight 220ms`，同一缓动曲线。

- 【未核实】UA 默认交叉淡入淡出的时长我没核到确切数值（Chromium 的 `html.css` 在本环境抓取失败）。文档中**不给出**这个数字。

**评估**：默认的 opacity-only 根交叉淡入淡出对一个"数据新闻编辑部"站点是**合适**的——它没有位移，不触发前庭不适，且 180ms 级别不会让人觉得在等。**不建议**改成 `slide`（横向位移 + 阅读型站点 = 花哨且更容易引发不适）。

## 2. A. 权威规格与无障碍

### 2.1 prefers-reduced-motion 的规范原文

【官方规范】**CSS Media Queries Level 5**，§12.1 "Detecting the desire for less motion on the page: the `prefers-reduced-motion` feature"。

- 规范地址：https://www.w3.org/TR/mediaqueries-5/#prefers-reduced-motion
- 我实际读到正文的地址（TR 页面在本环境抓取被截断，改用 CSSWG 编辑草案）：https://drafts.csswg.org/mediaqueries-5/#prefers-reduced-motion
- 【官方规范】MDN 对取值语义的原文（https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion）：

> The `prefers-reduced-motion` CSS media feature is used to detect if a user has enabled a setting on their device to minimize the amount of non-essential motion. The setting is used to convey to the browser on the device that the user prefers an interface that **removes, reduces, or replaces** motion-based animations.
> Such animations can trigger discomfort for those with **vestibular motion disorders**. Animations such as **scaling or panning large objects** can be vestibular motion triggers.

取值语义（MDN 同页原文）：

> `no-preference` — Indicates that a user has made no preference known on the device. This keyword value evaluates as **false**.
> `reduce` — Indicates that a user has enabled the setting ... The `reduce` keyword value evaluates as **true**; therefore, `@media (prefers-reduced-motion)` is equivalent to `@media (prefers-reduced-motion: reduce)`.

- 【官方规范】MDN 同页标注 **Baseline: Widely available**，"available across browsers since January 2020"。
- 【官方源码】本项目离线核对（`lighthouse@13.5.0` 自带的 `web-features@3.40.0` `data.json`）：
  `prefers-reduced-motion`: `baseline=high`，`baseline_low_date=2020-01-15`，`baseline_high_date=2022-07-15`，支持 Chrome 74 / Edge 79 / Firefox 63 / Safari 10.1。

**规范原文关键句（用于写代码注释/评审）**：MDN 明确点出 **"scaling or panning large objects"** 是前庭触发源 —— 这直接决定了 §3.1 里"封面内部 scale"要**小幅度**、§3.3 里"上移"要**小位移**，而**不要**做整页/大幅缩放位移。

### 2.2 WCAG 对动效的具体要求（条款号 + 触发方式 + 闪烁阈值）

三条相关条款，全部为 WCAG 2.2 现行文本：

**(1) SC 2.3.3 Animation from Interactions — Level AAA**
https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html

> Motion animation triggered by interaction can be disabled, unless the animation is essential to the functionality or the information being conveyed.

理解文档的关键区分（原文）：

> "Animation from interactions" applies when a **user's interaction initiates** non-essential animation. In contrast, **2.2.2 Pause, Stop, Hide applies when the web page initiates animation "automatically"** that is not in response to an intentional user activation. There may be situations where a particular animation may fail both success criteria.

以及关于滚动导致位移的边界（原文）：

> What about movement caused by a user scrolling a page? Moving new content into the viewport is **essential for scrolling**. The user controls the essential scrolling movement so it is allowed. Only add non-essential animation to the scrolling interaction in a responsible way. **Always give users the ability to turn off unnecessary movement.**

**官方"充分技术"（Sufficient Techniques）原文三条**：

> - **C39**: Using the CSS prefers-reduced-motion query to prevent motion
> - **SCR40**: Using the CSS prefers-reduced-motion query in JavaScript to prevent motion
> - **Gx**: Allowing users to set a preference that prevents animation

C39 页面（https://www.w3.org/WAI/WCAG22/Techniques/css/C39）给出两个方向，**两种都官方认可**：

```css
/* CSS for the motion effect */
@media (prefers-reduced-motion: reduce) {
  /* CSS to disable motion goes here */
}
```

> Alternatively, it is possible to take the inverse approach: define static styles, and then include a media query that only applies when the user has not set the reduced motion preference.

```css
/* "Static" CSS styles */
@media (prefers-reduced-motion: no-preference) {
  /* CSS for the motion effect goes here */
}
```

C39 的测试过程（原文）：

> For each interactive element that triggers a motion animation as a result of a user interaction: 1. Enable the reduced motion setting in your system; 2. Check that the motion animation is essential; 3. Check that the motion animation is suppressed. Expected Results: #2 or #3 is true.

**落到本项目**：推荐用 **C39 的"逆序写法"（`no-preference` 包裹）**，因为它让"静止态"成为默认值 —— 这正是解决 §3.3 里"无 JS / 无动效时内容不可见"问题的钥匙。（注意：`prefers-reduced-motion` 是**交互触发**动效的条款；滚动进场淡入属于"用户滚动触发"，落在 2.3.3 的管辖范围内，见理解文档引文。）

**(2) SC 2.2.2 Pause, Stop, Hide — Level A**
https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html

> For moving, blinking, scrolling, or auto-updating information, all of the following are true:
> **Moving, blinking, scrolling** — For any moving, blinking or scrolling information that (1) **starts automatically**, (2) **lasts more than five seconds**, and (3) is presented in parallel with other content, there is a mechanism for the user to pause, stop, or hide it unless the movement is essential; and
> **Auto-updating** — For any auto-updating information that (1) starts automatically and (2) is presented in parallel with other content, there is a mechanism for the user to pause, stop, or hide it or to control the frequency of the update unless ...

> "starts automatically" broadly refers to animations/updates that are **not the direct result of a user's intentional activation**, for example, selecting a link or button.

**落到本项目**：**任何自动播放且超过 5 秒的动画都必须能停**。因此 §3.6 的 count-up（通常 < 1s）不触发本条；但如果将来做"自动循环的数字/图表动效"，就必须给暂停控件。

**(3) SC 2.3.1 Three Flashes or Below Threshold — Level A**
https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html

> Web pages do not contain anything that **flashes more than three times in any one second period**, or the flash is below the general flash and red flash thresholds.

即 **3 Hz 上限**。同页给出的量化细节（原文摘录）：

> Substituting CSS pixels for the original pixel block means that the combined area of flashing becomes **341 x 256 CSS pixels, or a flashing area of 87,296 CSS pixels**.
> ... the industry standard definition of a general flash is a **change in luminance of 20 cd/m2 or more where the darker image is below 160 cd/m2**. (ITU-R BT.1702.) ... For HDR content when the darker state is **160 cd/m2 or more**, a general flash is one where the **Michelson contrast is 1/17 or greater** — calculated as `(LHigh - LLow) / (LHigh + LLow)`.

**落到本项目**：我们的动效都是 ≤ 1 次的单向过渡，**不接近 3Hz**，本条实际不构成约束。写出来是为了"没有闪烁风险"这个结论有条款依据。

### 2.3 Lighthouse / axe 有没有动效审计项？—— 如实回答：没有

这一条我问得很具体，因为它决定"动效会不会掉分"。

**【本项目实测】Lighthouse 13.5.0（`site/node_modules/lighthouse`）：**

- 遍历 `core/audits/` 的文件名，匹配 `anim|motion|reduc|flicker|flash` 的结果**只有 1 个**：`non-composited-animations`。
- 全 `lighthouse/core` 目录 grep `reduced-motion|prefers-reduced` 只有 **4 处命中，全部在 Baseline 支持数据 JSON 里**（`core/lib/baseline/web-features-data.json`），**不是审计项**。
- 该唯一相关审计的自我描述（`core/audits/non-composited-animations.js` 第 16-21 行原文）：

  > title: 'Avoid non-composited animations'
  > description: 'Animations which are not composited can be janky and increase CLS.'

  **它是性能类诊断（diagnostic），不是无障碍审计，也不参与 Accessibility 分数。** 而且它在 Lighthouse 的实验室加载过程中只追踪**加载期间真实发生的**动画 —— hover 触发的阴影过渡在跑分时根本不会触发，所以**不会被它抓到**（推演，非实测）。

**【本项目实测】axe-core 4.13.0（`site/node_modules/axe-core`）：**

- 在整个 `axe.js` 里 grep `animation` → **0 命中**。
- grep `prefers-reduced` → **0 命中**（`aria-hidden` 有 189 处，说明索引正常，不是搜错文件）。
- 唯一沾边的规则是 `blink`（`Ensure <blink> elements are not used`，`axe.js:30734-30736`）和 `marquee`（`axe.js:13304` 等），都是"别用这些过时标签"，与 CSS 动效无关。

**结论（已核实）**：
1. **Lighthouse 和 axe 都没有任何"检查 prefers-reduced-motion 是否被尊重"的审计项。** 你的 100 分和 99/95 分**不会因为动效做错而掉**（也不会因为做对而涨）。
2. 这意味着**无障碍动效必须靠人工/规范自证**，不能靠跑分兜底。第 2.2 节的 C39/SCR40 就是自证工具。
3. 唯一可能被 Lighthouse 抓到的是 `non-composited-animations`（会算进 Performance 类），但**前置条件是动画在加载窗口内真的跑了**，且它只是 diagnostic（权重为 0，只显示不扣分）。下面 §3.1 会给"用可合成属性"的具体做法，规避它。

## 3. B. 具体动效清单：逐条评估值不值得做

统一前提（本节所有代码都遵守）：

1. **静态样式为默认态**，动效只在 `@media (prefers-reduced-motion: no-preference)`（或 Tailwind 的 `motion-safe:`）里追加 —— 即 WCAG C39 的逆序写法。【官方规范】
2. **只动 transform 家族（`translate`/`scale`/`rotate`）与 `opacity`**，避免布局属性。Tailwind v4 的 `translate-*`/`scale-*` 映射到 `translate`/`scale` 独立属性（§1.5 已实测）。
3. 时长落在 **150–300ms**，卡片类不超过 300ms（依据 §4.1 的 M3/Carbon token 区间与 §4.3 经验值）。
4. 键盘 `:focus-visible` 必须获得与 `:hover` **同等**的视觉反馈。

### 3.1 卡片 hover：上浮位移 vs 阴影加深 vs 边框变色 vs 封面内部微缩放

#### 四种手法的逐项判断

| 手法 | 值不值得 | 理由（含来源） |
|---|---|---|
| **阴影加深**（现状） | **保留，当前唯一必做** | 纯 `box-shadow` 变化，不动几何 → 无 CLS、无位移 → 不触发前庭不适。已有 `shadow-1 → shadow-2`，token 已在 `theme.css` 里定义（本项目实测亮色 `--shadow-1:0 1px 2px #1c1b1a0d`、`--shadow-2:0 10px 30px -14px #1c1b1a2e, 0 2px 6px -2px #1c1b1a0f`）。代价：`box-shadow` 是 **paint 属性、不是可合成属性** → 每次 hover 重绘该卡片。单卡重绘成本很低，可接受。 |
| **上浮位移** | **推荐做，但只给 −2px，且与阴影同时** | 位移是「整卡抬起来」最直接的隐喻。但 MDN 明确把 **scaling or panning large objects** 列为前庭触发源（§2.1 原文）→ 位移必须极小。**2px 在感知上是"抬了一下"，不是"动了一下"**。 |
| **边框变色** | **不推荐**（本项目尤其） | ① 卡片已有 1px `border-border` + 阴影，再变色是"三重信号"，属花哨；② 会与 `group-hover:text-accent` 的强调色抢视觉层级；③ 站点的语义色已被 `--section-*` 占用（封面左侧 6px 色条），卡片外框再上色会稀释"区块色"这个信息。 |
| **封面内部微缩放**（对 SVG 做 `scale`） | **可选，幅度 ≤ 1.02，必须 `origin-center`** | 四条里**最接近"花哨"**的一条：它缩放的是一个 536×301 的大对象，正好命中 MDN 点名的前庭触发模式。要做就 **≤ 1.02**、时长 ≥ 250ms。唯一的缓冲：封面是 `role="presentation" aria-hidden="true"` 的装饰 SVG，缩放它不影响辅助技术。 |

#### 整卡链接（`<a>` 包住整张卡）的坑 —— 逐条

【本项目实测】当前结构（`Card.astro:38-43`）：

```html
<li class="my-0">
  <a
    href={href}
    class="border-border bg-surface-1 shadow-1 hover:shadow-2 focus-visible:no-underline group flex h-full flex-col overflow-hidden rounded-xl border transition-shadow duration-200"
  >
    {cover && <Cover {...cover} />}
    ...
  </a>
</li>
```

**坑 1：`:hover` 的视觉反馈没有镜像到 `:focus-visible`（现存缺陷）。**
卡片上当前有两个 hover 专属反馈：`hover:shadow-2`（第 41 行）和标题的 `group-hover:text-accent`（第 59 行）。键盘用户 Tab 到整卡链接时**只有 `global.css:20-24` 的虚线描边**，阴影不加深、标题不变强调色。这不是 WCAG 违规（有可见焦点指示），但属于「同一控件两套反馈」的不一致。修法：把 `hover:` 全部补上 `focus-visible:` / `group-focus-visible:`（Tailwind v4 原生支持这两个变体）。

**坑 2：`translate` 会创建新的堆叠上下文。**
【官方规范】MDN `translate` 的形式定义明确写着 **`Creates stacking context: yes`**（https://developer.mozilla.org/en-US/docs/Web/CSS/translate 的 "Formal definition" 表）。【未核实】同一页面**没有**声明它会为 `position: fixed` 后代创建包含块（`transform` 简写会，`translate` 独立属性我没核到规范依据）。对本项目影响：Card 内部没有 `position: fixed` 元素，**当前无实际风险**；但这条要进 review checklist —— 以后往卡片里塞 `fixed` 或依赖 `z-index` 的悬浮层时要重测。

**坑 3：`overflow-hidden` 与阴影/缩放的关系（好消息）。**
`overflow-hidden` 只裁剪**后代**，不裁剪元素自身的 `box-shadow`，所以 `shadow-2` 不会被切；而封面 SVG 放大到 1.02 时会被 `overflow-hidden` + `rounded-xl` 正确裁在圆角内 —— 这正是想要的效果。

**坑 4：transition 属性必须显式列出，`transition-shadow` 不会带上位移。**
【官方源码】产物 CSS 实测：`.transition-shadow{transition-property:box-shadow;...}`。所以加了 `translate-y-*` 之后必须换成 `transition-[box-shadow,translate]`，否则位移是**瞬跳**的（比不做还难看）。

**坑 5：`hover:` 在触屏上粘住的问题 —— Tailwind v4 已经解决。**
【官方源码】产物 CSS 里 `@media (hover:hover)` 出现 7 次，说明本项目用的 Tailwind v4.3.2 给 `hover:` 变体自动加了 `(hover: hover)` 门。**不需要**自己再包一层 `@media (hover:hover)`。

#### 推荐代码（可直接替换 Card.astro 第 39-42 行）

```html
<li class="my-0">
  <a
    href={href}
    class="border-border bg-surface-1 shadow-1 group flex h-full flex-col overflow-hidden rounded-xl border
           transition-[box-shadow,translate] duration-200 ease-out
           hover:shadow-2 focus-visible:shadow-2
           focus-visible:no-underline
           motion-safe:hover:-translate-y-0.5 motion-safe:focus-visible:-translate-y-0.5"
  >
```

要点说明：

- `-translate-y-0.5` = `calc(var(--spacing) * -0.5)`，本项目产物里 `--spacing:.25rem`（实测）→ **正好 −2px**。
- `duration-200` = `transition-duration: .2s`（实测），与原 200ms 一致，**没有改时长**。
- `ease-out` = Tailwind v4 的 `cubic-bezier(0, 0, 0.2, 1)`（`theme.css:435`），也正好等于 Material 3 的 `easing-standard-decelerate`（§4.1）—— 「进去快、停住慢」，适合 hover 这种短反馈。
- `motion-safe:` 保证 reduce 用户只看到阴影变化、无位移。阴影本身**不是"运动"**（MDN 的前庭描述针对 scale/pan/位移），保留是合理的。想更保守就只留阴影，同样成立。

标题的 hover/focus 一致性（`Card.astro:58-60`）也补一句：

```html
<Heading class="group-hover:text-accent group-focus-visible:text-accent text-lg leading-snug font-semibold tracking-tight">
```

#### 封面内部微缩放（可选，默认不建议）

如果要做，改 `Cover.astro:65-69` 的 `<svg>`：

```html
<svg
  class="block h-auto w-full origin-center motion-safe:transition-[scale] motion-safe:duration-300 motion-safe:ease-out motion-safe:group-hover:scale-[1.02]"
  viewBox={`0 0 ${W} ${H}`}
  role="presentation"
  aria-hidden="true"
>
```

- `scale-[1.02]`：**上限**。`translate`/`scale` 是独立属性，和 `transition-[box-shadow,translate]` 互不干扰，两张过渡可以共存。
- **不要**做 `1.05` 以上，也不要做 `scale` + 大幅 `translate` 组合。
- 副作用：SVG 内的 `<text>` 会一起放大 → 缩放光栅化会带来极轻微模糊，1.02 下肉眼基本无感。

#### 性能影响小结（3.1）

| 项 | 结论 |
|---|---|
| CLS | **0**。阴影、`translate`、`scale` 都不改变布局盒尺寸/位置，不产生 layout shift。 |
| 合成 | `translate`/`scale` 可合成；`box-shadow` 是 paint 属性，会重绘该卡片一次。单卡面积小，可接受。 |
| Lighthouse | 不影响。`non-composited-animations` 是 diagnostic（权重 0），且只在加载窗口内追动画，hover 过渡跑分时不会触发。 |
| 无 JS | 完全可用（纯 CSS）。 |

**推荐结论：做「阴影加深 + 2px 上浮 + focus-visible 对齐」；封面内缩放列为可选加分项，默认不做。**

### 3.2 链接 / 按钮 hover：下划线动画

#### 三种实现方式对比

| 方式 | 可动画性 | 是否可合成 | 判断 |
|---|---|---|---|
| `text-decoration` / `-color` / `-thickness` | 可过渡（颜色、粗细是连续量） | 否（paint） | **最克制**，但不能做「从左划出来」，只能整体变色/变粗。 |
| `background-size`（渐变当线条） | 可过渡（`0% 1px → 100% 1px`） | 否（paint） | 「从左划出下划线」的经典做法。**推荐用于导航/页脚等短链接**。 |
| `clip-path` | 【官方规范】本项目离线 `web-features@3.40.0` 数据集 `clip-path-animatable`：**baseline=high，low 2020-01-15，high 2022-07-15**（Chrome 55 / Firefox 49 / Safari 12.1） | 否（paint） | 能做更自由的方向（对角/圆形揭示），但**对纯下划线是杀鸡用牛刀**，且 `clip-path` 会创建新的裁剪上下文，容易与卡片 `overflow-hidden` 打架。**不推荐**。 |

#### 本项目现状（先别动）

【本项目实测】站点已经是「克制」的：

- `global.css:20-24`：`a, button, #main-content` 有 `focus-visible:outline-2 focus-visible:outline-dashed focus-visible:no-underline`（**焦点态用虚线描边替代下划线** —— 这个策略本身就很对）。
- 产物 `Footer.BxwaP4fT.css` 里：`.app-prose a{overflow-wrap:break-word;color:var(--foreground);text-underline-offset:4px;text-decoration-style:dashed}` + `@media (hover:hover){.app-prose a:hover{color:var(--accent)}}`。
- 正文链接已有 `text-underline-offset: 4px`，对中文（有下伸部/字面下沉）是合适的做法。

所以：**正文链接不要加下划线动画**。原因很具体：`background-size` 画的是**实线**，会和 `text-decoration-style: dashed` 的虚线**同时出现在同一个链接上**，视觉会很脏。

#### 推荐做法：只给「导航 / 页脚 / 按钮」这类实心链接加滑出下划线

写在 `global.css`（可复用现成的 `@utility` 写法，见 `global.css:31-45`）：

```css
@utility link-rule {
  /* 默认态：没有线 */
  background-image: linear-gradient(currentColor, currentColor);
  background-repeat: no-repeat;
  background-position: 0 100%;
  background-size: 0% 1px;
  text-decoration: none;
}

/* 只在允许动效时给过渡；reduce 用户仍是 0% → 悬停瞬间出现，不做动画 */
@media (prefers-reduced-motion: no-preference) {
  .link-rule {
    transition: background-size 200ms cubic-bezier(0, 0, 0.2, 1);
  }
}

@media (hover: hover) {
  .link-rule:hover {
    background-size: 100% 1px;
  }
}

/* 键盘焦点必须同等反馈 */
.link-rule:focus-visible {
  background-size: 100% 1px;
}
```

要点：

- 缓动 `cubic-bezier(0, 0, 0.2, 1)` 就是 M3 `easing-standard-decelerate`（§4.1，抄自 Material Web 官方 token 源码）；`200ms` 是 M3 `duration-short4`。**两个数字都是抄的，不是估的。**
- `currentColor` 保证亮/暗色主题与 `text-accent` 联动，不用改两处。
- `@media (hover: hover)` **这里必须自己写** —— 手写 CSS 享受不到 Tailwind `hover:` 变体的自动包裹（§1.5）。
- 嫌 `200ms` 慢可降到 `150ms`（M3 `duration-short3`），**不要低于 100ms**（会显得是瞬跳，反而像 bug）。

#### 性能影响小结（3.2）

- `text-decoration-color` / `background-size` / `clip-path` **都不是可合成属性**，过渡期间会 paint；文本级重绘面积极小，**对 Lighthouse 无影响**（跑分时不触发 hover）。
- **不要**用 `transition: all`。注意参考站点里有反例：Visual Cinnamon 的 CSS 就是 `transition: all .15s ease`（§5），那是反面教材。

**推荐结论：正文链接保持现状；只给导航/页脚/按钮加 `.link-rule` 滑出下划线。**

### 3.3 卡片进入视口的淡入上移（scroll-driven / IntersectionObserver）

这是全部候选项里**风险最高**的一项，两个问题必须一次性解决：**CLS** 和 **无 JS 时内容不可见**。

#### 问题一：会不会造成 CLS？—— 不会，但真正的 CLS 风险在别处

- `opacity` 不参与布局，**按定义不产生 layout shift**。
- `translate` / `transform` 是绘制阶段的变换，**不改变元素的布局盒**，因此不产生 layout shift。【未核实】我没能抓到一份把"transform 不计入 CLS"写成明文的一手规范（web.dev 的 CLS 文章在本环境抓取失败），所以这条按**工程结论**给出。
- 【本项目实测｜真实浏览器探针】移动端（390×844）首页：**LCP 元素 = H1（2016ms）、CLS = 0、零条 layout-shift、失败请求 0**，页面共 **17 张内联 SVG 封面**。这同时回答两个问题：① 当前 CLS 基线是 0，任何改动都必须守住；② **内联 SVG 在当前首页上不会成为 LCP 候选元素**（LCP 是 H1）。
- 自检方法：改完用 Lighthouse 的 "Cumulative Layout Shift" 审计看是否仍为 0，以及 DevTools Performance 面板录制看有没有 Layout Shift 事件。
- **本项目真正的 CLS 隐患不在动效，而在封面**：`Cover.astro:65-69` 的 `<svg class="block h-auto w-full" viewBox="0 0 536 301">` 有 `viewBox` + `h-auto w-full` → 浏览器能从 viewBox 推出固有宽高比 → **不会闪**。这是个好消息，保持它，别改成 `height` 固定值。

结论：**"淡入 + 2~4px 上移"本身不会引入 CLS。**

#### 问题二：无 JS 时内容不可见？—— 这是真问题，必须按下面的结构写

反面写法（**绝对不要**）：

```css
/* ❌ 危险：默认隐藏，靠 JS 才显示。JS 失败 = 内容永久不可见 */
.reveal { opacity: 0; translate: 0 12px; }
.reveal.is-visible { opacity: 1; translate: 0 0; }
```

正确写法：**静态样式可见为默认**，动效由「`no-preference` 媒体查询 + JS 加的 `.js` 类」双重门控。

```css
/* global.css —— 默认完全可见。无 JS、reduce motion、老浏览器都走这一支 */
.reveal { opacity: 1; }

@media (prefers-reduced-motion: no-preference) {
  /* 只有 JS 已确认可用时，html.js 才把初始态设成"待进场" */
  .js .reveal {
    opacity: 0;
    translate: 0 8px;
  }
  .js .reveal.is-visible {
    opacity: 1;
    translate: 0 0;
    transition: opacity 320ms cubic-bezier(0, 0, 0.2, 1),
                translate 320ms cubic-bezier(0, 0, 0.2, 1);
  }
}
```

`html.js` 必须在**首次绘制之前**加上，否则会先看到内容、再跳到隐藏（闪一下）。`Layout.astro` 第 115-128 行已经有一个同步的内联 FOUC 防护脚本，把这一行塞进它就行：

```html
<!-- Layout.astro：加在现有内联主题脚本（第 115-128 行）内部即可 -->
<script is:inline>
  (function () {
    // ... 现有的主题逻辑 ...
    // 新增：标记 JS 可用，供 .reveal 进场动画使用
    document.documentElement.classList.add("js");
  })();
</script>
```

JS 侧（放进 `Main.astro` 或一个独立组件；**注意必须挂 `astro:page-load`**，理由见 §1.3）：

```ts
<script>
  let io: IntersectionObserver | null = null;

  function setupReveal() {
    // 尊重用户偏好：reduce 时什么都不做，内容本来就是可见的
    if (!window.matchMedia("(prefers-reduced-motion: no-preference)").matches) return;

    const targets = document.querySelectorAll<HTMLElement>(".reveal:not(.is-visible)");
    if (!targets.length) return;

    io?.disconnect();
    io = new IntersectionObserver(
      entries => {
        for (const entry of entries) {
          if (!entry.isIntersecting) continue;
          entry.target.classList.add("is-visible");
          io?.unobserve(entry.target);   // 一次性，滚回去不重放
        }
      },
      // 元素进入视口下缘 10% 时就算"进场"，避免用户已经看到一半才开始动
      { rootMargin: "0px 0px -10% 0px" }
    );
    targets.forEach(el => io!.observe(el));
  }

  setupReveal();
  // ClientRouter 每次导航后都是新 DOM，必须重挂（这是 §1.3 同一类问题的正面范例）
  document.addEventListener("astro:page-load", setupReveal);
</script>
```

要点：

- `io?.disconnect()` + 重新 observe：避免每次导航累积 observer。
- **一次性**（`unobserve`）：滚回去不重放。重放会让页面在来回滚动时不断动，这是"花哨"的主要来源。
- 位移 **8px**、时长 **320ms**、缓动 `cubic-bezier(0,0,0.2,1)`（M3 decelerate）。8px 很小 —— 目的是"内容浮上来"，不是"飞进来"。**上限建议 12px**。
- **不要**给列表里每一张卡都加错开的 `transition-delay`（stagger）。视觉上会变成"瀑布"，是典型的花哨特征。若一定要错开，上限 40ms/项，且仅限首屏。
- `is-visible` 的建议挂载点：列表容器（`<ul>`）或整个 section，而不是每张卡各挂一个 —— 同时动起来的元素越少越好（§4.3）。

#### 替代方案：CSS 滚动驱动动画（scroll-driven animations）—— 只作为渐进增强

【官方规范】本项目离线 `web-features@3.40.0` 数据集 `scroll-driven-animations`：**`baseline=false`**（尚未进入 Baseline）。支持情况：`animation-timeline` / `view-timeline` / `animation-range` 在 **Chrome 115 / Edge 115 / Safari 26** 有，**Firefox 不在列表里**（该 feature 的 `support` 字段只有 chrome/chrome_android/edge/safari/safari_ios）。

结论：**不能单独用它**（Firefox 用户会看到什么？——如果没有 fallback，用 `animation-timeline` 写的进场会退化成"按默认时长播放一次"，可能拍在不可见区域，反而更糟）。

正确的渐进增强写法：

```css
/* 默认走 IntersectionObserver 的 .js/.is-visible 方案（见上） */

/* 浏览器支持滚动驱动时，改由滚动位置驱动，JS 完全不需要参与 */
@supports (animation-timeline: view()) {
  @media (prefers-reduced-motion: no-preference) {
    .js .reveal {
      /* 覆盖 IO 方案：不再靠 is-visible */
      opacity: 1;
      translate: none;
      animation: reveal-in linear both;
      animation-timeline: view();
      animation-range: entry 0% entry 60%;
    }
  }
  @keyframes reveal-in {
    from { opacity: 0; translate: 0 8px; }
    to   { opacity: 1; translate: 0 0; }
  }
}
```

- 好处：`@supports` 命中时是**滚动位置驱动**，不会"滚过头才播完"，也没有 JS 成本；未命中时自动退回 IO 方案。
- 【未核实】`animation-range: entry 0% entry 60%` 的观感需要实机调，本文给的区间是起点建议值而非抄来的值。
- **注意**：`@supports (animation-timeline: view())` 在 Firefox 里为 false → 会走 IO 分支，安全。

#### 性能影响小结（3.3）

| 项 | 结论 |
|---|---|
| CLS | 0（前提：不碰 height/width/margin；封面保持 `viewBox` + `h-auto`） |
| 主线程 | IntersectionObserver 回调极轻；一次性 unobserve |
| Lighthouse | 不影响。若用 scroll-driven 方案，注意 Chrome 的 `non-composited-animations` 可能报"Custom CSS properties cannot be animated on the compositor"之类，但该审计权重为 0（diagnostic） |
| 无 JS | 内容完全可见（`.js` 类没加上 → `.reveal` 保持 `opacity: 1`） |
| reduce motion | 不注册 observer、不加 `.js` 依赖样式 → 静态呈现 |

**推荐结论：做，但只用在「列表区块整体」这一层，不要逐卡错开。位移 ≤ 8px，一次性，挂在 `astro:page-load`。**

#### 3.4.2 补上缺失的 reduced-motion 闸门（必做）

```css
/* 复刻自 astro/components/viewtransitions.css:56-66（本项目的 Astro 产物没有带上它） */
@media (prefers-reduced-motion: reduce) {
  ::view-transition-group(*),
  ::view-transition-old(*),

    animation: none !important;
  }

  }
}
```

⚠️ 但这里有一个**必须交代清楚的事实**：W3C CSSWG 2024-09-24 的决议方向是"**reduce 时 UA 用纯交叉淡入淡出，而不是完全不动**"（§1.4 原文）。所以这段 CSS 会让本站比 UA 默认**更激进**（完全不动）。这两种都属于"尊重用户偏好"，选哪个是可辩护的；如果担心"完全不动会让人不知道页面变了"，可以改成弱化的交叉淡入淡出而不是 `none`。**补充（父 agent 运行时实测，2026-10-09）：** Astro 在 `reducedMotion: 'reduce'` 下**仍然调用** `document.startViewTransition`（调用次数 no-preference = 1、reduce = 1），所以默认 cross-fade 是否播放由 **UA** 决定；上面这段 CSS 是让本站**比 UA 更保守**。**每新增一个自定义 `transition:animate` 或自定义 `::view-transition-*` 动画，都必须用同一探针在 reduce 下复测**（实测表见 §1.4）。

**（a）已核实的部分**

【官方源码/issue】下面几个 issue 是真实的、可查的：

**结论（已核实）**：pm-forge 用的 `astro@7.3.5` 存在"hover 预取 + 点击重新下载"的重复请求路径。#17550 未合并，所以升级小版本**不会**自动修复。缓解手段：确认 Vercel 对 HTML 返回了合适的 `Cache-Control`（让浏览器的普通 HTTP 缓存能命中 prefetch 结果）；或者在 `astro.config.ts` 里显式配置 prefetch 策略（见下）。

**（b）关于「Astro 的 prefetch 会静默阻塞跨文档 View Transitions」—— 我核实到的是这个**

【本项目实测】这句话确实存在于 maggieappleton.com 的 HTML 注释里，原文逐字如下（我在 `https://maggieappleton.com/` 与 `https://maggieappleton.com/colophon` 的源码里都抓到，且两页完全一致）：

> `<!-- Browser-native prefetch on hover. Astro's prefetch script stops Chrome from running cross-document view transitions, so it stays off. -->`

同页另一条注释：

> `<!-- Inline so Chrome sees the opt-in before external CSS loads; otherwise it skips the transition on heavier pages. -->`

**她实际的实现（我读了她线上 HTML，可复核）**：

1. **没有用 `<ClientRouter />`** —— 全页搜 `astro-view-transitions-enabled` 零命中。
2. 用的是**浏览器原生跨文档过渡**，内联：`<style>@view-transition { navigation: auto; }</style>`。
3. **没有用 Astro 的 prefetch**，而是自己手写了一段 Speculation Rules：
   `<script type="speculationrules">{"prefetch":[{"where":{"href_matches":"/*"},"eagerness":"moderate"}]}</script>`
   也就是「浏览器原生 prefetch on hover」，注释说的是这个。

**我核不实的部分（明确写出来）**：我**没有找到**任何 Chromium / Chrome / W3C / Astro 的一手来源，声称"Astro 的 prefetch 脚本会阻止跨文档 View Transitions"。我查证过的一手依据指向**不支持**这个因果结论：

- 【官方规范】MDN `@view-transition` 页面给出的跨文档过渡触发条件是：同源、无跨源重定向、`navigationType` 为 `traverse`/`push`/`replace`，且 push/replace 时导航须由用户与页面内容交互发起 —— **prefetch 不在任何一条条件里**。
- 【官方规范】MDN `View_Transition_API/Using` 页面同样只列了"同源 + 双方 CSS opt-in 到 `@view-transition { navigation: auto }`"，全页 grep `prefetch` **零命中**。

因此我的结论是：**那条注释应被当作一位实践者的经验观察，而不是可依赖的规范结论。**（也不排除她观察到的现象另有原因，例如 opt-in 的时序 —— 她自己另一条注释就在处理"Chrome 要在外部 CSS 加载前看到 opt-in 否则跳过过渡"。）

**（c）对 pm-forge 最重要的推论**

**因为 pm-forge 用的是 `<ClientRouter />`，浏览器原生跨文档过渡根本不会参与** —— ClientRouter 在 `click` 上 `preventDefault()` 然后走自己的 `navigate()`（`ClientRouter.astro:62-103` 原文可复核），是 same-document 过渡。所以 maggieappleton 那个顾虑**对本项目完全不适用**。

反过来说：**如果想把 ClientRouter 换成原生跨文档过渡（零 JS、更少脚本风险）**，收益是彻底消除 §1.3 那类"脚本只执行一次"的问题；代价是项目里所有 `astro:page-load` / `astro:after-swap` / `astro:before-swap` 监听**全部失效**（`theme.ts`、`Header.astro`、`Main.astro`、`index.astro`、`BackButton.astro`、`ArticleEnhancements.astro`），且会失去路由播报器。**这是一个独立的重构议题，不建议和本轮动效美化绑在一起做。**（Astro 官方也在往这个方向走：官方博客《The future of Astro: zero-JS view transitions》被 docs 引用为"ClientRouter 的必要性会越来越低"。）

#### 3.4.4 【推荐】prefetch 显式化 + 脚本重执行的修复

**(1) 把 prefetch 默认值写进 config（可读性 + 可回滚）**

`site/astro.config.ts`，在 `defineConfig({...})` 里加：

```ts
export default defineConfig({
  // ClientRouter 会默认打开 prefetch 并设 prefetchAll: true（见 astro types/public/config.d.ts:1904,1924）
  // 这里显式写出来，避免"隐式默认"在升级时被改变
  prefetch: {
    prefetchAll: true,
    defaultStrategy: "hover", // 可选 'tap' | 'hover' | 'viewport' | 'load'
  },
  // ...
});
```

- 【官方文档】四个策略的语义（Prefetch 指南原文）：`hover`（默认，悬停或聚焦时）、`tap`（点击前）、`viewport`（进入视口时）、`load`（页面加载后全部）。慢连接/省流模式会自动降级到 `tap`。
- **不建议**改成 `viewport`：那会在移动端一进页面就把所有可见卡片全预取，流量开销明显。
- **不建议**改成 `false`：prefetch 是 ClientRouter 体感"快"的主要来源。
- 单独某个链接若不该预取，加 `data-astro-prefetch="false"`（官方 docs 原文给出的关闭方式）。

### 3.5 隐形排版动效（`text-wrap` / `font-variant-numeric` / `scroll-behavior`）

这三条的共同特征是：**不是"动"的动效，而是"消除跳变"**。对数据新闻站点反而比 hover 效果更值钱。

#### (1) `text-wrap: balance` —— **推荐，用在标题**

【官方规范】本项目离线 `web-features@3.40.0`：
- `text-wrap: balance`：**baseline=low，low date 2024-05-13**，支持 Chrome 114 / Edge 114 / Firefox 121 / Safari 17.5。
- `text-wrap: pretty`：**baseline=false**，支持 Chrome 117 / Edge 117 / Safari 26 —— **Firefox 不在支持列表**。

做法（加在标题上，不要全局加）：

```css
/* typography.css 或 global.css */
h1, h2, h3 { text-wrap: balance; }   /* 中文标题换行更均衡，避免末行只剩 1-2 字 */
```

- 中文语境下这条收益明显：中文标题经常出现"最后一行两个字"的孤行，`balance` 能把行宽摊匀。
- 【未核实】UA 对 `balance` 的**行数上限**（常见说法是"只对少数行生效"）我没抓到一手规范明文，所以**不要**指望它作用于长段落。
- `text-wrap: pretty` 是"避免孤字"的另一档，但 Firefox 缺失 → 只作为可选的渐进增强，加了也不会有害（不支持的浏览器直接忽略声明）。

#### (2) `font-variant-numeric` —— **已经加了，只需检查粒度**

【本项目实测】`global.css:10-13` 已经有：

```css
body {
  /* 数据站点：数字一律等宽，避免数字跳动与列不对齐 */
  font-variant-numeric: tabular-nums;
}
```

- 【官方规范】`font-variant-numeric`（含 `tabular-nums`）：**baseline=high**，low 2020-01-15，high 2022-07-15，支持 Chrome 52 / Firefox 34 / Safari 9.1。
- 这条是**最值钱的"隐形动效"**：它让数字在更新时不会横向抖动，也是 §3.6 count-up 能看的前提。
- **一个设计建议（属经验值，非规范）**：`tabular-nums` 全局生效意味着拉丁数字在大号标题里也是等宽的，会显得略松散。如果哪天觉得标题难看，可以只在正文/表格保留，标题局部用 `font-variant-numeric: proportional-nums`。**当前不建议改**，因为数据站点的一致性收益大于这点排版收益。

#### (3) `scroll-behavior: smooth` —— **已经在，但缺 reduce 门（现存缺陷）**

【本项目实测】`Layout.astro:47`：`<html class="overflow-y-scroll scroll-smooth">`；产物 CSS：`.scroll-smooth{scroll-behavior:smooth}`。

问题：**它是无条件生效的，没有 respect `prefers-reduced-motion`。**

- 【官方规范】WCAG C39 的 `reduce` 分支是"disable motion"；参考站点全都把 `scroll-behavior` 纳入 reduce 重置：
  - Maggie Appleton 线上 CSS 原文：`@media (prefers-reduced-motion: reduce){html:focus-within{scroll-behavior:auto}*,*:before,*:after{animation-duration:.01ms!important;animation-iteration-count:1!important;transition-duration:.01ms!important;scroll-behavior:auto!important}}`
  - Josh Comeau 线上 CSS 里也有同款的 reduce 重置块（多处）。
- 【官方规范】`scroll-behavior` baseline=high（low 2022-03-14，high 2024-09-14；Chrome 61 / Firefox 36 / Safari 15.4）。

修法（二选一）：

```css
/* 方案 A：保留 Tailwind 的 scroll-smooth，另加一条覆盖（推荐，改动最小） */
@media (prefers-reduced-motion: reduce) {
  html { scroll-behavior: auto; }
}
```

```html
<!-- 方案 B：把 Layout.astro:47 的 scroll-smooth 换成 motion-safe:scroll-smooth -->
<html class="overflow-y-scroll motion-safe:scroll-smooth">
```

- 方案 B 更"Tailwind"，但要注意 `motion-safe:` 会包一层 `@media (prefers-reduced-motion: no-preference)`，需要确认它与 `overflow-y-scroll` 的组合没问题（两者独立，无冲突）。
- **注意**：这一条是**当前就存在的无障碍缺口**，和要不要做新动效无关，建议顺手修掉。

#### 性能影响小结（3.5）

- `text-wrap: balance` 有排版计算成本，但只作用于少数标题 → 可忽略。**不要**全局套到 `p` 上。
- `font-variant-numeric` 零成本。
- `scroll-behavior: smooth` 零成本。

**推荐结论：`text-wrap: balance` 加到 h1-h3；`font-variant-numeric` 保持现状；`scroll-behavior` 立刻补 reduce 门。**

### 3.6 数字递增（count-up）计数动画：证据面板里值不值得做？

#### 结论：**默认不做。**

理由（按重要性排序）：

1. **它把"事实"变成了"表演"。** 站点的 MetricCards / 证据面板里的数字是**口径可查的结论**（`userbehavior.astro` 的注释明确写着"预置答案""口径可查"）。递增动画的语义是"这个数字正在长出来"，与"这是一个已经核定的结果"冲突。
2. **它让数字晚 0.6~1s 才能读。** 证据面板是给人扫读的；递增期间显示的是**错误值**（中间态），对"可复现"的定位是负分。
3. **无障碍成本不低**（见下），收益却只是"好看一点"。

#### 如果一定要做（例如只给首页一个 hero 数字），这样写

三条硬要求：

1. **最终值必须直接存在于 HTML 里**（SSR 输出终值）→ 保证无 JS、爬虫、屏幕阅读器拿到的是真值。
2. **动画必须由 JS 覆盖**，并且用 `matchMedia('(prefers-reduced-motion: no-preference)')` 门控。
3. **不要用 `aria-live`**。递增会在一秒内产生几十次 DOM 变更，`aria-live` 会把它们全播报出去（参考 SC 4.1.3 Status Messages 的意图是"通知重要变化"，不是"播报每一帧"）。正确做法是把**可视的动画数字 `aria-hidden`**，另给一个 `sr-only` 的静态真值。

```html
<!-- 组件输出（Astro SSR）：真值始终在 DOM 里 -->
<span class="font-mono tabular-nums">
  <span class="sr-only">1,234</span>
  <span aria-hidden="true" data-count-up="1234">1,234</span>
</span>
```

```ts
<script>
  function initCountUp(): void {
    if (!window.matchMedia("(prefers-reduced-motion: no-preference)").matches) return;

    document.querySelectorAll<HTMLElement>("[data-count-up]:not([data-counted])").forEach(el => {
      const target = Number(el.dataset.countUp);
      if (!Number.isFinite(target)) return;
      el.dataset.counted = "1";
      const duration = 700;            // 一次到位，不要超过 ~900ms
      const start = performance.now();
      const fmt = new Intl.NumberFormat("zh-CN");

      function frame(now: number): void {
        const t = Math.min(1, (now - start) / duration);
        // easeOutCubic：与 M3 ease-standard-decelerate 的观感一致，纯 JS 侧等价写法
        const eased = 1 - Math.pow(1 - t, 3);
        el.textContent = fmt.format(Math.round(target * eased));
        if (t < 1) requestAnimationFrame(frame);
        else el.textContent = fmt.format(target);   // 收敛到精确终值，避免浮点误差
      }
      requestAnimationFrame(frame);
    });
  }

  initCountUp();
  document.addEventListener("astro:page-load", initCountUp); // §1.3
</script>
```

要点：

- `tabular-nums`（站点已全局启用）是前提，否则宽度会一直抖。
- `easeOutCubic` 的公式 `1 - Math.pow(1 - t, 3)` 是标准三次缓出，**不是从哪抄的 token**，所以标注：这是我给出的实现选择，非官方数值。
- **不要**做"数到超过目标再回弹"（overshoot），那是花哨信号。
- **不要**放在 `aria-live` 容器里，**不要**多组数字同时错开递增。
- 时长上限 `700ms`（若要更保守，用 `500ms`）。

#### 性能影响小结（3.6）

- 一次 `requestAnimationFrame` 循环，约 0.7s，只改一个文本节点 → 可忽略。
- 与 Lighthouse 无关（跑分时不会触发或极短）。
- 主要成本是**可访问性设计成本**，不是性能成本。

**推荐结论：不做。** 如果 v0.15 之后还想加"一点生命感"，把钱花在 §3.3 的区块进场和 §3.1 的卡片反馈上，性价比更高。

【官方文档】`developer.apple.com/design/human-interface-guidelines/motion` 也是 JS 渲染页，我用它背后的官方数据接口取到正文（`https://developer.apple.com/tutorials/data/design/human-interface-guidelines/motion.json`，返回 `Copyright © 2026 Apple Inc.` 的 HIG 原文）。

**逐字读完的结论：Apple HIG 的 Motion 章节只给原则，不给数字。** 原文关键句：

> **Add motion purposefully**, supporting the experience without overshadowing it. **Don't add motion for the sake of adding motion.** Gratuitous or excessive animation can distract people and may make them feel disconnected or physically uncomfortable.
>
> **Make motion optional.** Not everyone can or wants to experience the motion in your app or game, so it's essential to avoid using it as the only way to communicate important information.
>
> **Aim for brevity and precision in feedback animations.** When animated feedback is brief and precise, it tends to feel lightweight and unobtrusive...
>
> **In apps, generally avoid adding motion to UI interactions that occur frequently.** The system already provides subtle animations for interactions with standard interface elements.
>
> **Let people cancel motion.** As much as possible, don't make people wait for an animation to complete before they can do anything, especially if they have to experience the animation more than once.
>
> visionOS: **avoid showing objects that oscillate in a sustained way.** In particular, you want to avoid showing an **oscillation that has a frequency of around 0.2 Hz** because people can be very sensitive to this frequency.
>

**这些原则直接约束本项目**：

- "**generally avoid adding motion to UI interactions that occur frequently**" → 卡片 hover 是高频交互，所以**位移必须小到几乎不察觉**（这正是 −2px 的依据）。
- "**Let people cancel motion / don't make people wait**" → count-up 让用户等 0.7s 才能读数字，**违反这条**（§3.6）。
- "**0.2 Hz 持续振荡**" → 任何循环动画（呼吸、脉冲、循环 marquee）都不要做。

**唯一给出的数字是 0.2 Hz 与游戏帧率**（原文："maintaining a consistent frame rate of **30 to 60 fps**"）—— 与 Web 动效时长无关。所以"Apple 建议 200ms"这类说法**没有 HIG 依据，请勿引用**。

### 4.2 CSS `linear()` 弹簧曲线

【官方规范】MDN `linear()`（https://developer.mozilla.org/en-US/docs/Web/CSS/easing-function/linear）原文：

> Baseline: **Widely available** — This feature is well established and works across many devices and browser versions. It's been available across browsers **since December 2023**.

语法与语义（MDN 原文摘录）：

> `linear(0, 1)` / `linear(0, 0.25, 1)` / `linear(0, 0.25 75%, 1)`
> The `linear()` function allows the approximation of complex animations and transitions by interpolating linearly between the specified points.
> By default, the stops are **equidistant**. For example, if there are five stops, they will occur at 0%, 25%, 50%, 75%, and 100% of the duration.
> You can use optional percentage values to provide finer control... `linear(0, 0.5 25% 75%, 1)` ... reaches 50 pixels in 25 seconds and **remains there** for 50 seconds.
> Formal syntax: `<linear()> = linear( [ <number> && <percentage> {0,2} ]# )`

MDN 给出的非法示例（原文，用于自查）：

> /* At least two parameters are required */ `linear(0.5)`
> /* Percentages must be in ascending order */ `linear(0, 0.25 80%, 0.5 60%, 1)`

【官方规范】本项目离线 `web-features@3.40.0` 数据集 `linear-easing`：
**baseline=high，low 2023-12-11，high 2026-06-11**；compat key `css.types.easing-function.linear-function` 支持 **Chrome 113 / Edge 113 / Firefox 112 / Safari 17.2**。

#### 可直接用的代码

【博客·补充】下面这条 `linear()` 值**逐字抄自** Josh W. Comeau《Springs and Bounces in Native CSS》（`https://www.joshwcomeau.com/animation/linear-timing-function/`），是我在该页 `<code>` 块里抓到的原文（页面抓取被截断在 100k 字符，这是我能核实到的完整值）：

```css
/* 一个轻微回弹的弹簧：先冲过 1（1.25），再在 1 上下收敛 */
linear(0, 1.25, 1, 0.9, 1.04, 0.99, 1.005, 0.996, 1.001, 0.999, 1)
```

用法：

```css
@media (prefers-reduced-motion: no-preference) {
  .pop {
    transition: scale 400ms linear(0, 1.25, 1, 0.9, 1.04, 0.99, 1.005, 0.996, 1.001, 0.999, 1);
  }
  .pop:hover { scale: 1.03; }
}
```

**本项目的建议：默认不要用弹簧曲线。**

理由：回弹（overshoot）是"活泼"的视觉语言，与"克制、数据新闻编辑部"的定位冲突；M3 / Carbon 的官方缓动里**也没有**回弹曲线（M3 `emphasized` 仍是单调的 `cubic-bezier(0.2, 0, 0, 1)`）。**如果**要用，只在极小的元素上用（例如某个 hover 徽标），且弹簧幅度不超过 1.05。

**不要手写 `linear()` 的点列** —— 手工算弹簧采样点极易出错（MDN 明说百分比必须升序、至少两个参数）。用生成器，或直接抄上面这条已验证的值。

### 4.3 「不花哨」的量化标准：哪些有权威依据，哪些是经验值

#### 有权威依据的部分

| 维度 | 有据可查的约束 | 来源 |
|---|---|---|
| 闪烁频率 | **≤ 3 次/秒**（超过即违规） | 【官方规范】WCAG SC 2.3.1 原文 |
| 自动播放长度 | 自动开始且**超过 5 秒**的移动/滚动信息，必须提供暂停/停止/隐藏 | 【官方规范】WCAG SC 2.2.2 原文 |
| 持续振荡频率 | **避免约 0.2 Hz 的持续振荡** | 【官方文档】Apple HIG 原文（visionOS 段） |
| 高频交互 | **"generally avoid adding motion to UI interactions that occur frequently"** | 【官方文档】Apple HIG 原文 |
| 不能只靠动效传达信息 | "avoid using it as the only way to communicate important information" | 【官方文档】Apple HIG 原文 |
| 动效必须可关闭 | 交互触发的非必要动画必须可禁用 | 【官方规范】WCAG SC 2.3.3 + 技术 C39/SCR40/Gx |
| 时长下限锚点 | Carbon 官方称 **150ms 为 "Default transition speed"** | 【官方源码】Carbon `dtcg/motion.json` |
| 时长上限锚点 | M3 微反馈档最高 **200ms**（`short4`），`medium4 = 400ms`；Carbon "expansion/toast" 档 **240ms** | 【官方源码】M3 / Carbon token |

#### 没有权威依据的部分（=经验值，请按工程判断使用）

我**没有找到**任何规范或官方设计系统给出「动效时长上限」「位移上限」「同时动起来的元素个数上限」这三个数字。以下**明确标注为本报告的经验建议**：

| 经验指标 | 建议值 | 说明为什么是这个数（非引用规范） |
|---|---|---|
| 微反馈时长上限 | **300ms** | M3 微反馈档到 `short4 = 200ms`，`medium`（250–400ms）官方描述用于 "expansion"。300ms 是两者之间的保守上限。 |
| 页面级过渡时长上限 | **400ms** | M3 `medium4 = 400ms` 是"大范围展开"的量级；超过它用户会感觉在等。Astro 内置 `fade` 用 180ms，可作下限参考。（区间端点抄自 M3） |
| 入场位移上限 | **12px**（推荐 8px） | 依据 Apple HIG "keep amplitude low" + MDN 对"大幅 scale/pan"的前庭警告，取明显小于正文行高的量。 |
| 缩放上限 | **1.02**（绝对上限 1.05） | MDN 明确点名大对象缩放是前庭触发源，只能取"几乎不可察觉"的量。（约束来自规范定性描述） |
| 同时动起来的元素个数上限 | **1 个区块 / 一批 ≤ 6 个且不 stagger；stagger 间隔 ≤ 40ms** | 无权威依据。经验判断：视口内多个独立动画竞争注意力 = 花哨；"瀑布"式错开是典型花哨特征。 |
| 时长下限 | **100ms**（微反馈建议 ≥ 150ms） | 低于 100ms 会被感知为"瞬跳"；150ms 有 Carbon 官方背书。 |
| 循环/无限动画 | **页面上最多 0~1 处，且必须可暂停** | 约束来自 SC 2.2.2；数量上限是经验值。 |

#### 一句话的"不花哨"判据（工程判据，非规范）

> **用户能说出"这一下让我更确定自己点到了什么"，但说不出"刚才是什么动画" —— 就对了。**
> 反之，如果用户注意到"这里有个动画"，那它大概率已经越界。

两个可执行自检：

1. **减半测试**：把位移/缩放/时长各自减半，如果页面"看起来没什么变化"，说明原值里超过一半是装饰，取减半后的值。
2. **关闭测试**：DevTools 里给 `*{transition:none!important;animation:none!important}` 跑一遍。如果觉得"少了什么"，那正是唯一该保留的一处；如果觉得"清爽多了"，说明做多了。

## 5. D. 真实站点怎么做的

方法：用 `web_fetch` 抓页面 → 解析 `<link rel="stylesheet">` 与内联 `<style>` → 逐个抓 CSS → 提取 `transition`/`animation` 声明与 `prefers-reduced-motion` 块。以下数值都是**从这些站点的实际 CSS 文件里抓出来的**。

### 5.1 The Pudding — `https://pudding.cool/`

**证据文件**：`https://pudding.cool/_app/immutable/assets/0.C2Vp5USR.css`（26,423 字节，站点主 CSS）

**发现 1：一套语义化的过渡 token**

```css
--transition-fast: .1s;
--transition-medium: .2s;
--transition-slow: .5s;
--transition-ease: ease-in;
```

**发现 2（最有价值）：用「变量是否存在」实现 reduce 门控**

```css
@media screen and (prefers-reduced-motion: no-preference){:root{--1s: 1s}}
```

然后全站过渡写成：

```css
transition: transform calc(var(--1s) * .25);
transition: transform calc(var(--1s) * .25),-webkit-transform calc(var(--1s) * .25);
transition: left calc(var(--1s) * .25);
```

**机理**：`--1s` **只在 `no-preference` 时被定义为 1s**。reduce 用户下 `--1s` 未定义 → `calc(var(--1s) * .25)` 在计算值阶段无效 → 该声明失效 → **过渡不存在**。这是"静态为默认"策略的一个**真实生产级先例**，而且是数据新闻站点（与我们的定位最接近）。

**发现 3：只 transition `transform` / `left`**，没有 `transition: all`，也没有 `box-shadow`。

**发现 4：reduce 块数量为 1** —— 一致性完全靠 `--1s` 这一个变量实现，非常省心。

### 5.2 Maggie Appleton — `https://maggieappleton.com/`

**证据文件**：内联 `<style>`（12,522 字节）、`https://maggieappleton.com/_astro/_slug_.CkZwsBbD.css`（13,555 字节）、`_slug_.rSj0_u2z.css`（14,528 字节）

**发现 1：原生跨文档过渡 + 自己写的 reduce 覆盖**

```css
@media (prefers-reduced-motion: reduce){
  ::view-transition-group(*),::view-transition-old(*),::view-transition-new(*){animation:none!important}
}
```

注意：**这正是 §1.4 里 Astro 文档承诺、但本项目产物缺失的那条规则**。她也得自己写。

**发现 2：全局 reduce 重置**

```css
@media (prefers-reduced-motion: reduce){
  html:focus-within{scroll-behavior:auto}
  *,*:before,*:after{
    animation-duration:.01ms!important;
    animation-iteration-count:1!important;
    transition-duration:.01ms!important;
    scroll-behavior:auto!important
  }
}
```

**发现 3：进场动画的完整参数（对标 §3.3）**

```css
@media (prefers-reduced-motion: no-preference){
  .cascade,.cascade-fade{
    animation-duration:.26s;
    animation-timing-function:cubic-bezier(.23,1,.32,1);
    animation-fill-mode:backwards;
    animation-delay:calc(.1s + var(--cascade, 0) * 45ms)
  }
}
```

-> 进场 **260ms**、缓动 `cubic-bezier(.23,1,.32,1)`（强 decelerate）、**stagger 间隔 45ms**。这与 §4.3 给的经验值（stagger ≤ 40ms）几乎一致，可视为该经验值的实证支撑。

**发现 4：卡片 hover 的组合（直接对标我们的 Card）**

```css
transition: transform var(--dur-base) var(--ease-spring),
            box-shadow var(--dur-quick) var(--ease-hover),
            opacity var(--dur-quick) var(--ease-hover);
```

-> **位移用较慢的 `--dur-base` + 弹簧曲线；阴影/透明度用较快的 `--dur-quick` + 平滑曲线**。这是"分离节奏"的成熟做法（几何变慢、颜色变快），值得借鉴：我们的卡片也可以让 `translate` 走 200ms、`box-shadow` 走 150ms。

**发现 5：hover 三重门**

```css
@media (hover: hover) and (pointer: fine) and (prefers-reduced-motion: no-preference){ ... }
```

三个条件一起用：**只有在精确指针设备 + 允许动效时才启用 hover 动效**。比单一 `hover:` 更严格，值得学。

### 5.3 Astro 官网 — `https://astro.build/`

**证据文件**：内联 `<style>`（4,217 字节）、`https://astro.build/_astro/tailwind.QfH26gv7.css`

**发现 1：Tailwind 站点，全部动效都在 motion-safe 里**

内联样式里两个 `no-preference` 块包住了所有 CSS 动画；Tailwind 产物里也有 `motion-safe:` 对应的媒体查询包裹。**这印证了"用 Tailwind 就把动效全写进 motion-safe:"是一个被官方站点自己采用的模式**（本项目也是 Tailwind v4）。

**发现 2：时间刻度与缓动**

```css
transition-duration: .3s;   transition-timing-function: cubic-bezier(0,0,.2,1)
transition-duration: .15s;  transition-timing-function: cubic-bezier(.4,0,.2,1)
transition: opacity .4s cubic-bezier(.23,1,.32,1)
```

-> `.15s` + `cubic-bezier(.4,0,.2,1)`（= M3 `easing-legacy`，也是 Tailwind 的 `--ease-in-out`）、`.3s` + `cubic-bezier(0,0,.2,1)`（= M3 `easing-standard-decelerate`，也等于 Tailwind `--ease-out`）。**与我们打算用的完全同源**。

**发现 3：有 marquee 动画，但默认 `paused`**

```css
animation: 50s linear infinite paused marquee;
```

-> 装饰性跑马灯**初始就是 paused**，只在 `:hover`/`:has(:focus-visible)`/`.in-viewport` 时才 `animation-play-state:running`。这是在 SC 2.2.2（自动播放 > 5s 需可暂停）上的**优雅合规做法**：默认不动，就不构成"自动播放"。

### 5.4 Josh Comeau — `https://www.joshwcomeau.com/`

**证据文件**：内联 `<style>`（6,455 字节）、`_next/static/css/7536305590e24225.css`（33,976 字节，**14 个 reduce 块**）、`8e8c255c1ff7ea73.css`（20,098 字节，8 个 reduce 块）

**发现 1：默认过渡 token**

```css
--sp-transitions-default:150ms ease;
```

-> **150ms + `ease`**。又一个"150ms 作为默认"的独立佐证（与 Carbon 的 "Default transition speed" 一致）。

**发现 2：reduce 门控极其彻底（14 个块）**，形态统一：

```css
@media (prefers-reduced-motion:no-preference){.sq4k8cp{transition:transform .3s}}
@media (prefers-reduced-motion:no-preference){.w1azqaf0{transition:opacity .2s}}
@media (prefers-reduced-motion:no-preference){.s2orcac{animation:clipIn-s2orcac 1.5s cubic-bezier(.31,0,.17,1.01) both;animation-delay:.75s}}
```

-> **每条动效单独用 `no-preference` 包住**，而不是"全局隐藏 + JS 显示"。这与 §3.3 推荐的写法同源。

**发现 3：动画大都只动 `opacity` / `transform`**，典型值：

```css
transition: transform .3s cubic-bezier(.06,.63,.43,1), opacity .3s;
transition: box-shadow .2s;
transition: stroke .25s;
animation: fadeIn .4s both;
```

**发现 4：用 CSS 自定义属性做过形状过渡**（进阶，本项目不必用）：

```css
transition: --color-background .4s;
```

-> 需要 `@property` 注册才能插值。**不建议本项目引入**（复杂度高、收益低）。

### 5.5 反面对照：Visual Cinnamon — `https://www.visualcinnamon.com/`

**证据文件**：`https://www.visualcinnamon.com/scss/main.min.css`（9,644 字节）、`home.min.css`（13,787 字节）

数据可视化领域公认的好站点，但动效工程**明显比上面四家粗**，正好用来标定"不该抄什么"：

```css
main.min.css: transition: all .15s ease;
              transition: background-color .2s linear;
              transition: all .2s linear;
home.min.css: transition: all .5s ease;
              transition: background-color .3s ease;
```

三个问题：

1. **`transition: all`** —— 会顺带过渡所有可动画属性，是不可预测性的来源。
2. **`prefers-reduced-motion` 块数量为 0** —— 两个 CSS 文件里一个 reduce 块都没有。
3. **`.5s` 偏慢** —— 超过 M3 的 `medium4 = 400ms`。

另一个事实：它的 HTML 里引了 `https://use.typekit.net/ibl0oid.css`（Adobe Fonts CDN）—— **这恰好违反本项目的硬约束 1（零第三方运行时请求）**，所以它连"字体策略"都不能照抄。

**它仍值得看的是版式与图表设计**，不是动效实现。

### 5.6 五个站点的汇总对照

| 站点 | 微反馈时长 | 进场时长 | 缓动 | reduce 门控形态 | 对我们的取舍 |
|---|---|---|---|---|---|
| **The Pudding** | `.1s` / `.2s` | — | `ease-in`（`--transition-ease`） | **变量缺失法**：`@media (no-preference){:root{--1s:1s}}` | **强烈推荐抄**（§3.3 思路一致，实现更省） |
| **Maggie Appleton** | `--dur-quick` / `--dur-base` 分离 | `.26s`，delay `.1s + n*45ms` | `cubic-bezier(.23,1,.32,1)` | 全局 `.01ms` 重置 + 逐条 `no-preference` + 自写 `::view-transition-*` 关停 | 抄 `::view-transition` 那条（§3.4.2）+ "几何慢/颜色快"的分离节奏 |
| **Astro 官网** | `.15s` | `.3s` / `.4s` | `cubic-bezier(.4,0,.2,1)`、`cubic-bezier(0,0,.2,1)` | 全部走 Tailwind `motion-safe:` | **和我们技术栈一致，直接对标** |
| **Josh Comeau** | `.2s`–`.3s` | `.4s`，默认 token `150ms ease` | 多条自定义 bezier | 逐条 `no-preference`（14 个块） | 抄"逐条包裹"的彻底程度 |
| **Visual Cinnamon**（反例） | `.15s`–`.5s` | — | `ease` / `linear` | **0 个 reduce 块**；用 `transition: all`；用 Typekit CDN | **不要抄它的动效与字体** |

## 7. 未核实清单（请勿在实施方案里当成已知事实）

1. **Chrome / Safari 是否已实现 CSSWG 2024-09-24 的决议**（reduce 时 UA 用纯交叉淡入淡出而非完全不动）—— 无法在本环境切换系统偏好实测。**注意：这不影响 §3.4.2 的结论** —— 父 agent 的实测已证明 Astro 在 reduce 下**仍然调用** `startViewTransition`（见 §1.4），所以动画是否播放**完全取决于 UA**，我们不能假设它一定会关掉。
2. **UA 默认 `::view-transition-*` 交叉淡入淡出的时长数值** —— Chromium 的 `html.css` 抓取失败，本文不给数字。
3. **`translate` 独立属性是否为 `position: fixed` 后代创建包含块** —— MDN `translate` 页只写 `Creates stacking context: yes`，没写包含块。按"加了就测"处理。
4. **`transform`/`translate` 明确不计入 CLS 的一手规范明文** —— 只找到工程共识，未找到条款。（但父 agent 的移动端实测给出 CLS = 0、零条 layout-shift，见 §1.4，是实测层面的支撑。）
5. **`text-wrap: balance` 的行数上限**（常见说法是少数行）—— 未找到一手明文。
6. **`scrollama\@3.2.0` 的 `destroy()` 确切 API 名** —— §3.4.4 给的是示意，落地前请查该版本的 `index.d.ts`。
7. **Vercel 对本站 HTML 的 `Cache-Control` 实际值** —— 决定 astro#10907 的重复下载在本站是否真的发生。建议用 DevTools Network 面板 hover 一个链接、再点击，看是否有两次请求。
8. **maggieappleton.com 那条注释的因果是否成立** —— 见 §3.4.3(b)：注释原文已核实，但"Astro prefetch 阻止跨文档 View Transitions"这个因果**未找到任何一手来源**，且 MDN 列出的触发条件不含 prefetch。
9. **Lighthouse `non-composited-animations` 的可合成属性白名单** —— 我核实了该审计存在（唯一相关项）、是 diagnostic，但没抓到 Chrome 文档的属性清单（`developer.chrome.com` 在本环境抓取失败）。
10. **第 4.3 节表格里标注为"经验值"的全部数字** —— 无权威依据，是我的工程建议。

- 上一轮"没能核实到 `prefers-reduced-motion` 权威来源"：本轮找到了 —— **WCAG 技术 C39**（官方充分技术）、**CSS MQ Level 5 §12.1**、以及 **CSSWG 关于 view transitions 与 reduce 的正式决议**。同时**实测出**本项目线上产物缺少 Astro 文档承诺的那条 reduce 闸门（§1.4），并用真实浏览器探针确认 Astro 在 reduce 下**仍然调用** `startViewTransition`。

- 上一轮"怕花哨"：本轮把"花哨"拆成可执行判据（§4.3），并把所有数值锚定到 M3 / Carbon / 真实站点；只有标注为经验值的部分允许自由裁量。
