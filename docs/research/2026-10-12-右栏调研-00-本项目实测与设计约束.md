## 1. 问题量化：右侧空白是结构性的，不是视口问题

方法：`astro preview` + Playwright，在四个视口下量 `main.app-layout` 与 `#article` 的 `getBoundingClientRect()`。被测页 `/case-studies/student-union-platform/`。

| 视口宽 | `main.app-layout` 宽 | 正文列 `#article` 宽 | **右侧空白** | 占容器 |
|---|---|---|---|---|
| 1280 | 1120 | 638 | **466** | 42% |
| 1440 | 1120 | 638 | **466** | 42% |
| 1600 | 1120 | 638 | **466** | 42% |
| 1920 | 1120 | 638 | **466** | 42% |

**结论：空白恒为 466px、恒定占容器 42%，不随视口变化。** 成因是模板本身：`main` 是 `max-w-app`（1120px）容器，正文被 `max-w-readable`（68ch）锁死在 638px 且左对齐。

### 1.1 「把正文加宽」为什么救不了这 466px

- 字号 16px，中文全角字宽 = 16px → 638 ÷ 16 = **每行 39.9 个汉字**（实测 `cjkCharsPerLine: 39.9`）。
- 拉丁文的舒适行长经验值（45~75 字符）**不能直接外推**到中文，依据见 04 篇。
- 即便加宽到容器上限，也只能吃掉一部分空白，且会开始伤阅读。**466px 必须靠新增内容去填。**

### 1.2 只有详情页有这个问题

首页与四个列表页的主体是满宽栅格（卡片 / hero 12 栏），不涉及本问题。四个详情页模板全部使用 `app-prose max-w-readable`：

- `src/pages/case-studies/[slug]/index.astro:113`
- `src/pages/analysis/[slug]/index.astro:92`
- `src/pages/dissections/[slug]/index.astro:111`
- `src/pages/toolbox/reports/[slug]/index.astro:75`

## 2. 关键 API 证据：目录栏几乎是免费的

### 2.1 Astro 的 render() 直接返回 headings

【官方源码】`site/node_modules/astro/dist/content/runtime.d.ts:72-76`：

```ts
type RenderResult = {
    Content: AstroComponentFactory;
    headings: MarkdownHeading[];
    remarkPluginFrontmatter: Record<string, any>;
};
```

【官方源码】`site/node_modules/@astrojs/internal-helpers/dist/markdown.d.ts:29-33`：

```ts
export interface MarkdownHeading {
    depth: number;
    slug: string;
    text: string;
}
```

→ 所以四个详情页只要把 `const { Content } = await render(entry)` 改成
`const { Content, headings } = await render(entry)` **即可拿到目录，零新依赖、零 Markdown 管线改动**。

### 2.2 标题 id 已经存在，且 slug 与 id 同源

【官方源码】`site/node_modules/@astrojs/markdown-remark/dist/rehype-collect-headings.js`：

- L1：`import Slugger from "github-slugger"`
- L6：`function rehypeHeadingIds()`
- L12-16：遍历**所有** h1~h6
- L50-53：

```js
node.properties = node.properties || {};
if (typeof node.properties.id !== "string") {
  node.properties.id = slugger.slug(text);
}
```

- L54：`headings.push({ depth, slug: node.properties.id, text })`

两个可直接依赖的推论：

1. **slug 就是 DOM 上的 id**（同一个变量），所以 `href={"#" + h.slug}` 必然命中，不需要二次计算。
2. 作者若在 Markdown 里手写了 `id`，会被尊重（L51 的 `typeof !== "string"` 判断）。

产物实证（`dist/case-studies/student-union-platform/index.html`）：

```html
<h2 id="一背景与问题">一、背景与问题</h2>
<h2 id="二我的角色">二、我的角色</h2>
<h2 id="三过程与关键取舍">三、过程与关键取舍</h2>
<h2 id="四结果与量化">四、结果与量化</h2>
<h2 id="五复盘与反思">五、复盘与反思</h2>
```

### 2.3 目录长度实测（dist 产物统计）

| 页面 | h2 | h3 | 最长标题字数 |
|---|---|---|---|
| case-studies / 5 篇 | 5 | 0 | 9 |
| analysis / 2 篇 | 5 | 0 | 9~15 |

## 3. position: sticky 可行性：已在真实页面上验证通过

这是整个方案的**技术前提**，所以先验证再设计。方法：在真实预览页里用 `page.evaluate` 把目标结构（`display:grid; grid-template-columns:minmax(0,1fr) 20rem; gap:3rem; align-items:start` + `position:sticky; top:6rem`）`prepend` 进 `main.app-layout`，祖先链与将来的真实结构完全一致，然后滚动测量。

结果（视口 1440×900）：

| 测量项 | 结果 |
|---|---|
| `document.scrollingElement` | `html` |
| `html` 的 `overflow-y` | `scroll`（滚动条槽位） |
| `body` 的 `overflow-y` | `visible` |
| 正文到 `html` 之间「overflow 非 visible」的祖先 | **0 个** |
| 滚动中 aside 的 `rect.top` | **96px（= 6rem，精确贴住）** |
| `stickyHolds` | **true** |
| 滚过容器末尾时 | `-300px`（= 被容器正确推走，符合预期） |

**结论：sticky 在这条祖先链上工作正常。**

一个必须记住的坑：`html` 上的 `overflow-y-scroll` **不会**破坏 sticky，因为它按规范传播到 viewport；但同样的声明若写在 `body` 上就会坏。当前站点是安全的那一种，**将来不要把这条挪到 `body`**。

### 3.1 栅格算术（1440 视口实测）

```
容器 main.app-layout      1120px（含 px-4 = 16px×2 内边距）
容器内容盒                1088px
grid: minmax(0,1fr) 20rem + gap 3rem
  → 左列实测             720px
  → 右栏实测             320px
  → 间距                  48px
  → 合计                1088px  ✓ 正好等于内容盒，无横向溢出
```

### 3.2 另一个必须记住的坑：scroll-behavior: smooth

`html` 上有 `scroll-behavior: smooth`（`src/styles/global.css:86-90`，包在 `prefers-reduced-motion: no-preference` 里）。
**后果：`window.scrollTo(0, y)` 会变成动画**，写验收脚本时同步读 `scrollY` 会读到 0（我第一次探测就踩了这个，误判 sticky 失效）。
→ 所有验收脚本必须用 `window.scrollTo({ top: y, behavior: "instant" })` 并等两帧 `requestAnimationFrame`。

## 5. 门禁约束（新组件必须满足）

| 门禁 | 约束原文/口径 | 对本设计的约束 |
|---|---|---|
| `check-headings.mjs` | L29 `/<h([1-6])[\s>]/g` 统计**所有** h1~h6；L31 要求恰好 1 个 h1；L33-36 检查**层级不跳级** | **目录组件里禁止出现任何 h1~h6 标签**（栏标题必须用 `<p>`/`<span>`），否则会污染统计甚至触发跳级 |
| `check-links.mjs` | L7 `SKIP = /^(https?:|mailto:|tel:|data:|#|javascript:)/` | **`href="#..."` 被整个跳过，不会被校验** —— 也就是说目录锚点错了**现有门禁抓不到**。→ 需要新增一条门禁 |
| `check-case-studies.mjs` / `check-dissections.mjs` / `check-ld.mjs` / `check-og.mjs` / `check-home-metrics.mjs` | 各自口径 | 与右栏无直接冲突 |

**建议新增门禁 `check-toc.mjs`**：对每个含目录的产物页，断言「目录里每个 `href="#X"` 都能在**同一页**找到 `id="X"`」。理由：这正是现有门禁的盲区，而改 Markdown 标题是**高频操作**，手工维护目录必然漂移。

## 8. 设计红线（本次改动不得违反）

1. **移动端（<1024px）逐像素不变**：不加宽、不换行、不新增可见元素、不改动线顺序。
2. **CLS = 0**：右栏与目录的出现不得造成任何布局位移（sticky 不产生位移；动效只许用 opacity/transform）。
3. **每页恰好一个 h1，且不得新增任何标题元素。**
4. **零第三方运行时请求**；不新增运行时依赖（headings 来自 Astro 自带）。
5. **移动端 Lighthouse ≥ 90 不降**：目录脚本在 <1024px 时**不得注册任何观察器**。
6. **暖色、克制、不花哨。**
7. **不编造数据**：右栏出现的每个数字都必须来自 frontmatter 或可机械核对的产物。

## 9. 工具链脚注（本次调研踩到的两个环境坑）

1. **write 工具无法直接写 E: 盘**：E: 是 exFAT，不支持硬链接，`write` 的原子写入（先建临时目录再 link）会报
   `EISDIR: illegal operation on a directory, link '...<name>.tmpdir\<name>.tmp' -> '...<name>'`。
   同一目录下换任何文件名都一样失败，写 C: 则正常。
   **变通**：先 `write` 到 `C:\dev\pm-forge\_staging-*.md`，再 `Copy-Item -LiteralPath ... -Force` 到 E:（已实测字节一致、UTF-8 不变）。
   不要用 PowerShell 的 `Set-Content` 写中文（会变 GBK 乱码）。
2. **Playwright 借装路径**：`C:\dev\pm-forge\toolkit\node_modules\playwright\index.mjs`。
   Astro 7 的 `preview` 是**全局单槽守护进程**，脚本开头必须先 `npx astro preview stop` 清槽；多个预览脚本**不能并发**。
