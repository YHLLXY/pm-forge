## 2. hover 预取：**线上确实在发**（与代码推断一致）

做法：加载首页 → 记录请求数 → `hover` 第一个站内链接 → 再记录。

```json
{
  "hovered": "/interviewers/",
  "requestsBeforeHover": 3,
  "requestsAfterHover": ["other https://www.yuhailinlxy.com/interviewers/"],
  "prefetchLinkTags": ["https://www.yuhailinlxy.com/interviewers/"]
}
```

**结论**：鼠标划过站内链接后，DOM 里**新增了一个 `<link rel="prefetch">`**，并产生了对应的网络请求。

这与源码推断链完全吻合：
`astro.config.ts` 无 `prefetch` 键 → `astro/dist/transitions/vite-plugin-transitions.js:54` 判定 `prefetchDisabled = false` → `astro/components/ClientRouter.astro:151-152` 执行 `init({ prefetchAll: true })` → 官方类型注释 `astro/dist/types/public/config.d.ts:1904`「Enabled by default on pages using the `<ClientRouter />` router」。

**对二期的意义**：站点当前**并非**「零额外请求」。hover 就发同源预取请求。这不违反「零第三方请求」红线（全部同源），但写方案时不能再宣称"没有任何交互触发的请求"。

## 3. View Transitions 与 `prefers-reduced-motion`：**Astro 不会跳过 `startViewTransition`**

同一探针跑两次（唯一变量是上下文的 `reducedMotion`），在页面里先 monkey-patch `document.startViewTransition` 计数，然后点击 `a[href="/case-studies/"]`：

| 变量 | `no-preference` | `reduce` |
|---|---|---|
| `meta[name=astro-view-transitions-enabled]` | `"true"` | `"true"` |
| `meta[name=astro-view-transitions-fallback]` | `"animate"` | `"animate"` |
| `typeof document.startViewTransition` | `"function"` | `"function"` |
| `matchMedia("(prefers-reduced-motion: reduce)").matches` | `false` | `true` |
| 点击后 `startViewTransition` 调用次数 | **1** | **1** |
| 点击后 `location.pathname` | `/case-studies/` | `/case-studies/` |
| `performance.getEntriesByType("navigation").length` | **1** | **1** |
| 新页面内封面 SVG 数 | 10 | 10 |

**三条结论**：

1. **软导航确实在工作**：`navigation` 条目数保持 1（没有整页重载），URL 变了，新页面的 DOM（10 张封面）正常渲染。
2. **那个我先前在 `dist/index.html` 里 grep 不到的两个 meta，实际是存在的**（`enabled=true`、`fallback=animate`）。此前"未核实"的判断作废：**以浏览器实测为准**。
3. **关键**：即使 `prefers-reduced-motion: reduce`，Astro **照旧调用** `document.startViewTransition`。
   Astro 源码里那句 DEV 警告（`ClientRouter.astro:57-61`）说的是"动画会被禁用"，指的是**浏览器按用户偏好跳过动画播放**，而不是不调用 API——这与我测到的一致。
   → **推论（必须实施时复测）**：默认的浏览器原生 cross-fade 会由 UA 按用户偏好处理；**但一旦我们加上自定义的 `transition:animate`，就不能默认 UA 还会帮我们关掉它**。届时必须：
   - 用同一探针在 `reducedMotion: "reduce"` 下复测；
   - 并给自定义动效显式加 `@media (prefers-reduced-motion: reduce) { animation: none; transition: none; }` 兜底。

## 6. pagefind 搜索在软导航之后**仍然可用**（排除了一个风险）

担心：`<ClientRouter />` 接管站内跳转后，`/search/` 页的 pagefind 初始化脚本可能不再执行（Astro 换页时只重跑带 `data-astro-rerun` 的脚本）。

做法：分别在「硬加载 `/search/`」与「从首页点击搜索链接软导航到 `/search/`」两种情况下，向搜索框输入「案例」，然后记录 pagefind 相关请求。

| 场景 | 输入后 pagefind 请求 | 说明 |
|---|---|---|
| 硬加载 `/search/` | `pagefind.js` / `pagefind-worker.js` / `pagefind-entry.json` / `pf_meta` / `wasm.unknown.pagefind` / `index/zh_*.pf_index` = **6 个** | 正常加载索引 |
| 软导航到 `/search/` | 同样的 6 个 **+ 16 个 `fragment/zh_*.pf_fragment` = 22 个** | **不仅可用，而且真的检索出了结果** |

两种场景下 `pageerror` 均为 **0 条**，`performance.getEntriesByType("navigation").length` 保持 1（软导航未整页重载）。

**结论**：**搜索没有被 View Transitions 破坏**，issue 里常见的"换页后搜索失效"在本站不存在。这是 C 轨（微动效）可以少担心的一个风险点。
**顺带记一条行为特征**：pagefind 是**懒加载**的——在 `/search/` 页面加载完成时它**不发任何请求**（`window.pagefind` 仍是 `undefined`），**直到用户第一次输入才拉取**。所以"打开搜索页没看到网络请求"是正常的，不是 bug。

## 8. 【P0 bug 复现】第二次站内跳转进 `/search/`，输入框静默失效（2026-10-09 线上实测）

做法：Playwright → 打开首页 → 点击搜索链接（软导航）→ 在搜索框输入「案例」→ 返回首页 → **再次**点击搜索链接 → 再输入「案例」。全程记录 pagefind 请求。

| | 第一次进 `/search/` | 第二次进 `/search/` |
|---|---|---|
| 输入框能否输入 | 能（`input.value` = `案例`） | 能（`input.value` = `案例`） |
| pagefind 请求总数 | **22** | **0** |
| 其中 `fragment/zh_*.pf_fragment` | **16** | 0 |
| 其中 `index/zh_*.pf_index` | 1 | 0 |
| `pageerror` | 0 | 0 |

**结论**：输入框外观完全正常、也能打字，**但一个字都搜不出来，且控制台没有任何报错**——典型的"静默失效"。

**成因**（`astro@7.3.5` 源码 + 官方文档）：
- 官方文档《View transitions》"Script re-execution" 原文：`Bundled module scripts, which are the default scripts in Astro, are only ever executed once.`
- `astro/dist/transitions/swap-functions.js:29-45` 的 `detectScriptExecuted()`：**有 `src` 的用 URL 做去重键，内联的用 `textContent`**；`deselectScripts()` 给跑过的脚本打 `data-astro-exec=""`。
- `astro/dist/transitions/router.js:82-98` 的 `runScripts()` 跳过带该属性的脚本。
- `site/src/pages/search.astro:35-122` 的初始化逻辑**全写在模块顶层**（顶层取 `#search-input` / `#search-status` / `#search-results`，然后挂 `input` 监听）→ 第二次进入时脚本被跳过，新 DOM 上**没有任何监听**，而模块里的旧引用指向已被替换掉的节点。

**同一机制影响数据故事页**：`site/src/pages/data-stories/userbehavior.astro:186-284` 同样是顶层写法（其脚本在产物里是 hoisted `src` 模块，走 URL 去重路径）。二次进入后 `IntersectionObserver`、`scrollama`、`#q-run` 的 click 监听全部缺失 → 图表不渲染、查询按钮点了没反应。**注意 DuckDB-WASM 本身没有坏，坏的是触发它的监听。**
