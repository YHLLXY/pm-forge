# 2026-10-09 调研：详情页版头（article header）与首页 hero「证据面板」

> **调研对象**：pm-forge 作品集站（Astro 7 + Tailwind v4，纯静态 SSG，Vercel，https://www.yuhailinlxy.com/ ）。
> **要解决的问题**：① 列表页有数据封面卡，详情页（case-studies / analysis / dissections / toolbox/reports 的 `[slug]`）开头仍是纯文字，视觉断层；② 首页 hero 左对齐大标题 + 一段说明，右侧到 1120px 版心是空的。
> **硬约束**（本文件所有建议都按此校验）：零第三方运行时请求（字体自托管、无 CDN、插画优先内联 SVG）；Lighthouse 移动端四类 ≥ 90；纯静态构建；暖色 / 克制的数据新闻编辑部气质；无障碍不得破坏（prefers-reduced-motion、对比度、标题层级）；内容以中文为主。

## 0. 调研方法与可信度标注

沿用同目录已有文档 `docs/research/2026-10-09-视觉美化外部调研-原始素材.md` 的约定：

- **【实测】**= 我用 web_fetch 真的打开并读取了该 URL 的内容，结论基于抓到的 HTML / CSS 原文。
- **【源码实测】**= 我直接读取了本仓库 `C:\dev\pm-forge` 里的源文件或依赖包源码。
- **【API 实测】**= 通过 `api.github.com/repos/.../contents/...` 取到了仓库内文件的**正文**（不是网页壳）。这一层证据比"网页 200"强，因为拿到的是文件字节。
- **【搜索】**= 仅来自搜索结果标题/摘要，**未打开正文**，可信度低。
- **【失败】**= 尝试打开但失败（DNS / 超时 / 反爬 / 页面要求 JS），**不代表该资源不存在**。

- **【判断】**= 我个人的工程/设计推断，与来源事实严格分开。

**读出来的设计决策（【判断】但依据充分）**：

- **页壳 1200px / 标题栏 608px / 正文栏 620px**。"宽版头"其实是"**页壳宽、文字栏窄**"，不是"标题横跨整页"。608 与 620 几乎同宽，标题栏只比正文栏窄 12px —— 这个 12px 正好是那层点阵装饰（`width:calc(100% - 12px)` + `left:-6px`）的出血量。
- 层次只有三级：**kicker（栏目）→ h1 → subhead（含作者）**；日期另起一行、字号与 subhead 同级（16px）、颜色降级（#66615b）。
- 视觉"杂志感"来自三样东西，都不贵：衬线标题（ivar-display）与无衬线副文（messina）的**字体对撞**、点阵纹理、插画。**没有渐变、没有玻璃、没有阴影**。
- 同一张插画通过 `<picture>` 输出 841×473（≥491px）/ 750×422（<490px），而 og:image 是 **1200×628** —— **同一素材多裁切**，即"列表卡片 / 详情头图 / 社交图"三用一张资产。

`https://ourworldindata.org/2026-lpi-update` 的版头原文（精简）：

```html
<article class="centered-article-container grid grid-cols-12-full-width centered-article-container--article">

    <div class="centered-article-header__title-container col-start-2 span-cols-6 span-md-cols-6 col-md-start-1">
      <h1 class="centered-article-header__title">A 73% average decline in wildlife populations: …</h1>

      </div>
    </div>
  </header>
  <p class="article-block__text col-start-5 …">
```

**可核验的结构事实**：

- 全页是 **12 栏**网格；版头占 **col 4–11（span 8）**，内部再开一个 **8 栏**网格，标题/副标题/meta 都占内部 col 2–7（span 6）→ **版头文字栏 ≈ 页面宽度的 6/12 = 50%**。
- **正文 `col-start-5`** → 正文栏比版头栏更窄，且左右不对称。这就是"宽版头 + 窄正文"的真实实现：**不写死 px，而是在同一个网格里用不同的 col-start/span**。
- 版头有独立的 **`centered-article-header__banner`** 空槽位（本文为空）→ 站点层面预留了"版头可以有一条 banner"的变体。
- 副标题是 **`<h2>`**，不是 `<p class="deck">`。这一点对本项目有直接影响：**加 deck 用 h2 会改变标题层级**（见 §1.3），OWID 的做法是 h2，但那会让文档大纲里出现两个顶部标题。

#### 1.2.5 Information is Beautiful【实测】

`/visualizations/worlds-biggest-data-breaches-hacks/` 页面头部只有 h1 与分享计数（"Share this: Facebook 7,592 …"），CSS 来自 `https://infobeautiful4.s3.amazonaws.com/www/dist/style.min.css`（字体 IBM Plex Sans）。它的 h1 命中的是 UA 默认规则 `h1{font-size:2em;margin:.67em 0}`，说明**它的视觉重量 100% 来自那张巨型可视化图**，而不是排版。

### 1.3 版头元素清单：必要 / 可选 / 装饰

| 元素 | 判定 | 证据 | 对本项目的具体建议 |
|---|---|---|---|
| **kicker / 栏目名** | **必要** | The Markup 用 `<p class="article-type">` + 栏目色链接（"Privacy"）；我们的卡片已用 `--section-*` 色标板块 | 直接复用 `Card.astro` 里的 `sectionLabel` 映射与 `style="color:var(--section-…)"` |
| **H1 标题** | **必要** | 5 个可核验站点都有唯一 h1 | 保持每页唯一 h1；详情页 h1 = 文章标题 |
| **副标题 / deck** | **可选但推荐** | The Markup 有 `.article-subhead` 且**把作者并进同一个 `<p>`**；OWID 用 `<h2 class="centered-article-header__subtitle">`；Pudding **没有** deck | 每个 collection 都已有 `description` 字段（源码实测 `content.config.ts`），**直接当 deck 用，不要新增 schema**；用 `<p>` 而非 h2，避免多出一个顶级标题 |
| **作者 / 署名** | **不适用（单人作品集）** | The Markup/Pudding/Nightingale/OWID 都有 byline | 用等价的"角色/身份"替代：case-studies 已有 `projectRole`，dissections 已有 `productName`/`depth`/`evalWindow`。**不要为了像新闻站而硬加作者名** |
| **日期** | **必要** | 5 站全部有 `<time datetime>`；Nightingale 另给 updated | 复用 `Datetime.astro`（内含 `<time datetime={iso}>` 与 modified 逻辑；源码实测）。放 meta 行，不要放在 h1 上方 |
| **阅读时长** | **装饰 / 可以不做** | 我核验的 5 个站点**没有任何一个**在版头显示阅读时长 | 不做。中文 `ch` 估算误差大，且对求职作品集无说服力 |
| **数据来源声明** | **必要（属于"证据可信度"，不属于"视觉"）** | OWID 有 "Cite this article"；本项目已有 `ProvenanceBanner.astro`（toolbox）与 `resultsNote`（案例 metrics） | 保持现状：来源/口径声明放在正文前的元信息块里，**版头只负责视觉识别，不塞长声明** |
| **tags** | **装饰** | 我核验的站点里 tags 都不在版头（WordPress 类站点一般放文末） | 保持现状：标签在文末 |
| **面包屑** | **可选（推荐）** | OWID 版头有 `centered-article-header__breadcrumbs` | 本项目已有 `Breadcrumb.astro`。它是**解决"列表页看过封面、详情页又见封面"重复感的最低成本手段** |
| **封面 / 头图** | **可选（三选一，见 §1.4）** | The Markup 有（`.article-header--has-image`）；Nightingale 有 `entry-image--none` 分支；Pudding 只有 64px 小图 | 见 §1.4 |
| **分享按钮 / 评论** | **装饰** | IIB 有分享计数；The Markup 有 `article-footer-titles__share` | 不做（纯静态站、无后端） |

### 1.4 关键问题：列表页那张数据封面，详情页怎么复用

| 做法 | 真实案例（已实测） | 优点 | 缺点 | 对本项目（Cover.astro 536×301）的适配 |
|---|---|---|---|---|
| **(a) 同图复用作 hero** | The Markup：og:image 1200×628 与正文头图 841×473 / 750×422 是**同一张插画的不同裁切** | 资产只有一份；认知连续 | 详情页第一屏与列表卡片长得一样，**读者会怀疑自己没跳转**；536×301 拉到 1120 宽会变成 629px 高，首屏被封面吃掉 | ⚠️ **最省事但重复感最强**。若要用，必须配合面包屑 + 不同的比例/尺寸 |
| **(b) 宽幅 banner 变体** | OWID 预留 `centered-article-header__banner` 槽位（实测存在，本文为空）；Pudding 用 **64px 小图**替代大图；Nightingale 有"无封面"分支 | 同一套视觉语言、不同容器比例 → 既连续又不重复；宽幅 banner 天生适合"版头宽、正文窄" | **不能把 536×301 直接拉成 1120×420**：SVG 是绝对坐标，`preserveAspectRatio` 默认 `xMidYMid meet`，比例不匹配会留白/变形。必须新写一份 viewBox 与坐标 | ✅ **推荐**。算法见下 |
| **(c) 不用封面，改用指标条 / metric strip** | OWID 主题页有结构化 `"type":"key-insights"` 块（实测 JSON：heading "Key Insights on CO₂…" + insights 列表）；**本项目已有 `MetricCards.astro`** | 信息密度最高；最贴"数据新闻"气质；零图片资产；对 LCP 最友好 | 失去图文比例带来的"杂志感"；若数字本身弱，会像仪表盘 | ✅ **推荐（与 b 组合）** |

#### 关于「重复感」的正面回答

重复感来自**三件事同时发生**：同一个形状（16:9 卡片）、同一段文字（标题）、同一个位置（第一屏最上方）。打破其中任意两个即可，成本从低到高：

1. **必做（零成本）**：在版头插入 `Breadcrumb`（首页 / 案例研究 / 当前标题），并让版头 kicker 显示中文板块名（"案例研究"）而不是封面里的英文 `kicker`（"CASE STUDY"）。同一信息换语言/位置，重复感立刻下降。
2. **必做（一次改组件）**：详情页封面用**不同比例** + **不同内容密度**：列表卡封面只放 `metrics[0]`（现状 `headline: c.data.metrics[0]?.value`，源码实测 `index.astro`），详情页放**全部 facts** → "同族不同张"。
3. **可选（效果最好）**：正文前先给**指标条**（做法 c），把封面从"第一屏唯一视觉"降级为"版头辅助块"。

#### (b) banner 变体的具体算法（Cover.astro 改造）

源码实测：`Cover.astro` 里 `const W = 536; const H = 301;`，所有坐标（kicker y=46、headline y=158/178、分割线 y=216、facts 数字 y=248、标签 y=268、三列间距 168）都**硬编码在 536×301 坐标系**里。

- 现有宽高比：**536 / 301 = 1.781**。若只把容器变宽：
  - 720px → 高 404px
  - 608px → 高 341px（= The Markup 标题栏宽度）
  - 1120px（满版心）→ **高 629px**（首屏基本被吃掉，**不要这样用**）
- 目标 banner 比例建议 **1120×420（2.667）** 或 **1120×400（2.8）**。**不要用 `preserveAspectRatio="none"` 拉伸**（文字会变形）。
- 正确做法：同一组件加 `variant`，为 banner 单独写一套坐标：

```astro
---
// Cover.astro 增加 variant（示意；坐标是【判断】建议值，需目视验收后调）
type Props = CoverProps & { variant?: "card" | "banner" };
const { variant = "card", ... } = Astro.props;
const box = variant === "banner"
  ? { W: 1120, H: 420, kickerY: 56, headlineY: 210, sublineY: 248, ruleY: 292,
      factY: 340, factLabelY: 366, colStep: 260, padX: 56, maxFacts: 4 }
  : { W: 536,  H: 301, kickerY: 46,
      headlineY: shownFacts.length ? 158 : 178,
      sublineY:  shownFacts.length ? 190 : 210,
      ruleY: 216, factY: 248, factLabelY: 268, colStep: 168, padX: 30, maxFacts: 3 };
const { W, H } = box;
---
<svg class="block h-auto w-full" viewBox={`0 0 ${W} ${H}`} role="presentation" aria-hidden="true">
```

- banner 变体里 **facts 可放 4–5 列**（`colStep×4 ≤ W - padX×2`），卡片只放 3 列 → 直接解决"同族不同张"。
- `svg` 用 `h-auto w-full` + `viewBox`：**viewBox 提供固有宽高比，浏览器解析 CSS 时即可预留高度**，这是内联 SVG 相对 `<img>` 的一个实在优势（【判断】，务必用 §2.5 的方法实测 CLS=0）。

#### 尺寸计算速查

| 容器宽 | 保持 536×301 比例时的高 | 说明 |
|---|---|---|
| 536 | 301 | 组件原始尺寸（列表卡现状） |
| 608 | 341 | = The Markup 标题栏宽 |
| 672 | 377 | |
| 720 | 404 | 详情页单栏比较舒服 |
| 1120 | 629 | **过高一屏**，必须用 banner 变体才能满宽 |

### 1.5 版头与正文的阅读框宽关系

**真实站点的实测值**：

| 站点 | 页壳宽 | 版头文字栏 | 正文栏 | 关系 |
|---|---|---|---|---|
| The Markup | 1200px | **608px** | **620px** | 版头比正文**窄 12px**（差额正好是装饰出血） |
| OWID | 12 栏全宽 | 12 栏中的 **6 栏（起始第 4 栏）** | 起始第 **5** 栏 | 正文比版头更窄、且不对称 |
| The Pudding | — | 字号自适应（`clamp`），未给版头栏宽 | — | 字号自适应而非容器自适应 |

**本项目现状（源码实测）**：

- `@utility app-layout { @apply max-w-app mx-auto w-full px-4; }`，`max-w-app = max-w-[1120px]`（`src/styles/global.css`）。
- `@utility max-w-readable { @apply max-w-[68ch]; }`（同文件）。
- 详情页正文是 `class="app-prose max-w-readable"`，而 `.prose` 自带 `max-width:65ch`（`node_modules/@tailwindcss/typography/src/styles.js`）→ **实际生效的是更小的 65ch，`max-w-readable` 目前是死代码**（实施方案里顺手修掉，不然会误导后来人）。

**建议（【判断】+ 可直接抄的代码）**：引入三档宽度 token，把"宽版头 / 窄正文"从"靠类名碰运气"变成"有名字的容器"：

```css
/* src/styles/global.css 追加（Tailwind v4 @utility） */
@utility max-w-app      { @apply max-w-[1120px]; }   /* 已有：页壳 */
@utility max-w-headline { @apply max-w-[46ch];  }    /* 新增：版头标题栏 */
@utility max-w-deck     { @apply max-w-[52ch];  }    /* 新增：deck */
@utility max-w-readable { @apply max-w-[68ch];  }    /* 已有：正文（当前被 prose 的 65ch 覆盖） */
```

> 为什么是 46ch 而不是 608px：中文 1 字 ≈ 1em，**46 个中文字符 ≈ 736px**（按 16px 计），比 The Markup 的 608px 宽；但我们的版心只有 1120px，标题 46ch 在桌面上约 736px，两侧各留 ~190px，观感接近 The Markup 的 608/1200 = 0.51 的"半宽标题"。**建议在真机上目视微调**——【判断】中文标题的行长舒适区比拉丁短，标题尤其不该超过两行。

**版头与正文的分界处理（三条可核验参照）**：

- The Markup：`.article-title{margin-bottom:20px}`、`.article-body{margin:15px auto}` → 标题到正文总间距很小。
- The Pudding：`.byline{margin-bottom:5rem}` = **80px** → byline 到正文间距很大。
- 两者共性：**版头内部紧凑（12–20px 级），版头与正文之间疏（48–80px 级）**。这是"一个组块"的经典做法，建议采纳。

### 2.1 真实案例：hero 右侧到底放什么

### 2.2 面板内容清单：哪些能真实生成、哪些不能

**本项目已存在的真实数据源（源码实测 `site/src/pages/index.astro`）**：
`cases`、`latestAnalysis`、`latestReports`、`latestDissections`、`recordCount = (await getCollection("dissectionRecords")).length`；拆解条目另有 `claims.recordCount`、`claims.verdicts.{成功,部分,失败}`。

| 候选指标 | 能否真实生成 | 怎么取（构建期，零运行时请求） |
|---|---|---|
| 案例研究 N 篇 | ✅ | `(await getCollection("caseStudies")).length` |
| 数据分析 N 篇 | ✅ | `(await getCollection("analysis")).length` |
| AI 产品拆解 N 篇（主评/对照评各几篇） | ✅ | `dissections` + `data.depth === "主评"` 计数 |
| **评测记录 N 条**（含成功/部分/失败分布） | ✅ | `(await getCollection("dissectionRecords")).length`；分布用 `reduce` 聚合。**口径必须与 `check-dissections.mjs` 一致**（该脚本已有"报告数字 ↔ 记录集合一致性"校验，源码实测） |
| 工具箱报告 N 篇 | ✅ | `(await getCollection("toolkitReports")).length` |
| 数据集/标签 N 个 | ✅ | 对所有条目 `flatMap(data.tags)` 去重计数 |
| **最近更新时间** | ✅ | `max(pubDatetime ?? modDatetime)`，用 `Datetime` 渲染 |
| 总字数 | ✅ | 构建期统计 `entry.body`（中文字符数），**口径要写在小字里** |
| Lighthouse 四类分数 | ⚠️ **能，但必须由脚本产出 JSON，禁止手写** | 见下方 |
| 无障碍 100 分 | ⚠️ 同上 | 同上 |
| GitHub 活跃度 / commit 数 / star | ❌ **不要做** | 需构建期访问 GitHub API（构建依赖外网 + token + 限流），与"零第三方请求"的精神相悖；非要做的唯一安全形态是"构建期拉取、失败则整块不渲染"，成本远大于收益 |
| 访问量 / 阅读数 / 面试邀约数 | ❌ **不可能真实** | 纯静态站无后端；手写就是假数据 |
| "成功率" | ⚠️ 只有写清口径才可用 | 例如"拆解评测成功 41 / 128 条"；**不要把 `scores` 平均分包装成"成功率"** |

**明确拒绝的装饰性假数据**（建议在实施方案里写死这条）：`+∞`、`99%`、`10k+`、"5 年经验"、无来源的"用户满意度"、手写的 `Lighthouse 100`、"GitHub ★ 999"。**宁可面板只有 4 个数字，也不要有 1 个假数字** —— 这是求职作品集里最容易被面试官当场戳穿的地方。

**Lighthouse 分数怎么进面板（可落地，且不违背约束）**

源码实测 `site/scripts/lh.mjs`：在 `localhost:4321` 自起 preview，对每页跑两次 `npx lighthouse --output=json --only-categories=performance,accessibility,best-practices,seo`，阈值常量 `THRESHOLD = 90`，取两次高分。默认（不加 `--preset=desktop`）即 **Lighthouse 移动端配置**。

建议做法（三步）：

1. 在 `lh.mjs` 里增加一步：把每页四类分数写入**受版本控制的产物**，例如 `site/src/data/lighthouse.json`：
   ```json
   {
     "generatedAt": "2026-10-09T10:00:00+08:00",
     "preset": "lighthouse-mobile-default",
     "pages": 13,
     "worst": { "performance": 99, "accessibility": 100, "best-practices": 100, "seo": 100 }
   }
   ```
2. 首页 hero 面板只在 `import lh from "@/data/lighthouse.json"` 存在、且 `generatedAt` 在有效期（例如 30 天）内时渲染，并**永远显示 `generatedAt`**（"2026-10-09 实测"）。
3. 在提交流程里要求"改动了页面就必须重跑 `lh.mjs`"。**如果做不到自动，就干脆不放这一项** —— 写死的 100 分是负资产。

### 2.4 移动端怎么退化（1120 双栏 → 窄屏堆叠）

- **断点**：`lg`（1024px）以下堆叠。理由：1120px 版心在 `lg` 才真正有双栏空间；`md`(768) 下每栏只有 ~350px，方案 A 的两列 KPI 会被挤到换行。
- **顺序**：h1 → deck → CTA → **面板** → 社交。面板放 CTA 之后，避免首屏被数字占满。
- **面板内部**：方案 A 在 <400px 降为 `grid-cols-1`；方案 B 的 `<dl>` 天然单列（这是 B 的又一优势）。
- **留白守恒**：桌面 hero 建议 `pt-8 pb-10 sm:pt-12 lg:pt-16`，堆叠后不要缩太小，否则两个栏目会显得贴在一起。
- **可直接用的骨架**：

```astro

  class="border-border grid grid-cols-1 gap-8 border-b pt-8 pb-10 sm:pt-12 lg:grid-cols-12 lg:gap-10 lg:pt-16">
```

### 2.5 性能：数字递增 / 微型图会不会影响 LCP、CLS

#### 先给硬事实（都能追到来源）

**Lighthouse 性能分构成**（【API 实测】`core/config/default-config.js` 的 `auditRefs`）：

| 指标 | 权重 |
|---|---|
| Total Blocking Time (TBT) | **30** |
| Largest Contentful Paint (LCP) | **25** |
| Cumulative Layout Shift (CLS) | **25** |
| First Contentful Paint (FCP) | 10 |
| Speed Index (SI) | 10 |
| Interaction to Next Paint (INP) | 0（当前不计分） |

**判分阈值**（【API 实测】`core/audits/metrics/*.js` 的 `scoring.p10 / median`）：

- CLS：`p10: 0.1`、`median: 0.25`；源码注释原文："This 0.1 target score was determined through both manual evaluation and large-scale analysis."
- LCP（移动）：`p10: 2500` ms，`median: 4000` ms。
- 默认节流（【API 实测】`docs/throttling.md`）：`throttlingMethod: 'simulate'`（Lighthouse 默认），移动网络预设 = **延迟 150ms / 下行 1.6 Mbps / 上行 750 Kbps / 无丢包**（"Slow 4G"，约 4G 最差 25%）。
- **CPU 降速倍率**：我**没找到**（`core/config/constants.js` 与 `default-config.js` 里 grep `cpuSlowdownMultiplier` 无命中）→ **未核实**，不给数字。

**MDN 的定义**（【实测】原文）：

- CLS："measures the extent to which users encounter unexpected layout shifts, in which elements of the page are moved in an unexpected way: that is, that are not the result of a user action like pressing a button **or part of an animation**."；布局位移的典型原因："`<img>` or `<video>` elements that are not given width and height attributes"。
- `LayoutShift` 接口：**"Limited availability / Experimental"**（MDN 明确标注，非 Baseline）；有 `value` / `hadRecentInput` / `sources`（我在页面 HTML 里逐字符串确认存在）。
- `LargestContentfulPaint` 接口：**Baseline 2025（2025-12 起）**，属性 `element` / `renderTime` / `loadTime` / `size`。
- `prefers-reduced-motion`：Baseline Widely available（2020-01 起），用于"minimize the amount of non-essential motion"。
- `font-variant-numeric`：Baseline Widely available，"controls the usage of alternate glyphs for numbers…"。

#### 把事实翻译成对本项目的结论

1. **内联 SVG 封面/微型图**：不发起网络请求 → 不增加 LCP 的网络路径，**用它替换 `<img>` 是净收益**。**但"Inline SVG 是否计入 LCP 候选元素"我未核实**（MDN 的 LCP 定义只说 "largest image or text paint"），必须用下面第 4 条眼见为实。
2. **微型图的 CLS 风险 ≈ 0**，前提是容器有确定宽高比（`svg` 带 `viewBox` + `w-full h-auto`，或在容器上写 `aspect-ratio`）。MDN 说的"没写 width/height 的 `<img>` 会造成位移"在这里被 `viewBox` 的固有比例替代掉了。
3. **数字递增（count-up）是三项里唯一有真实风险的动作**：
   - ❌ 如果 JS 把 `12` 改写成 `7`、`128` 改写成 `3`，**文本宽度变化会让容器重排**，把旁边/下面的元素挤动 → 属于"元素位置变化"，会被记成 layout shift（【判断】，依据 MDN 对 layout shift 的定义；MDN 那句 "or part of an animation" 指的是 CSS 动画本身，不等于"动画驱动的内容变化不会被统计"）。
   - ✅ 三种安全做法，按推荐顺序：
     1. **不做递增，直接静态渲染**。Lighthouse 的 TBT 权重 30，任何 `requestAnimationFrame` 循环都在往那块送人头；递增对"可信度"零贡献。
     2. 固定宽度容器 + `font-variant-numeric: tabular-nums`（**本项目 `body` 已全局设置**，源码实测 `global.css`）→ 每个数字占同一宽度，数字变化不改宽度。
     3. 若一定要动，只动 `opacity` / `transform`（合成层），并用 `@media (prefers-reduced-motion: reduce){ animation: none }` 关掉；**不要动 `width` / `font-size` / `height`**。
4. **测量方法（三种，从便宜到正式）**：
   - **a. 眼看**：DevTools → Performance → 勾 Layout Shifts，刷新，看首屏有没有紫色方块。
   - **b. 代码量**（放进页面临时跑一次）：
     ```js
     // LCP 元素是谁？
     new PerformanceObserver(list => {
       for (const e of list.getEntries())
         console.log("LCP", e.startTime.toFixed(0), e.element?.tagName, e.element?.className, e.size);
     }).observe({ type: "largest-contentful-paint", buffered: true });

     // CLS 累计（含归因）
     let cls = 0;
     new PerformanceObserver(list => {
       for (const e of list.getEntries()) {
         if (e.hadRecentInput) continue;
         cls += e.value;
         console.log("shift", e.value.toFixed(4), e.sources?.map(s => s.node?.className));
       }
     }).observe({ type: "layout-shift", buffered: true });
     window.addEventListener("load", () => setTimeout(() => console.log("CLS =", cls.toFixed(4)), 2000));
     ```
     （属性名 `value` / `hadRecentInput` / `sources` 已在 MDN 页面确认存在；`LayoutShift` 在 MDN 标为 Limited availability，所以**只把它当测量工具，不要让它进生产代码**。）
   - **c. 正式验收**：直接用仓库里已有的 `site/scripts/lh.mjs`（源码实测：13 页 × 四类 × 每页跑两次取高分，阈值 90）。改动前后各跑一遍，**看 `performance` 这一类有没有从 100 掉下来**；它的默认配置正是移动端模拟节流，与约束 #2 的口径一致。
5. **额外一条容易踩的**：Evidence 面板里的"最近更新日期"若来自 `max(pubDatetime)`，它是**构建期常量**，零运行时成本；若做成"客户端算今天过去几天"，就会引入一个必然引起文本变化的更新 → 不要做。
