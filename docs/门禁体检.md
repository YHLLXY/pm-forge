# 门禁体检

> 起因：外部评审提出"构建门禁脚本已经很多（7 个），再加 `check-toc.mjs` 要考虑维护成本"。
> 本文用**实测数据**回答，不用估计。测量时间 2026-10-13，环境 Windows / Node（与构建同机）。
> 测量方式：`cd site && node scripts/<门禁>.mjs`，逐个计时，均为 dist 已就绪状态。

## 一、结论先行

| | |
|---|---|
| build 链里的门禁数 | **10 个**（外部评审说的"7 个"是少算了） |
| 10 个门禁的代码总量 | **775 行 / 32.4KB** |
| 10 个门禁串行实测总耗时 | **3 114 ms ≈ 3.1 秒** |
| 占比 | 一次完整构建（含 `astro check` + `astro build` + `pagefind`）约 1–2 分钟，门禁占 **约 3%** |

**判断**：维护成本的主要项不是运行时，是**每次新增门禁时的编写与反向验证**。10 个门禁平均 78 行，
单个门禁 29–169 行，属于"一屏能读完"的规模。**成本可接受**。

## 四、体检中发现的两个问题

### 4.1 一条隐私防线正在降级运行（真实）

`check-dissections.mjs` 每次运行都会打印：

```
⚠ 私有隐私词表未加载（out/dissection-privacy-lexicon.txt 不存在），人名词表子项跳过——防御不完整
```

实测 `site/out/dissection-privacy-lexicon.txt` **不存在**。于是隐私扫描只剩"模式层"（手机号 / 身份证号正则），
**"人名词表层"整体跳过**。

- **不是设计缺陷**：词表故意不入库（`site/.gitignore:5: out/` 已正确忽略，`git log -- site/out/*` 显示**从未跟踪过**）。这是"规则入库、具体词表留本地"的正确做法。
- **是真实缺口**：本机词表缺失 ⇒ 这道防线在本机**只有一半**。而它在构建里**永远是绿的**（缺失只 `warn` 不 `fail`），所以没人会注意到。
- **处置建议**：词表是私有的、内容只有你知道，需要你本地建一个；或者接受"模式层够用"。**本条登记为观察项，不擅自改门禁语义**。

### 4.2 `site/out/` 里堆了调试产物

`site/out/` 下现在有 `debug-doubao-composer.png`、`debug-doubao-count-answer.txt`、`debug-doubao-toggle.png`、`dissection-staging/`、`qa/`。
该目录已被 gitignore，不影响仓库，但属于可清理的运行残留。

## 五、给"要不要删门禁"的回答

**不删。** 理由：

1. 总成本 3.1 秒，不是负担。
2. 门禁的价值不在于"每次都抓到东西"，而在于**让某类错误不可能静默发生**——`check-headings` 诞生的原因就是 Lighthouse 100 分没挡住两个 `h1`。
3. 真正该做的是**给那 6 个"只有绿过"的门禁补反向验证**（证明它们能红），而不是删掉它们。

**关于"加 `check-toc` 会不会让门禁太多"**：本次新增的 `.vercel.app` 检查**不新开门禁文件**，折进已有的
`check-links.mjs`——这是对"维护成本"这条批评的直接回应。
