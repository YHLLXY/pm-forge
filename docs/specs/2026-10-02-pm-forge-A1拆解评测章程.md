## 1. 定位与拆解对象

**定位**：面向 AI PM 面试五考点之"模型评估与伦理风险"，展示"会评估 AI"而非"会用 AI"。板块回答的问题是：**一款面向消费者的 AI 产品，在具体任务上的真实能力边界是什么**——以实测记录回答，不以印象回答。

**拆解对象与深度分层（2026-10-02 已拍板）**：

| 产品 | 角色 | 深度分层（草案） |
|---|---|---|
| 豆包 | 主评 | 全量任务集（10-20 个）+ 完整失败案例库 + 边界探测 |
| Kimi | 对照评 | 核心任务子集，重点**长文本**维度对照 |
| DeepSeek | 对照评 | 核心任务子集，重点**推理与结构化产出**对照 |

- 分层理由：验收硬线（spec §3.3：≥10 任务实测 + ≥5 失败案例）按**板块总量**计，不按产品计；三产品全量并行会三倍膨胀工作量且装不进 11 月窗口。
- 对象调整：新增或替换拆解对象 = 修订本章程 + 用户拍板，缺一不可。

## 2. 六条铁律

（spec §3.3 必含条款的 operable 化，逐条可检查）

1. **自有数据**：只用自己账号下的真实输入输出；禁止爬取，禁止引用或转存他人会话数据。
2. **手动逐条**：不做任何规模性、自动化调用（含脚本批量、并发压测）；遵守各产品用户协议；额度/限流提示原样记录，不绕过。**修订款（v2.1）**：①用户已授权的 AI 协作者可以**人工节奏逐条代跑**消费端产品（一次一条、无脚本无并发），账号归属与授权责任在用户；②API 计费入口属服务的正常使用方式，用户授权下允许脚本逐条执行，不属于"规模性自动化"。**修订款（v2.2）**：网页端 DeepSeek 的代跑授权与豆包/Kimi 同款（OS 级键入禁止、DOM 层操作、不触碰本站以外窗口）。
3. **日期 + 版本留痕**：每条实测结论标注评测日期与产品版本。版本口径：产品内"关于/版本"信息或可见功能开关状态（如"深度思考：开"）；确实无法获得时统一标注"未公开版本 + 入口形态（网页/App/可见模型名）"。**无版本标注的结论不得发布**（评测记录 schema 校验兜底，见 §6）。
4. **措辞纪律**：只陈述"任务 X 在版本 Y 上的实测表现"；不做贬损性结论、不给产品整体打分或排名、不使用情绪化修饰语。跨产品对比只写"在任务 X 上，A 实测表现为…，B 实测表现为…"，不写"A 比 B 好"。
5. **时效声明**：报告页脚固定："产品持续迭代，本文结论可能过期，以评测日期为准。"
6. **隐私红线**：评测输入不得包含 vault 个人综合档案内容、真实他人姓名、学校、成绩等个人信息；测试输入一律使用可公开的合成任务。

## 3. 账号与成本口径

- **免费能力面为主**：评测在用户实际账号类型下进行，报告标注账号类型（免费/付费及可见会员权益）。
- **付费口径（2026-10-02 已拍板）**：豆包、Kimi 均未付费——按免费口径实测，报告标注"付费能力面未测"。DeepSeek 消费端聊天免费；用户 API 侧充值与余额（累计消费 300+ 元）**归 A2 线成本口径，与 A1 分账**，不混入拆解报告。
- **成本口径分账**：A1 只记录消费者产品形态的可见成本（免费额度、价格页可见的会员信息）；toolkit/evals 使用的 DeepSeek API 定价属 A2 线口径，不混入拆解报告。

## 4. 评测维度与任务集

- **rubric 复用 A2 四维**（锚点见 evals/rubric 文档）：事实性/幻觉控制、结构完整、可操作性、指令遵守；**新增产品化三维**：响应延迟（体感分档）、会员门槛、交互体验（改稿/追问/导出等）。
- **能力面分组**：写作 / 检索 / 结构化产出 / 边界探测。
- **失败案例库 ≥5 条**（板块总量）：失败输入 + 实际输出摘录 + 归因分析。失败案例与成功案例同等呈现，**不做选择性展示**。
- **边界能力探测**：逐条实测"能/不能"，每条附实测证据（输入 + 输出摘录）。

## 5. 版权与利益披露

- **截图**：一律自截图，每图标注"来源：{产品名}，截图日期"；只截产品界面与任务相关内容，不出现任何他人账号信息。不使用官方 logo 做页面装饰，产品以文字指称。
- **利益关系披露（DeepSeek 双重身份）**：本站工具箱底层调用 DeepSeek API。拆解 DeepSeek 的报告须在开头披露该关系，并声明：拆解结论基于对消费者产品形态的实测，与 API 依赖关系无关，不构成利益倾向。
- **引用**：产品输出原文摘录属合理引用范围，注明出处与评测日期；转述外部报道时链接须国内直连可访问，否则只述内容不挂链。

## 6. 评测记录与发布流程

- **接缝（spec §9.2）**：每条实测记录落评测记录 JSON（日期 / 版本 / 任务 / 输入摘录 / 输出摘录 / 评分 / 账号类型），报告页由 schema 驱动生成；schema 校验测试保证"无版本标注的结论"构建失败。schema 细节在 writing-plans 阶段定，不阻塞章程。
- **两步式发布（spec §10）**：实测材料生成到 out/ → 用户通读全文（措辞纪律终审）→ 显式拷贝进 site/content → 构建校验 → 发布。
- **验收沿用 spec §3.3 ①-⑤，不放宽**；上线前用户通读全稿是第 ⑤ 条的硬要求。
