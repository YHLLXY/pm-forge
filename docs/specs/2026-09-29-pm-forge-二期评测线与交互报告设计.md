## 1. 背景与目标

### 1.1 一期收工盘点（二期的起点）

一期四模块全部建成并维护中：analysis（M1 案例一）、toolkit（M2 三工具上线 toolbox.yuhailinlxy.com）、site（M3 五板块上线 yuhailinlxy.com）、vault-tools（M4 巡检三件套，37 测试）。工程地基（uv/pytest/pre-commit/任务卡协议）已被四个模块验证。

### 1.2 问题陈述

对照 2026 年 AI PM 面试五考点（技术边界 / Prompt 工程 / RAG-Agent 选型 / **模型评估与伦理风险** / 与算法团队对话）与作品集三件套（上线 AI 产品 ✓ / 拆解 AI 产品 ✗ / evals 计划 ✗）：**"模型评估"是 pm-forge 唯一没接住的考点**，拆解与 evals 是作品集空缺。此外作品集缺一个"面试官可以亲手玩"的差异化招牌。二期就是补这三件事。

### 1.3 工程目标（一句话）

把"会用 AI"升级为"**会评估 AI**"：为自家 toolkit 建 evals 门禁、发布一份方法论站得住的 AI 产品拆解报告，并交付一个面试官可现场自己查询的交互式数据故事——全部满足国内可访问与隐私红线。

### 1.4 不做什么（YAGNI 总纲）

- 不做多用户、登录、评论、国际化（继承一期总纲）。
- D（toolkit 产品化二期）整体不入二期范围；若用户重启，前置条件见 §6。
- 不做规模化/自动化调用第三方 AI 产品（A1 章程红线，§3.3）。
- evals 真实评分不进 CI（花钱且不稳定，CI 只做 schema 校验，§5）。
- B 不做完整自由 SQL 编辑器、不做移动端 WASM（§4 门禁）。
- C 不做批量发布，试点先行、白名单制、宁缺毋滥（§6）。

## 3. 主线 A：评测线

### 3.1 架构决策：新顶层目录 `evals/`

评测体系独立成第顶层模块，不放 toolkit 内、不放 analysis 内：

- **为什么独立**：职责是"质量门禁"，横跨 toolkit 三工具，既不是应用功能（toolkit）也不是数据案例（analysis）。面试叙事也需要它独立可见——"我为自己的 AI 产品建了评测体系"。
- **技术栈**：Python（uv + pytest + ruff + pre-commit），复用 M1/M4 已验证的工程模式；评分器走 OpenAI 兼容接口调 DeepSeek（key 只进 `.env`）。
- **依赖方向（单向，更新 AGENTS.md 依赖图）**：
  - `evals ──HTTP 黑盒调用──→ toolkit`（被测对象是**产品本身的 API 合同**，不 import toolkit 任何内部实现；本地起 dev server 或指向部署版，经 `.env` 配置 base_url）；
  - `evals ──报告 md──→ site/content`（评测计划与基线报告发布进工具箱板块）；
  - 评测集 JSONL 与 rubric 文档入 git（小文件、无隐私）。

### 3.2 A2 · toolkit evals 门禁（10 月，先开工）

**范围**：

1. **评测集**：三工具（竞品分析 / 用户反馈洞察 / PRD 草稿）各 20-30 条真实任务，JSONL 入 git。每条 schema：

   ```json
   {"id": "comp-001", "tool": "竞品分析",
    "input": {…工具入参…}, "task": "一句话任务描述",
    "difficulty": "基础|复杂|边界",
    "expect": {"must_include": ["…"], "notes": "人工关注点"}}
   ```

   案例须覆盖：常规任务、中文口语化输入、超长/残缺输入、边界（空结果、无竞品的小众产品）。

2. **Rubric 四维度**（调研依据：五考点"模型评估"+ 一期"证据链"精神的延伸），每维度 1-5 分并附**锚点示例**（好/差输出对照）：
   - **事实性 / 幻觉控制**：断言是否带证据链标注，编造成分有无；
   - **结构完整**：是否覆盖该工具产出 schema 的必需模块；
   - **可操作性**：结论是否具体、可执行，还是空话；
   - **指令遵守**：无证据结论是否按规范标"待验证"（幻觉标注遵守率）。

3. **评分器（LLM-as-judge）**：DeepSeek 打分，**钉版本纪律**（审查修订第 3 点）：固定温度 0；每次运行记录 API 返回的 `model` 字符串 + 评测日期；模型一旦升级、同集分数漂移即可被察觉；分数仅作回归参考，报告披露评分方法、版本与成本（预计 90 case × 2 次调用 ≈ 几元人民币，运行前按 M0 规则先估后跑）。

4. **人工校准**：从全集中抽 ≥30 条由用户+AI 双人独立评分，报告模型分与人工分的一致率（±1 分内），分歧逐条归因写进报告——这是"模型评估"考点的核心展示物。

5. **产出物**：
   - 《AI 工具箱 evals 计划》文档（PM 制品：目标、指标、方法、局限、成本）→ site 工具箱板块；
   - 基线报告（首跑分数 + 校准一致率 + 失败案例摘录）→ site + docs/；
   - 一键回归：改动 prompt 或代码后重跑，自动生成与基线的分数对比表。

**A2 验收（定死）**：

- ① 三工具各 ≥20 条评测集，JSONL schema 校验 pytest 全绿（非法记录 fail）；
- ② rubric 四维度各有锚点示例文档；
- ③ 评分全链可复现：温度 0、model 字符串与日期留痕、原始输出与评分留存 artifacts；
- ④ 人工校准 ≥30 条，一致率与分歧归因入报告；
- ⑤ 《evals 计划》+ 基线报告发布进 site 工具箱板块，含成本披露；
- ⑥ 一键回归命令可用，对比表自动生成；
- ⑦ pytest + ruff 全绿（沿用 pre-commit 纪律）。

### 3.3 A1 · AI 产品拆解板块（11 月）

**前置硬门槛：评测章程（审查修订第 1 点，开工前定稿并随板块首发）**。章程必含条款：

1. 只用自己账号下的真实输入输出，禁止爬取/共享他人数据；
2. 不做任何规模性、自动化调用（手动逐条，遵守产品 ToS）；
3. 每条结果标注**评测日期 + 产品版本**；国产产品多不公开版本号，统一口径为"产品内'关于/版本'或可见功能开关状态"，确实无法获得时标注"未公开版本 + 入口形态（网页/App/模型名）"；
4. 措辞纪律：只陈述"任务 X 在版本 Y 上的实测表现"，不做贬损性结论、不给产品整体打分排名；
5. 报告页脚固定声明："产品持续迭代，本文结论可能过期，以评测日期为准"；
6. 隐私红线：评测输入不得包含 vault 个人综合档案内容、真实他人姓名等个人信息。

**范围**：

- 选 1-2 个国产 AI 产品（§12 拍板；推荐排序见该节），按章程执行；
- **任务集 10-20 个真实任务**，按能力面分组（写作 / 检索 / 结构化产出 / 边界探测），复用 A2 rubric 并增加产品化维度（响应延迟、会员门槛、交互体验）；
- **失败案例库 ≥5 条**（失败输入 + 实际输出 + 归因分析）；
- **边界能力探测**（它能干啥/不能干啥，逐条实测）；
- 成本与延迟观测（免费能力面为主，付费维度视 §12 拍板结果）；
- 交互评测报告：site 新板块「AI 产品拆解」，报告组件层（§7）首个落地者。

**A1 验收（定死）**：

- ① 章程全文随板块首发，且每条实测结论可追溯到日期+版本标注；
- ② ≥10 个任务实测记录 + ≥5 条失败案例；
- ③ 报告页国内直连可开、Lighthouse 移动端不回退 M3 标准（≥90）；
- ④ 全部截图/引用为自产或已授权形态，版权处理方式在 plan 阶段定（倾向自截图+标注）；
- ⑤ 板块上线前用户通读全稿确认措辞纪律（对外发布物，AGENTS.md 变更前征得同意）。

## 4. 辅线 B：旗舰交互式数据故事（DuckDB-WASM）

**产品形态**：读者可自己查的交互报告——页面内嵌 DuckDB-WASM，数据（parquet）+ 预置查询 + 受限查询框全在浏览器本地跑；Observable Plot（ISC）画图 + Scrollama（MIT）滚动叙事；全部 npm 自托管进 site 构建产物，**零 CDN、零运行时第三方请求**（国内红线）。

**数据集**：默认复用 M1 已抽样的 UserBehavior 10 万行（转 parquet 自托管，预估几 MB；省取数）；若用户想要新叙事可换公开数据集（+1-2 天取数清洗，§12 拍板）。

**两道门禁（审查修订第 4 点，防 MVP 蔓延）**：

1. **体积预算门禁**：duckdb-wasm 资源约 30-50MB，国内移动端首屏不可接受。规则 = 懒加载（点击"开始探索"才拉 WASM 与 parquet）+ 构建检查脚本实测产物体积，预算上限写进脚本（parquet ≤5MB、WASM 全套 ≤40MB，spike 实测后回填精确值），超限构建 fail。
2. **移动端降级门禁**：移动端只渲染**预生成图表**（构建时本地 DuckDB 跑出结果固化）+ 提示"桌面端可自由查询"，绝不加载 WASM。

**MVP 卡界**：预置问题清单（8-12 个）+ 3-5 个交互图（可调参数）+ 1 个受限查询框（白名单列 + 模板化 SQL，非自由编辑器）。**多了不做。**

**B 验收（定死）**：

- ① 首屏（未点击"开始探索"前）网络面板验证零 WASM/parquet 下载；
- ② 桌面端预置问题、交互图、受限查询框全部可用；
- ③ 移动端视口（Playwright）降级模式可用且无 WASM 加载；
- ④ 体积门禁生效（人为塞超限文件验证 fail）；
- ⑤ 国内直连可开、Lighthouse 移动端 ≥90；
- ⑥ 滚动叙事 ≥5 节，每节有指标口径标注（复用报告组件层）。

## 5. 插空 E：工程基建小包（半天级，随时插空）

1. **GitHub Actions CI**（pm-forge 为公开仓，Actions 免费额度充足）：矩阵 job——site（astro build）、toolkit（vitest + next build）、analysis / vault-tools / evals（pytest）。**evals 只跑 schema 校验，不跑真实评分**（不花钱、不依赖 key）。
2. **站内搜索复活（Pagefind）**：M3 移除搜索是为避开二进制分发坑。**2026-09-29 已实测**：npmmirror 有 pagefind 1.5.2 主包 + `@pagefind/windows-x64`、`@pagefind/linux-x64` 平台二进制，障碍消除 → 纳入范围；构建时索引、客户端运行，符合国内红线；集成后对中文内容实测分词效果，不达预期则砍掉此项（决策规则预先定死）。
3. **RSS 全文输出**（@astrojs/rss）。
4. **SEO 结构化数据**（JSON-LD：Person / WebSite / Article）。

**E 验收（定死）**：① CI 主分支全绿；② 搜索对 site 中文内容返回正确结果（含分词验证例）；③ RSS 通过验证器；④ JSON-LD 通过 schema 校验；⑤ Lighthouse 各项不回退。

## 6. 第二梯队 C：vault → 公开方法论文库（寒假 2027-01）

**管线**：vault-tools 扩展发布子命令：白名单 → **自动脱敏扫描** → **wikilink 链接重写**（vault 内链 → 移除或改"相关方法论"占位，审查修订第 2 点的硬伤）→ frontmatter 转换（保留 `source: claude`）→ 输出 site/content → 构建校验。

**脱敏扫描器**：词表覆盖真实人名、学校/班级、成绩数字、情感/家庭类、内部域名词表；情感/家庭类命中即 fail（硬红线），其余命中人工复核。白名单机制：非白名单文件即使误操作也进不了管线（测试证明）。

**试点先行**：首篇候选《2026-09-28-vault只读巡检三件套的键控消歧设计》（内容干净、含真实仓库链接可核验）。试点过审前不谈规模，**宁缺毋滥**。

**C 验收（定死）**：① 试点文章上线且公开站内链零悬空；② 脱敏扫描器 pytest 全绿（正/负用例夹具）；③ 白名单外内容进不了管线（测试证明）；④ 发布前人工通读 + 对照 vault 原文 diff 终检。

**D（toolkit 产品化二期）**：不入二期。若未来重启，前置条件：分享链接必须带显式确认 + 过期机制（评测输入可能含用户自己的数据）。

## 7. 报告组件层（跨工程架构决策，审查修订第 5 点）

现有 Quarto 静态报告、A1 交互评测报告、B 交互数据故事三形态**不得各起一摊**。决策：在 site 内建统一报告呈现层——

- 一套 **design token**（色板 / 字号 / 口径标注样式）落 `shared/style/`，site 组件实现（ReportLayout / 分数徽章 / 维度条 / 口径标注组件）；
- Quarto 报告经 CSS 变量套用同一配色；A1、B 直接用组件；
- 图表配色规范统一（Observable Plot 与既有报告图表同一色板）。

具体组件形态在 A1 writing-plans 时定，本 spec 定原则：**三个报告形态，一套视觉与口径语言**。

## 8. 用户故事

1. 作为求职中的 PM，我想有一份自己产品的 evals 计划与基线报告，以便在面试中证明"会评估 AI"而不只是"会用 AI"。
2. 作为求职中的 PM，我想发布一份方法论站得住的 AI 产品拆解报告，以便展示产品判断力而非自夸项目。
3. 作为面试官，我想在候选人的站点上亲手跑一个查询、看到实时出图，以便确认候选人的数据分析能力是真实的。
4. 作为 toolkit 的用户，我想知道每个工具在什么任务上可靠、什么任务上会翻车，以便正确使用而不是盲信输出。
5. 作为 toolkit 的维护者，我想在改动 prompt 后一键重跑评测并看到分数对比，以便确认改动没有让质量回退。
6. 作为评测报告的读者，我想看到每条结论的评测日期与产品版本，以便自己判断结论是否过期。
7. 作为评测报告的读者，我想看到失败案例而不只是成功展示，以便信任这份评测的客观性。
8. 作为手机上的访客，我想在没有 WASM 的降级页面看到预生成图表，以便不耗尽流量与内存也能读完报告。
9. 作为站点读者，我想用站内搜索直接搜到"幻觉""RFM"等中文关键词对应的页面，以便快速定位内容。
10. 作为站点订阅者，我想通过 RSS 读到全文更新，以便不漏新案例。
11. 作为知识库的主人，我想把一篇干净的方法论笔记安全地发布到公开站，以便展示知识资产化能力而不泄露隐私。
12. 作为未来的我，我想让脱敏扫描器自动拦截含隐私的笔记，以便即使疏忽也不会把个人档案发上公开互联网。
13. 作为面试备战者，我想让"评测章程"先于任何拆解内容发布，以便整条评测线的客观性有公开承诺背书。
14. 作为协作者（AI），我想让 CI 自动验证五模块构建与测试，以便每个改动都有统一的绿色基线。

## 9. 测试决策与接缝

**接缝选择（从高到低，尽量少）**：

1. **A2 最高接缝 = toolkit 三工具的 HTTP API 合同**（黑盒产品级评测，测的是产品不是 prompt 复制品）；次级接缝 = 评分器 `judge(case, output, rubric) -> Score` 依赖注入点（pytest 用录制的响应 fixture，单测永不真实调用 LLM）。
2. **A1 接缝 = 评测记录 JSON schema**（日期/版本/任务/输出摘录/评分），报告页由 schema 驱动生成，schema 校验测试保证不出现"无版本标注的结论"。
3. **B 接缝 = 图表组件纯 props 接口**（预置查询结果 → 图）+ 构建体积检查脚本（门禁本身即测试）。
4. **E 接缝 = CI workflow 本身**。

**测试原则**：只测外部行为（HTTP 响应结构、报告渲染产物、schema 校验、构建产物体积），不测实现细节；沿用一期先例——toolkit 用 vitest + Playwright，Python 模块用 pytest，site 用 astro build 作构建校验；B 新增 Playwright 桌面/移动双视口用例与产物体积断言；所有 LLM 相关单测走 fixture，真实调用只在显式的评测运行中发生。
